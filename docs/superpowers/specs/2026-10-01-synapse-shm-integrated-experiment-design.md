## 0. 语义重构：为什么不能照搬 E1 装置的实验设计

E1 的 sweqa 装置回答的问题是"**系统 vs 系统**"：share/share-pipeline/nico/tintinweb 四个臂是四个完整系统，比 token、比质量，臂间配对。

SHM 并入 SYNAPSE 之后，它不再是"另一个系统"，而是 **SYNAPSE 状态平面的存储层子系统**。它的实验语义随之改变：

1. **臂内条件，不是臂**。SHM 的正确位置是 share/share-pipeline 臂内部的 on/off 条件；nico/tintinweb 作为第三方插件永远没有这个条件——它们是对照系，不是被试。
2. **收益记账在宿主侧，不在模型接口侧**。SHM 消掉的是"每次状态消费全量读盘+哈希+解码"的宿主机成本（E0a 实测 62.7ms/5.5MB → 段命中 ~0ms/0B），token 是模型输入输出计量、预期不变。两种账并列、永不混算。
3. **间接机制通道必须测**：SYNAPSE 有状态预算（`SYNAPSE_STATE_BUDGET_MS`），加载超预算会 `state-skipped`（状态面静默降级）。SHM 压缩加载时长 → **可能提高状态面激活率**——这是 SHM 唯一可能影响 token 的机制通道（状态发不出去/收不回来都会改变对话形态），必须作为一等指标测，不能只测延迟。

## 2. 实验矩阵

### L0 机制层（完成，零成本，每版本回归必跑）

- `test/unit/synapse-shm-*.test.ts`（31 项：段协议+语料平面+装配）
- 钉扎等价：段/文件两加载器产出 deep-equal（chunkIds/meta/previews/逐 float），排序与得分一致——**这一条是所有上层实验的效度前提**，版本变了重跑。

### L1 微基准（完成，零 API 成本）

E0a（run=shm-e0-20260930）：64/256/1006 chunks 三负载 × 120 对，shm 全部显著更快（0.45/1.96/8.10ms vs 0.86/3.66/14.54ms）。不追预算。

### L2 任务组账本（E0c，跑中）

真实 pi 四角色（role-pipeline 固定编排）× SWE-QA Flask 3 题 × 段开/关。判定（功能断言，冻结于 E0 spec）：段开臂每任务 `shm-attach≥1 && corpus-load=0`、段关臂 `corpus-load≥1`、答案有效。首个 attempt 已验证激活（attach=1/hit=1/corpus-load=0）。

### L3-E1s 小规模臂内配对（重跑中，~15 元）

- 设计：SYN 臂（share 产品自然形态）段开/关 × SWE-QA q4–q7（4 题 8 任务），同题配对、臂序交替。
- 指标与判定（冻结于 E0 spec §3.4 + e1s-report）：
  1. **主指标（功能断言）**：corpus-load 配对差 CI 下界 > 0（段接管加载）；
  2. 墙钟配对差 CI（n=4 只报方向，标"已实现待扩样"）；
  3. token 并列（预期同分布，不设判据）；
  4. **state-skipped 率并列**（本设计新增的观察项，E1s 报告补列）。
- 边界（冻结）：每题独立 storageRoot（公平性：每题同冷起点）；跨任务驻留由 E3 判定；不测 reads/轮（P6-5 正文装段决赛后）。

### L3-E2 四臂嵌套（正式规模，决赛后，~40–60 元，待批）

E1 装置框架的复用与改造点：

| E1 装置组件 | 复用方式 | 改造 |
|---|---|---|
| `matrix.mjs` 四臂/抽样冻结 | 原样复用臂定义与种子（样本字节一致） | 增 `SHM_CONDITIONS = [off, on]`，只作用于 `SHARE_ARMS` |
| `run.mjs` manifest/续跑/不中断/evidence | 原样复用 | manifest 增 `synapse.shm` 与 `SYNAPSE_SHM` env 记录；段开配置在臂内注入 |
| `analyze.mjs` 会话归因/token | 原样复用 | 增 shm-*/corpus-load/state-skipped 账本列（本项目 v7 事件） |
| `score.mjs` 官方 judge/盲评/中位数 | 原样复用 | 不改（质量口径与 E1 完全可比） |
| `report.mjs` 配对 bootstrap/δ 非劣 | 原样复用 | 预定义配对扩两组：share(on)−share(off)、share(on)−框架臂 |

- 配置矩阵：share × {off,on}、share-pipeline × {off,on}、nico、tintinweb = 6 配置；15 题（60 题正式版的前 15，E1 同种子抽样）× 6 = 90 任务。
- 判定（冻结于跑数前）：
  1. **H1a（主）**：每 share 臂内 on−off 的语料加载字节配对差 CI 下界 > 0；
  2. H1b：on−off 墙钟非劣（CI 下界 > −δ，δ=60s）；
  3. H1c：on−off 的 state-skipped 率差 ≤ 0（方向性；机制通道）；
  4. H1d：on−off token 等价（并列报告，CI 跨 0 = 预期成立）；
  5. H2（探索性，不设硬判定）：share(on) 对框架臂的 token/质量与E1 历史结论的关系——"SHM 是否扩大系统间优势"只做描述。
- 红线：E2 的系统间数字与E1 sweqa 正式跑**分口径报告**（模型同、装置代次不同），永不合并池。

### L4-E3 跨任务驻留链（新增，小成本 ~5 元，可与 E2 并行批）

- 设计：同一 storageRoot+namespace 上连续 4 题（share 臂），段开臂不清理段（跨任务驻留是常态）；对照=同 4 题独立 storageRoot（每题冷起点）。两序列 × 2 臂 = 16 任务。
- 判定：驻留臂第 2 题起 `corpus-load=0 && shm-hit≥1`（账本逐题证明）；首题 publish 成本单列（首次加载 62ms 一次性）；**"跨任务累计字节节约 = (题数−1)×5.5MB/题"的实测对账**。
- 语义：这是设计文档 v1"跨 run 驻留"主张的任务级证据，也是答辩叙事"记忆平面常驻"的支撑数字。

## 3. 本项目设计资产（E1 装置没有、必须保留的）

1. **I/O 级账本事件**（metering v7：shm-attach/hit/miss/invalid + corpus-load）：E1 的 analyze 只有 token/通信分类，没有文件字节级事件。这是 H1a 能判定的唯一证据基础。
2. **钉扎等价性测试**：任何"更快"的主张都先证"没变语义"。
3. **口径分离纪律**：token 列、宿主字节列、激活率列三账并列，判定各归各。
4. **机制证据方法论**：进程身份（writer PID）、账本归属（哪条 service 写的事件）定位法——本次首批翻车的诊断正是靠它。
