# S2：跨进程共享内存数据面设计

- 日期：2026-09-20
- 状态：设计草案，待评审
- 目标平台：openEuler 24.03-LTS-SP3
- 依赖：[S1 iSulad 容器化运行时](2026-09-20-synapse-isulad-runtime-design.md)
- 相关：[S3 eBPF I/O 观测](2026-09-19-synapse-ebpf-io-metering-design.md)、`src/synapse/content-store.ts`、`src/synapse/envelope-inbox.ts`

## 1. 背景

赛题要求验证"结构化通信、非文本状态传递和共享记忆复用在减少重复计算、降低协作开销和提升任务效率方面的
实际效果"，并统计"文本通信 token 或字符开销、非文本状态传递次数及数据规模"。

Python 原型 README 对自己的字节数字有一句诚实的限定：

> 进程内共享 CAS 口径下，逻辑消息字节降低 HotpotQA **94.6%**、MuSiQue **96.5%**
> （**真实跨进程传输字节将在数据平面实测**）。

"进程内口径"意味着那是**理论上界**。本仓库今天的情况相同：`content-store.ts` 是本地文件 CAS，
`envelope-inbox.ts` 是原子写文件投递，README 已知缺口 #5 写着「信封的句柄尚未兑现」——
子 Agent 校验完信封就丢弃，不会按 `memoryRefs` 去取正文。

S2 把这个口径变成实测。

### 1.1 与 PR #11 的边界（重要）

PR #11「P3 完整向量状态交换 + P4-1 残差编解码」覆盖 `embedding.ts`、`delta.ts`、`corpus.ts`、
`state-retrieval.ts`。它解决的是**传什么**：把语义状态编码成残差，线缆上只走句柄。

**S2 解决的是字节怎么动**：CAS 放在哪、投递走什么传输、句柄如何兑现。

两者正交，且 S2 让 PR #11 的收益第一次可被真实测量——残差编码省下的字节，
只有在传输层真实存在时才谈得上"传输开销降低"。

**S2 不得重新实现 PR #11 的任何部分。** 动工前先确认 PR #11 的合并状态。

## 2. 范围

### 2.1 做

- CAS 从普通文件系统移到 `/dev/shm`（tmpfs），使内容对象在共享 IPC namespace 的容器间可直接读取。
- 信封投递从原子写文件换成 **AF_UNIX `SOCK_SEQPACKET`**。
- **兑现句柄**：子 Agent 按 `memoryRefs` 主动从 CAS 取正文，而不是随提示词接收引用加摘要
  （关闭已知缺口 #5）。
- 让 `MeteringTotals.control.transportBytes` 第一次成为真实的量。

### 2.2 不做

- 不做语义层。embedding、残差编码、向量检索属 PR #11。
- 不做跨节点。Gazelle / DPDK 只在跨节点大吞吐场景才值得，而本设计是同机。
- 不做自适应传输策略引擎（按消息大小在 UDS / SHM / 网络间选档）。那需要 S2 与 S3 都落地后
  用实测数据校准；没有数据的选档就是拍脑袋。
- 不删除文件投递路径。它是对照组，也是 S1 降级时的退路。

## 3. 架构

```text
   父会话                                          子 Agent
      │                                               │
      │  1. put(bytes) ──────────────┐                │
      │                              ▼                │
      │                    ┌──────────────────┐       │
      │                    │  /dev/shm 上的   │       │
      │                    │  内容寻址存储     │◄──────┤ 3. 按句柄取正文
      │                    │  （tmpfs）       │       │    （兑现 memoryRefs）
      │                    └──────────────────┘       │
      │                                               │
      │  2. 信封（只含句柄 + 校验码）                    │
      └────────── AF_UNIX SOCK_SEQPACKET ─────────────►│
                                                       │
                 大数据不传，只传引用
```

### 3.1 为什么是 `SOCK_SEQPACKET` 而不是 `SOCK_STREAM`

信封是**有边界的消息**，不是字节流。`SOCK_SEQPACKET` 原生保留消息边界，
省掉长度前缀 framing 与其带来的一整类半包/粘包错误。Python 原型走的是
AF_UNIX 长度前缀 framing（`protocol/transport.py`），S2 可以直接用更强的原语。

### 3.2 `/dev/shm` 而不是 POSIX `shm_open`

Node.js 没有原生的 POSIX 共享内存绑定，用 `shm_open` 需要 N-API 原生插件——
而 VISION 的「Compose before inventing」要求先用现有原语。

`/dev/shm` 是 tmpfs，**普通文件 API 就能读写**，因此 `content-store.ts` 的现有实现
（临时文件 + rename 发布、读时重算摘要）几乎可以原样搬过去，只换存储根。
代价是多一次页缓存拷贝，收益是零原生代码、零新依赖、现有测试全部可复用。

若 S3 的实测显示这层拷贝构成瓶颈，再考虑原生 mmap——但那要有数据支持，不是预判。

## 4. 关键决策

### 4.1 `transportBytes` 在这里诞生，且必须与内核账对账

S3 刻意把 `control.transportBytes` 保持为 `"N/A"`，理由写在其 §5.1：内核 VFS 字节与传输字节
是两个量，文件投递的字节可能整段命中页缓存而从未触及任何传输介质。

S2 把投递换成 socket 之后，`transportBytes` 第一次真实存在，并且有了一个**可证伪的对账关系**：

```text
socket 上发出的字节（应用层自报）
        ≈
内核侧观测到的 sendmsg/recvmsg 字节（S3 采集器）
```

两者不符即有一方错了。这是 S2 的核心验收，也是 S3 存在的意义第一次兑现。

**注意：S3 当前的线协议只有 `write`/`read`/`openat`/`renameat2` 四个 syscall。**
要观测 socket 传输，S3 的契约必须扩展 `sendmsg`/`recvmsg`（或 `sendto`/`recvfrom`）。
这是 S2 对 S3 的一个明确的反向依赖，须在实现计划里排在对账实验之前。

### 4.2 句柄兑现改变了消息的含义，不只是尺寸

今天记忆以"引用加摘要"随提示词传递——子 Agent 拿到的是**文本**。
兑现句柄后子 Agent 拿到的是**引用**，正文按需取。

这不是一次尺寸优化，而是控制面与数据面的分离：

```text
今天：  State → Text → 文件 → Text → State
S2：    State ──────── 共享 ─────────→ State
        同时：Instruction → 小控制消息 → Agent
```

因此 S2 必须同时回答一个正确性问题：子 Agent 取正文时的**权限投影**如何保持。
现有 `LaunchContract.scope` 与 `access.ts` 已经约束了"子 Agent 能看什么"，
句柄兑现**不得成为绕过该约束的旁路**——这是比字节数更重要的验收项。

### 4.3 文件路径保留为对照组

赛题明确要求"系统需同时支持纯文本协作模式和结构化协议协作模式，并在相同任务条件下完成可复现实验对比"。
S2 因此不删除文件投递，而是让传输方式成为可配置档位，由 S4 的实验框架在同条件下 A/B。

## 5. 失败行为

| 情况 | 处理 |
|---|---|
| `/dev/shm` 不存在或不可写 | preflight 拒绝启用共享内存档位，退回文件 CAS，**在产物中标记** |
| 跨容器读不到对端写入的对象 | 说明 IPC namespace 未真正共享（S1 的前提破了）——拒绝，不得静默退回 |
| socket 连接失败 / 对端不在 | 按现有错误分类处理；投递失败不得被记为"投递成功但内容为空" |
| 句柄兑现时对象已不存在 | 走现有 `object-unavailable` 分类，与 `rehydrateLaunchContract` 的语义一致 |
| 子 Agent 无权读取所引用对象 | **拒绝兑现**，记为权限错误。见 §4.2 |

## 6. 测试与验收

**CI 层**：传输选档、句柄兑现的权限投影、错误分类——纯函数与可注入接缝，Windows 可测。

**openEuler 真机层**：

1. **跨容器可见性** —— A 容器 `put` 的对象，B 容器按句柄读到且摘要一致。（依赖 S1 的验收 1）
2. **`transportBytes` 对账** —— 应用层自报的 socket 字节与 S3 内核侧观测的字节相符（§4.1）。
   **这是 S2 最重要的一条**：它同时证明 S2 的计量与 S3 的采集都是对的。
3. **权限不被旁路** —— 构造一个子 Agent 引用其 scope 之外的对象，断言兑现被拒绝。
4. **A/B 可复现** —— 同任务、同模型、同种子下文件档与共享内存档各跑一次，
   字节与时延的差值稳定可复现。

## 7. 开放风险

- **S1 未落地前 S2 无法跨容器验证。** 单进程内的共享内存 CAS 可以先实现并测试，
  但"跨进程真实传输字节"这个核心目标要等 S1。
- **S3 的线协议需扩展 socket syscall**（§4.1）。这是一次对已评审契约的修改，需按 S3 的
  纪律重新验收其解析器与归因。
- **PR #11 的合并状态未知。** 若它已合入，S2 的句柄兑现须与其 `state-retrieval.ts` 协调而非重复。
- **`/dev/shm` 默认大小有限**（通常为内存的一半），大对象场景需要容量策略与清理策略。
  现有 `SYNAPSE_DEFAULT_MAX_OBJECT_BYTES`（1 MiB）是起点，但 tmpfs 的总量约束是新问题。

## 8. 交付边界与后续

S2 交付后，"逻辑消息字节降低 94.6%" 这类数字第一次有了跨进程的实测支撑，
而不是"进程内口径"的理论上界。`transportBytes` 成为真实的量，并被内核侧独立对账。

后续（S5，本设计不涉及）：拿到 S2 与 S3 的实测数据后，才谈得上按消息大小、扇出度与队列长度
在 UDS / 共享内存 / 网络之间自适应选档。
