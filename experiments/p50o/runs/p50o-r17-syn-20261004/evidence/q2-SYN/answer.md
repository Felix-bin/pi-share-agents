## Purpose of the registration tracking flag

The flag is `Blueprint._got_registered_once`. Its purpose is to turn "setup after registration" into a hard failure, because a blueprint's setup work is not performed when you call the setup method — it is *recorded* as a deferred function and replayed by `Blueprint.register`. Once registration has happened, anything recorded afterwards can no longer be applied consistently, so Flask raises instead of silently dropping or half-applying it. The error text in the code states this purpose outright: *"It has already been registered at least once, any changes will not be applied consistently."* (`src/flask/sansio/blueprints.py:213-221`).

**Where the flag lives and how it is flipped** (verified in the tree; the ranked anchors' `flask/src/...` path does not exist here):
- Declared as a class attribute: `_got_registered_once = False` at `src/flask/sansio/blueprints.py:172`, directly on `class Blueprint`.
- Set to `True` at `:320` inside `Blueprint.register`, between `app.blueprints[name] = self` (`:319`) and `state = self.make_setup_state(...)` (`:321`) — i.e. *before* the static-folder rule, the `_merge_blueprint_funcs` call and the replay loop `for deferred in self.deferred_functions: deferred(state)` (`~:338`). So it marks "registration has begun/occurred at least once", not "setup finished replaying".
- Read at `:214` in `Blueprint._check_setup_finished` (`:213-221`), which raises `AssertionError`.
- A repo-wide grep for the identifier returns exactly three hits, all in that one file (declare/read/write), and there is no reset anywhere — it is a one-way latch: once a blueprint has been registered on any app, its setup phase is permanently closed.

**How the flag is enforced.** `@setupmethod` (`src/flask/sansio/scaffold.py:42-49`) wraps each setup method so that `wrapper_func` calls `self._check_setup_finished(f_name)` and only then invokes the method. The base `Scaffold._check_setup_finished` raises `NotImplementedError` (`scaffold.py:220-221`); `Blueprint` overrides it with the flag check (`blueprints.py:12` imports `setupmethod`). The flag therefore covers both the blueprint's own mutators (`record:223`, `record_once:232`, `register_blueprint:255`, `add_url_rule:412`, `app_template_filter:443`, `app_template_global:515/534`, `before_app_request:553`, …) and the `Scaffold`-inherited ones (`route:335`, `get/post/put/delete/patch:295-327`, `endpoint:435`, `before_request:459`, `errorhandler:597`, …). Execution confirmed this for `route`, `before_request` and `add_url_rule` after `register_blueprint`: each raised the quoted message, while `GET /x` still returned `200 b'x'`; a fresh blueprint's flag is `False`, and the attribute exists on `Blueprint` only, not on `Scaffold`.

**Why "consistently" is the operative word.** Two distinct hazards are behind the message. (1) The deferred replay happens in `register` (`:337-338`), so setup added after that is never replayed for the app that already registered the blueprint. (2) The same blueprint may be registered again later on another app or under another name — executed check: one blueprint registered on two apps under two names, flag staying `True`, `len(bp.deferred_functions) == 1`, both apps serving `/x`. A mutation made after the first registration would reach only the later registration and not the earlier app, which is exactly divergent state. Point (2)'s cross-app divergence is inferred from the mechanism rather than executed directly; the mechanism parts (write-before-replay, second registration, unchanged `deferred_functions`) were verified.

**It used to be a warning, now an error.** `CHANGES.rst:160-161`: *"Calling setup methods on blueprints after registration is an error instead of a warning. :pr:`4997`"*. The earlier release recorded the intention (`CHANGES.rst:297-300`, issue `4571`): such use "will show a warning. In the next version, this will become an error just like the application setup methods." The flag's current role is to back that error.

**App-side analogue, deliberately using a different attribute.** The application scaffold enforces the same class of rule with `_got_first_request` (`src/flask/sansio/app.py:411,414`; `src/flask/app.py:667,911`) and the message "has already handled its first request" (`docs/lifecycle.rst`, ~42-49). The rationale quoted there — WSGI servers may run many workers across distributed machines, so setup must be complete before serving — is the same reason a blueprint must be fully set up before registration; a blueprint has no request lifecycle of its own, so its trigger is registration rather than first request.

**On "blueprint collection class".** No class named `*Collection` exists in `src/` (the only `Collection` token is the annotation `t.Collection[str] | None` at `src/flask/views.py:51`). I resolve the task's phrase to `Blueprint` (default reading, stated because the name does not match): it is the class in this worktree that both collects the deferred setup functions (`self.deferred_functions: list[DeferredSetupFunction] = []`, `blueprints.py:207`) and carries the registration-tracking flag. The app-side `app.blueprints` is a plain dict attribute, not a class, and holds no such flag. If the task meant a differently named container, this identification is an inference from those two properties rather than a name match.
