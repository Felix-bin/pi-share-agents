# Answer

The separation is a three-layer split, not a single hook. Static-asset *state and primitives* live in the shared sansio base, static-asset *serving and cache policy* live only in the two WSGI-facing components, and *registration* is an abstract primitive in the base that each component fills in — with caching kept consistent by making both components read the same app-level config value rather than by inheriting one implementation.

**Layer 1 — the shared seam (`Scaffold`, `src/flask/sansio/scaffold.py:52`).** `Scaffold` is documented as the "Common behavior shared between `Flask` and `Blueprint`" (lines 53-54) and is the base for both sansio classes (`sansio/blueprints.py:119 class Blueprint(Scaffold)`, `sansio/app.py:59 class App(Scaffold)`). It owns the static *state*: class attrs `_static_folder`/`_static_url_path` (72-73), `__init__` params `static_folder`/`static_url_path`/`template_folder`/`root_path` (75-81), and the primitives `static_folder` property/setter (224/234), `has_static_folder` (241), `static_url_path` property/setter (249/265, the property deriving `f"/{basename}".rstrip("/")` when unset). It does **not** own serving: a grep of `src/flask/` for `send_static_file|get_send_file_max_age` returns hits only in `app.py`, `blueprints.py`, `helpers.py`, and one call site in `sansio/blueprints.py` — never in `sansio/scaffold.py` or `sansio/app.py`. The runtime-typing proof is `sansio/blueprints.py:326`: `view_func=self.send_static_file,  # type: ignore[attr-defined]` — the ignore exists because the method is not there. Similarly, `Scaffold.add_url_rule` (368) is pure abstraction: its whole body is `raise NotImplementedError` (433), as does `_check_setup_finished` (220-221).

**Layer 2 — the two components implement serving, and they duplicate rather than inherit.** `Flask` has `get_send_file_max_age` (`app.py:281`) and `send_static_file` (`app.py:308`); `Blueprint` has the same pair (`blueprints.py:55`, `:82`). The two `get_send_file_max_age` bodies are textually identical (app.py:298-306 vs blueprints.py:72-80 — same statements, order, and trailing `# type: ignore[no-any-return]`), and the two `send_static_file` bodies share the same explanatory comment ("send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too.") and the same `max_age = self.get_send_file_max_age(filename)` → `send_from_directory(...)` shape (app.py:325-328, blueprints.py:99-102). The reason for duplication is the WSGI/sansio split: serving needs `from .globals import current_app` and `from .helpers import send_from_directory` (`blueprints.py:8-9`), imports the sansio layer must not carry, so the WSGI subclasses re-declare the methods (`blueprints.py:10`, `:18`; `app.py:81 class Flask(App)`) instead of putting them on `Scaffold`.

**Layer 3 — registration fills the abstract primitive with a blueprint-specific hook.** `Flask.register_blueprint` (`sansio/app.py:570`) just delegates: `blueprint.register(self, options)`. `Blueprint.register` (`sansio/blueprints.py:273`) does name bookkeeping, then at 325-330: `if self.has_static_folder:` → `state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")`. That call goes through `BlueprintSetupState.add_url_rule` (`sansio/blueprints.py:34`, `:87`), which prefixes with `url_prefix` (98-102) and dot-prefixes the endpoint (`f"{self.name_prefix}.{self.name}.{endpoint}".lstrip(".")`, 110-116), landing on `app.add_url_rule` (`sansio/app.py:605`) — so `endpoint="static"` becomes `admin.static`. The app's own static route is registered directly with the same primitive, bypassing `BlueprintSetupState`: `if self.has_static_folder:` → weakref lambda → `self.add_url_rule(f"{self.static_url_path}/<path:filename>", endpoint="static", host=static_host, view_func=...)` (`app.py:267-279`), giving the bare endpoint `static`.

**Why caching stays consistent despite the duplication.** Both copies resolve max-age from the same app-level policy key, `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]` (app.py:298, blueprints.py:72), whose default is `None` (`app.py:201`, inside `default_config`). And `send_file` calls made *inside* a blueprint view resolve through `helpers.py:387-389`: `_prepare_send_file_kwargs` sets `kwargs["max_age"] = current_app.get_send_file_max_age` when no max-age is given (docstring at 496-498: "`cache_timeout` defaults to `Flask.get_send_file_max_age`"). A blueprint therefore inherits the host app's cache policy, and route-level caching on the blueprint's own static endpoint comes from its duplicate copy of the same lookup.

**The consistency is policy resolution, not identical behaviour — a nuance the evidence preserves.** A component can override `get_send_file_max_age` and opt out. Executed runtime check confirms both halves: with `SEND_FILE_MAX_AGE_DEFAULT = 3600`, the blueprint static route returns `Cache-Control: public, max-age=3600` and `url_for("admin.static", filename="test.txt") == "/admin/static/test.txt"`; but with a `Blueprint` subclass overriding `get_send_file_max_age` to `100`, the same configured 3600 yields `max-age=100` — component override wins. On the app side, `app.send_static_file` and `flask.send_file` agree in all three regimes (`None` / `3600` / subclass `10`). Note also that `send_file` called inside a blueprint view still resolves through the *app's* bound method (`helpers.py:389`), so the two paths agree only while no override exists.

**Documented contract cross-check.** `docs/blueprints.rst:191-217` states the blueprint static route is served at "the `url_prefix` of the blueprint + `/static`" (e.g. `/admin/static`), the endpoint "is named `blueprint_name.static`", and adds the precedence caveat that with no `url_prefix` the blueprint's `/static` is unreachable because "the application's `/static` route takes precedence." That matches the registration chain above: url_prefix is applied by `BlueprintSetupState` (98-102), while the app's own `endpoint="static"` rule at `/static` is registered independently.
