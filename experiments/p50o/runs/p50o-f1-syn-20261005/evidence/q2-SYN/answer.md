## Purpose of the registration‑tracking flag

The flag is **`Blueprint._got_registered_once`** — a class attribute defaulting to `False` on `Blueprint` at `src/flask/sansio/blueprints.py:172` (the class that collects a blueprint's setup work: `route`, `add_url_rule`, `record`/`record_once`, `before_request`, … ).

Its purpose is a **once‑ever latch: it records that this blueprint object has already been merged into an application, so setup‑time mutation is refused afterwards.** It is set `True` at `:320` inside `Blueprint.register`, immediately after `app.blueprints[name] = self` and *before* the deferred functions run (`for deferred in self.deferred_functions: deferred(state)`), and it is read in exactly one place, `Blueprint._check_setup_finished` (`:213‑221`):

```python
if self._got_registered_once:
    raise AssertionError(
        f"The setup method '{f_name}' can no longer be called on the blueprint"
        f" '{self.name}'. It has already been registered at least once, any"
        " changes will not be applied consistently.\n"
        "Make sure all imports, decorators, functions, etc. needed to set up"
        " the blueprint are done before registering it."
    )
```

That hook is invoked by the `@setupmethod` wrapper (`src/flask/sansio/scaffold.py:42‑50`, `self._check_setup_finished(f_name)` before delegating; base hook raises `NotImplementedError` at `scaffold.py:433`). `@setupmethod` decorates the setup surface inherited from `Scaffold` (`route` `:335`, `add_url_rule` `:367`, `endpoint` `:435`, `before_request` `:459`, `after_request` `:486`, `teardown_request` `:507`, `context_processor` `:541`, `url_value_preprocessor` `:558`, `url_defaults` `:583`, `errorhandler` `:597`, `register_error_handler` `:641`, the method shortcuts `:295‑327`) and 17 sites in `blueprints.py` (`record` `:223`, `record_once` `:232`, `register_blueprint` `:255`, `add_url_rule` `:412`, the `*_app_*` vari‑ants `:443‑624`). So *any* guarded setup call after the first registration raises `AssertionError`, while all pre‑registration setup is unaffected. Because the latch is set before the deferred functions execute, setup from inside a deferred callback is refused too.

**Why the project wants it:** the message states the reason — "any changes will not be applied consistently". Registration is the moment a blueprint's collected setup is replayed against the app (`make_setup_state`, static route, `_merge_blueprint_funcs`, then the deferred loop), and a blueprint may be mounted on more than one app or under more than one name (`first_bp_registration` / `first_name_registration`, `:316‑317`, and the `name=` option documented at `:281‑300`). The per‑instance, per‑object latch is the cheap way to make "you configured this blueprint too late" a hard error rather than silent divergence. Project‑authored rationale is in the changelog, not in a docstring: `CHANGES.rst:297‑300` (2.2.0 — "Use Blueprint decorators and functions intended for setup after registering the blueprint will show a warning. In the next version, this will become an error **just like the application setup methods**", issue 4571) and `CHANGES.rst:160‑161` (2.3.0 — "Calling setup methods on blueprints after registration is an error instead of a warning", PR 4997). The app‑side parallel is the same hook with a different latch: `Flask._got_first_request` (`src/flask/sansio/app.py:404‑422`, commented "tracks internally if the application already handled at least one request"), documented at `docs/lifecycle.rst:43‑47`.

**Scope distinctions that matter:** the latch is *per blueprint object and permanent* — not per app and not per registration name ("already been registered at least once"); the per‑app/per‑name distinctions are carried by `first_bp_registration` / `first_name_registration`, which drive `record_once`'s `state.first_registration` guard and the `_merge_blueprint_funcs` call. It is also not the mechanism behind `record_once`'s once‑semantics — those are implemented inside the deferred wrapper.
