## `ensure_ascii` and Unicode in serialized JSON output

The ASCII-only parameter is a **representation switch, not a character switch**. `DefaultJSONProvider.ensure_ascii` (`src/flask/json/provider.py:144`) defaults to `True`, and in that state every non-ASCII code point in the data is replaced by a `\uXXXX` escape sequence, so the serialized text is pure ASCII. With `False`, the same code point is emitted as the literal character inside the returned `str` — the character, and therefore the value a reader gets back, is identical either way. The attribute's own docstring states exactly this: "Replace non-ASCII characters with escape sequences. This may be more compatible with some clients, but can be disabled for better performance and size" (`src/flask/json/provider.py:145-148`).

The switch reaches Python's `json.dumps` through a default, not a forced argument: `dumps` does `kwargs.setdefault("ensure_ascii", self.ensure_ascii)` before `json.dumps(obj, **kwargs)` (`provider.py:176-179`). Consequences that follow directly:

- A caller-supplied `ensure_ascii=` on `app.json.dumps(...)` overrides the attribute for that call, because `setdefault` leaves an existing key alone.
- The parameter lives only on `DefaultJSONProvider`; the base `JSONProvider` defines no such attribute and its contract only requires `dumps`/`loads`. A custom provider therefore does not inherit the behaviour unless it reimplements it, and nothing in the repo tests that a custom provider honours it.
- It governs the text produced by `dumps`, `dump`, `response` and hence `jsonify` (`provider.py:response`, `src/flask/json/__init__.py`). `flask.json.dumps` **outside** an app context does not consult it — that path falls back to stdlib `json.dumps` and sets only `default`.
- `EnvironBuilder.json_dumps` delegates to `self.app.json.dumps` (`src/flask/testing.py:88-94`), so it inherits the setting; `tests/test_testing.py:110-114` sets `app.json.ensure_ascii = False`, serializes `"\u20ac"`, and asserts the UTF-8-decoded input stream is `'"\u20ac"'` (literal euro sign, not `\u20ac` escaped).

The direct behavioural assertion in the repo is parametrised over exactly the two states: `dumps("\N{SNOWMAN}")` yields `'"\\u2603"'` for `True` and `'"\u2603"'` (literal U+2603) for `False` (`tests/test_json.py:48-54`).

Where the parameter does **not** reach is the byte layer or the decoding layer:

- `DefaultJSONProvider.response` passes only `indent`/`separators` to `dumps` and hands the resulting `str` to the response class, appending `"\n"` (`provider.py:response`). Werkzeug encodes `str` bodies as UTF-8 (`werkzeug/wrappers/response.py:31-37`, `289-298`), so with `ensure_ascii=False` the non-ASCII characters travel as multi-byte UTF-8, and with `True` the body is ASCII (a UTF-8 subset). The serializer never emits bytes itself; `ensure_ascii` chooses escapes versus literal text, not an encoding.
- `application/json` is not in Werkzeug's `_charset_mimetypes` set (`werkzeug/utils.py:160-188`), so the response `Content-Type` carries no `charset` parameter in either state — clients rely on JSON's own UTF-8 default.
- Decoding is independent: `loads` accepts `str` or UTF-8 bytes and applies no `ensure_ascii` logic (`provider.py:loads`); `dump`'s docstring only warns that a text file for output must use UTF-8 to be valid JSON (`provider.py:dump`).
- Jinja's `|tojson` layering is separate: it always rewrites `<`, `>`, `&`, `'` to `\u003c`, `\u003e`, `\u0026`, `\u0027` (`jinja2/utils.py:637-674`), which is why `tests/test_json.py::test_tojson_filter` sees `\u003c/script\u003e` escapes regardless of `ensure_ascii`. Flask wires that filter to the provider's `dumps` (`src/flask/app.py:422`), so `ensure_ascii=False` only makes it *less* escaped, never escape-free in templates.

History/configuration relationship: the parameter was previously the `JSON_AS_ASCII` config key (the justification recorded when it was added was "less bytes being transmitted over the network", `CHANGES.rst:1192-1195`); `JSON_AS_ASCII` was removed in 2.3 in favour of the equivalent `app.json` provider attribute (`CHANGES.rst:153-154`, `CHANGES.rst:286-288`, `docs/config.rst` versionchanged 2.3). Documentation of the attribute exists only through autodoc of `DefaultJSONProvider` (`docs/api.rst:265-267`); no prose chapter mentions Unicode escaping. This matches the attribute's documented trade-off: `True` favours client compatibility, `False` favours size and speed.
