## Dependency chain in `tests/test_testing.py::test_subdomain` (lines 302–318)

The test builds one chain of five inputs and three consumers; each link is a prerequisite of the next, and the runtime effect of each appears only at the link that consumes it.

1. **Construct the app with the flag** — `flask.Flask(__name__, subdomain_matching=True)` (tests/test_testing.py:303). Stored verbatim as `self.subdomain_matching` (src/flask/sansio/app.py:407). Nothing reads it yet; it is consumed only at step 4.
2. **Configure the host** — `app.config["SERVER_NAME"] = "example.com"` (:304). This value is read at two later points, never at assignment time: (a) `EnvironBuilder.__init__` takes `app.config.get("SERVER_NAME") or "localhost"` as the environment host, plus `PREFERRED_URL_SCHEME` and `APPLICATION_ROOT` (src/flask/testing.py:64–80); (b) `create_url_adapter` passes `self.config["SERVER_NAME"]` as `server_name` into `bind_to_environ` (src/flask/app.py:453, 464–466) and requires it on the no-request fallback path (:470–471).
3. **Register the route** — `@app.route("/", subdomain="<company_id>")` on `view` (:307–309). This is what gives `url_for` a rule to build and dispatch a rule to match. The subdomain string becomes a *dynamic* domain part of the rule: `Rule.compile` sets `domain_rule = self.subdomain or ""` and parses it into matcher parts (werkzeug/routing/rules.py:703–706, 602–686), so the domain pattern demands the converter (`[^/]+`) match the request's subdomain. Without this registration, step 5 raises `BuildError`.
4. **Create the request context** — `with app.test_request_context():` (:311) → `Flask.test_request_context` builds a Flask `EnvironBuilder` from the app's config (src/flask/app.py:1474–1481) → `RequestContext.__init__` → `app.create_url_adapter(self.request)` (src/flask/ctx.py:316–323). This is where configuration and the constructor flag converge: with `subdomain_matching=True` and no explicit `subdomain`, Flask passes `subdomain=None` (src/flask/app.py:456–466), so Werkzeug derives the current subdomain by comparing the request host with `SERVER_NAME` (werkzeug/routing/map.py:322–339). The resulting adapter is the object `flask.url_for` uses.
5. **Build the URL** — `flask.url_for("view", company_id="xxx")` (:312) → `current_app.url_for` (src/flask/helpers.py:232–238) → uses `req_ctx.url_adapter` (src/flask/app.py:1059–1064), with `_external` defaulting to `_scheme is not None` = False inside a request (:1071–1074). `adapter.build` skips its internal-URL shortcut because the rule's `domain_part` (`"xxx"`) differs from the adapter's subdomain (`""`, the bare `SERVER_NAME`), so it emits the full `http://xxx.example.com/` (werkzeug/routing/map.py:943–952, host from `get_host`: :707–715). The URL the client will fetch is therefore *derived from config + route registration*, not written literally in the test.
6. **Dispatch the request** — `with client: response = client.get(url)` (:314–315). The builder uses the URL's host (`xxx.example.com`), a fresh `RequestContext` is pushed, and `RequestContext.push`/`match_request` calls `adapter.match(return_rule=True)` (src/flask/ctx.py:357–365, 393–394). On that request the adapter again derives `subdomain="xxx"` from the host — possible only because step 1 left it as `None` rather than forcing a value — and the dynamic-domain rule fills `company_id="xxx"`, which `view` returns.
7. **Assertions close the loop** — `200` and `b"xxx"` (:317–318) simultaneously witness that the rule matched at that subdomain and that the value travelled `url_for` → URL path/subdomain → view argument.

Ordering constraints the chain actually imposes:
- `SERVER_NAME` must precede step 4 and the client's request, but **not** the client object: `FlaskClient.__init__` only sets cookies/environ_base (src/flask/testing.py:127–136) and `open()` constructs the `EnvironBuilder` at call time (:176–196), which is where the config is read.
- Route registration must precede step 5 (rule lookup happens at build time) and step 6.
- The request context must precede `flask.url_for`; outside a request, `app.url_for` needs `SERVER_NAME` to build its own adapter (src/flask/app.py:1075–1090).
- `subdomain_matching=True` is consumed only on the matching/binding side (src/flask/app.py:458–462). Its absence does not change the URL produced in step 5 — building already goes external either way, because `domain_part` ≠ the adapter subdomain in both cases — it changes whether the host `xxx.example.com` is ever turned into a subdomain for the matcher.

Two neighbours in the same file use the same shape and bracket the above: `test_nosubdomain` (:321–334) is the identical chain minus the subdomain, and `test_blueprint_with_subdomain` (:117–138) is the same chain with a blueprint-provided rule and an explicitly passed subdomain (`app.test_request_context("/", subdomain="xxx")`), i.e. it supplies at step 4 what step 4 otherwise derives.
