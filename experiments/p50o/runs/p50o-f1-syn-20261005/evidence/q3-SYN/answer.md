## Modular component registration and static asset serving

The repo has no separate "component registration" subsystem for static assets. What it has is a two-level composition: `Blueprint` is the modular unit (docs call it the way Flask makes "application components"; `docs/blueprints.rst:1-14`), an app registers one with `Flask.register_blueprint` (`src/flask/sansio/app.py:570-590`), which delegates to `Blueprint.register(app, options)` (`src/flask/sansio/blueprints.py:273-340`). Static asset serving is *not* factored out of either class into a registrable component — it is configured on the shared base class and implemented (twice) on the two concrete components, with caching kept consistent through one config key plus a documented duplicate method.

**Registration flow**

- `Flask.register_blueprint` records the blueprint in `app.blueprints` and calls `blueprint.register(self, options)` (`sansio/app.py:570-590`).
- `Blueprint.register` validates the name, sets `_got_registered_once`, builds a `BlueprintSetupState`, and replays every deferred function registered via `record` / `record_once` (`sansio/blueprints.py:273+`, `record`/`record_once` at `:231-252`).
- `BlueprintSetupState.add_url_rule` is the funnel that rewrites a component-local rule into an app rule: it prefixes `url_prefix`, defaults `subdomain`, and dotted-prefixes the endpoint (`sansio/blueprints.py:87-118`). So a component's routes are registered on the application's url map under `blueprint_name.endpoint` (`docs/blueprints.rst:99-106`).

**Static serving is per component, configuration is shared**

- Shared configuration lives in the common base `Scaffold` (`src/flask/sansio/scaffold.py:58-88`): `static_folder` (made absolute against `root_path`, `:224-238`), `static_url_path` (derived from the folder's basename when unset, `:249-267`), and `has_static_folder` (`:241-246`).
- App side: `Flask.__init__` registers `"{static_url_path}/<path:filename}"` with `endpoint="static"` and the view `lambda **kw: self_ref().send_static_file(**kw)` (weakref, to avoid an app↔view reference cycle), only `if self.has_static_folder`, and without checking the folder exists; `host=static_host` is asserted to require `host_matching` (`src/flask/app.py:262-279`).
- Blueprint side: the blueprint registers its own separate static route *at registration time*, not construction time — `if self.has_static_folder: state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")` (`sansio/blueprints.py:323-327`). Endpoint/public URL become `blueprint_name.static` / `url_prefix + /static` (`docs/blueprints.rst:200-210`).
- Coupling point between the two: a blueprint with no `url_prefix` cannot serve its static folder at all, because the app's `/static` route takes precedence and blueprint static folders are not searched as a fallback (`docs/blueprints.rst:212-217`; `sansio/blueprints.py:144-147`). Unlike templates, blueprint static folders are not merged.

**How caching stays consistent across both**

- One config key drives both: `SEND_FILE_MAX_AGE_DEFAULT`, default `None` (`src/flask/app.py:201`), documented as "Override this value on a per-file basis using `~flask.Flask.get_send_file_max_age` on the application or blueprint" (`docs/config.rst:250-256`).
- Both components implement the same resolution logic: `Flask.get_send_file_max_age` (`src/flask/app.py:281-306`) and `Blueprint.get_send_file_max_age` (`src/flask/blueprints.py:55-79`) both read `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]` — from the *app*, not from the blueprint — return `None` when it is `None`, convert a `timedelta` with `total_seconds()`, otherwise return the value. Each carries the in-source note "Note this is a duplicate of the same method in the Flask class."
- Both `send_static_file` implementations (`app.py:308-328`, `blueprints.py:82-102`) resolve the value explicitly and pass it on: the comment reads "send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too", followed by `max_age = self.get_send_file_max_age(filename)` and `send_from_directory(...)`. The app-level default path is `helpers._prepare_send_file_kwargs`, which sets `max_age` to `current_app.get_send_file_max_age` when the caller did not supply one (`src/flask/helpers.py:387-389`).
- Behavior is pinned by tests: changing `SEND_FILE_MAX_AGE_DEFAULT` changes the `Cache-Control: max-age` on a blueprint static response (`tests/test_blueprints.py:195-206`, `/admin/static/css/test.css`); a `Blueprint` subclass overriding `get_send_file_max_age` returns its own value (100) even though the app config says otherwise (`tests/test_blueprints.py:228-244`); and `app.send_static_file` honors the config while a bare `send_file` with no config yields no max-age (`tests/test_helpers.py:53-63`).

**Where the premise does not hold**

The "architecture that separates static asset serving from the main application framework" is, in this repo, neither a module nor an extension/plug-in registry: there is no `register_component`-style API, and static serving is not delegated to a separate registered object. The separation is (a) a route plus a view function per component registered onto the app, and (b) config properties inherited from `Scaffold`. Consistency of caching is achieved by duplicating the hook in `Flask` and `Blueprint` against a single config key — a copy-paste invariant the source itself flags as a duplicate (`app.py:290-291`, `blueprints.py:64-65`), not a single shared implementation. No code path or test enforces that the two copies stay identical.
