## Blueprint registration carries the static route; caching consistency comes from a duplicated method pair reading one shared config key

The modular component is `flask.Blueprint`. Static-asset serving is separated from the main application framework by making the blueprint register its **own** static route during registration, and caching stays consistent because both classes implement the same two methods with byte-identical bodies over a single config key.

**The registration chain.** `src/flask/__init__.py:2-3` exports `Flask` (from `.app`) and `Blueprint` (from `.blueprints`); `src/flask/blueprints.py:18` is `class Blueprint(SansioBlueprint)`, and `src/flask/sansio/blueprints.py:119` is `class Blueprint(Scaffold)`. So the public component is the IO-capable subclass of the sans-IO blueprint, which shares `Scaffold` with the app (`src/flask/sansio/scaffold.py:52`; the docstring names exactly `Flask` and `Blueprint` as its two users). Registration enters at `src/flask/sansio/app.py:570` `def register_blueprint(self, blueprint: Blueprint, **options)`, whose body is the single delegation `blueprint.register(self, options)` (`:595`).

**Where static serving is separated.** The blueprint adds its static route itself, inside `Blueprint.register` (`src/flask/sansio/blueprints.py:273`), at `:323-327`: `if self.has_static_folder:` → `state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")`. The URL prefix comes from the component's own state (`BlueprintSetupState.add_url_rule` joins `self.url_prefix`, `:100-104`) and the endpoint is namespaced to `f"{self.name_prefix}.{self.name}.{endpoint}"` (`:116-122`) — hence `/admin/static/<filename>` with endpoint `admin.static`, confirmed by `tests/test_blueprints.py:210-211` (`url_for("admin.static", filename="test.txt") == "/admin/static/test.txt"`). The app has its own, separate registration of the same pattern, but as an instance-level rule in `Flask.__init__` (`src/flask/app.py:262-279`: same guard, same route string, `endpoint="static"`, weakref'd view), not as a registration-time event. The app-side path additionally accepts `static_host`/`host_matching` (`app.py:267-278`), which the blueprint path does not — the two registration routes are not identical.

**Where caching is kept consistent.** `get_send_file_max_age` and `send_static_file` exist twice, once per component: `src/flask/app.py:281`/`:308` and `src/flask/blueprints.py:55`/`:82`. Both read the same key — `value = current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]` (`app.py:298`, `blueprints.py:72`), with the one default defined at `app.py:201` (`None`) — and both convert a `timedelta` via `int(value.total_seconds())` (`app.py:303-304`, `blueprints.py:77-78`). Both `send_static_file` bodies pass `max_age=self.get_send_file_max_age(filename)` explicitly into `send_from_directory` (`app.py:325-326`, `blueprints.py:99-100`), with the same comment on both sides (`app.py:323-324`, `blueprints.py:97-98`): *"send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too."* This is the mechanism that preserves consistency: the generic fallback in `_prepare_send_file_kwargs` (`src/flask/helpers.py:387-389`) substitutes `current_app.get_send_file_max_age`, which would ignore a blueprint's own method, so the explicit `max_age=` forward is what makes the blueprint's override authoritative. The static-folder/url-path state both use (`_static_folder`/`_static_url_path` at `sansio/scaffold.py:72-73`, `has_static_folder` at `:241-246`, `static_url_path` deriving `/basename` at `:258-260`) comes from the shared `Scaffold`. Both docstrings state plainly that each method "is a duplicate of the same method in the Flask class" — consistency here is duplication plus one shared config value, not one shared implementation.

**Executed confirmation.** `pytest tests/test_blueprints.py::test_templates_and_static tests/test_blueprints.py::test_default_static_max_age tests/test_helpers.py::TestSendfile::test_static_file -v` → **3 passed** (exit 0). Direct header observation under a single config, with the app `/static` route and a blueprint `/admin/static` route live in one app: config `None` → both `no-cache`/`None`; `3600` → both `public, max-age=3600`/3600; `timedelta(seconds=7200)` → both `7200`; with `3600` configured and per-component overrides, app → `max-age=10`, blueprint → `max-age=100`. On the real `blueprintapp`, `/admin/static/test.txt` and `/admin/static/css/test.css` moved from `no-cache` to `public, max-age=3600` when `SEND_FILE_MAX_AGE_DEFAULT` was set (both 200).

**Answered vs. open.** Answered: which component is registered, the two registration paths, and the exact mechanism (duplicated methods + single config key + explicit `max_age=` forward) that makes both components report the same cache header while each still honors its own override. Open: (a) `send_static_file` is *referenced* from `sansio/blueprints.py:326` under `# type: ignore[attr-defined]` because the sans-IO `Blueprint` does not define it — it is defined only on the IO subclass at `src/flask/blueprints.py:82`, so citations must span both files; (b) the observed header run is a synthetic app plus the existing `blueprintapp`, not a full-suite run, and `/static/index.html` on `blueprintapp` 404s because that app has no app-level static folder, so the app-side values come from the synthetic app; (c) nothing about werkzeug's internals was verified; (d) `flask_mut2_i417ar2x/mutated_test.py` was not opened and no source file was modified; (e) the sans-IO/IO layering as an alternative reading of "separation" was not investigated (`src/flask/sansio/README.md` unread).
