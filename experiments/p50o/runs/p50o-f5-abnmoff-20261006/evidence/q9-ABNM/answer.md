## Architectural decisions reflected by the dual inheritance

**1. The validation/encoding boundary is collapsed at the type level, on purpose — the separation is not implemented in the exception taxonomy.**
`UnexpectedUnicodeError(AssertionError, UnicodeError)` makes one type simultaneously a developer-failure type and a text/bytes-conversion type. That is verified, not inferred: the executor ran the class from this worktree (`PYTHONPATH=src`, exit 0) and got MRO `UnexpectedUnicodeError → AssertionError → UnicodeError → ValueError → Exception → BaseException → object`, with `issubclass`/`isinstance` `True` against *both* bases, and an instance caught by both `except AssertionError:` and `except UnicodeError:`. So Flask does not ask a caller to decide whether "unexpected unicode or binary data" is a *validation failure* (assertion-style) or an *encoding issue* (UnicodeError-style): both nets catch the same object. Catching is a union, not a partition. (In a caller that writes both clauses, only the first-listed wins — plain clause-order semantics, not a property of the class.)

**2. The separation this design *does* enforce is a layering one, and the class sits on the debug side of it.**
`src/flask/debughelpers.py` is top-level `flask`; it is not in `src/flask/sansio/`, its imports run `from .sansio.app import App` and `from .globals import request_ctx` (plus Jinja/Werkzeug), and no `sansio/` module imports it — the four `debughelpers` import sites are `wrappers.py:208`, `templating.py:83`, `app.py:502`, `tests/test_basic.py:1108`, all outside `sansio/`. The dependency arrow points `debughelpers → sansio`. `sansio/README.md` states that folder "cannot do any IO… cannot use the Flask globals", which `debughelpers.py` violates (globals use at line 139; request/routing objects at `DebugFilesKeyError.__init__`, `debughelpers.py:57-59`). Reading: the *framework-neutral core* owns setup/context invariants and raises bare `AssertionError` for them (`sansio/app.py:415,657`, `sansio/blueprints.py:215`, `ctx.py:268,429`); the *debug-facing layer above it* owns "better error reporting" (the class docstring's own words) and is where the assertion/encoding type mixing is allowed to exist. So the design decision reflected is: taxonomy blurring is acceptable in the reporting layer, not in the core.

**3. `AssertionError` as co-base is this module's tag for "developer error", not a framework dispatch hook.**
The sibling idiom in the same file — `DebugFilesKeyError(KeyError, AssertionError)` (line 23) and `FormDataRoutingRedirect(AssertionError)` (line 50) — shows `AssertionError` being mixed with the type that a *natural* failure would have (`KeyError`, `UnicodeError`) so the debug exception remains catchable as the natural error while also reading as a programming error. `UnexpectedUnicodeError` follows that same recipe; the base order in source (assertion first) is recorded identity ordering only — neither base defines methods that would conflict, and both catches succeed regardless.

**4. Insofar as "debug-mode" applies, it is a gate on the surrounding helpers, not on this class.**
The debug helpers are entered conditionally: `wrappers.py:195-210` (`if current_app and current_app.debug …: from .debughelpers import attach_enctype_error_multidict`) and `app.py:492-504` (`if not self.debug …: raise request.routing_exception`, else `raise FormDataRoutingRedirect(request)`). `UnexpectedUnicodeError` participates in none of this — it is never raised.

**5. Contradiction to flag: the framework's error handling does *not* key on assertion-style errors, so the dual inheritance buys no dispatch behavior.**
`except AssertionError` occurs nowhere in `src/flask/`. `handle_user_exception` (`app.py:779-804`) branches on `BadRequestKeyError` (only to set `show_exception` when `self.debug or TRAP_BAD_REQUEST_ERRORS`), `HTTPException` + `trap_http_exception`, then `_find_error_handler`. `handle_exception` (`app.py:841-848`) propagates purely by configuration: `propagate = self.config["PROPAGATE_EXCEPTIONS"]; if propagate is None: propagate = self.testing or self.debug` — type-agnostic. Any earlier framing that debug/test handling "keys on assertion-style errors and `app.testing` propagation picks it up without special-casing" is half-supported: the `testing`/`debug` propagation is real and observed, the assertion-type keying is not. The observed truth is narrower: `AssertionError` is a *raise-site convention* in this repo (`sansio/app.py:415,657`, `sansio/blueprints.py:215`, `ctx.py:268,429`), never a *catch/dispatch* key. The dual inheritance therefore constitutes a caller-side catchability contract (both a developer-error net and a decoding-error net can handle it), not an internal routing decision.

**6. What cannot be attributed to this design:** any recorded intent, or any live behavior. `UnexpectedUnicodeError` has exactly one worktree-wide occurrence — its definition at `src/flask/debughelpers.py:17`; the string `UnicodeError` likewise appears once in the entire worktree; there is no `raise`, no `except UnicodeError`/`UnicodeDecodeError` in `src/` or `tests/`. `CHANGES.rst` and `docs/` contain no mention of `debughelpers`, `UnexpectedUnicode`, or a unicode-error design rationale (their only "unicode" hits, lines 679 and 826, are unrelated). The class is also unexported (no `__all__`, no `__init__`), though the public-adjacent module path means Python callers could catch it. So the decisions above are read from the artifact, its placement, and the module's idiom — not from any stated or exercised behavior.
