## Modular component registration architecture: separate static serving, shared caching

The separation is real but *partial*, and it works in three layers: a shared abstract base, two independent concrete registration sites, and a single app-level config value that both components read.

**1. Shared base — `Scaffold` (`src/flask/sansio/scaffold.py:52`).** Its docstring is "Common behavior shared between :class:`~flask.Flask` and :class:`~flask.blueprints.Blueprint`." Both static *metadata* properties live here, not on either component: `static_folder` (`:224`), `has_static_folder` (`:241`), `static_url_path` (`:249`, derived from `os.path.basename(self.static_folder)` when unconfigured). The registration *primitive* is an abstract contract on the same base — `@setupmethod def add_url_rule(...)` (`:368`) whose body is `raise NotImplementedError` (`:433`). So `Scaffold` does not serve static files at all; it defines the hook and the properties each component implements. Ancestry: `class Flask(App)` → `class App(Scaffold)` (`sansio/app.py:59`); `class Blueprint(SansioBlueprint)` → `class Blueprint(Scaffold)` (`sansio/blueprints.py`), and `CHANGES.rst:100-101` records the change ("Restructure the code such that the Flask (app) and Blueprint classes have Sans-IO bases", 3.0.0).

**2. Two registration sites, one per component, at different lifecycle moments.**
- **App, at construction** — `src/flask/app.py:267-279`, inside `Flask.__init__`: `if self.has_static_folder:` → `self.add_url_rule(f"{self.static_url_path}/<path:filename>", endpoint="static", host=static_host, view_func=lambda **kw: self_ref().send_static_file(**kw))`, preceded by the weakref comment ("Use a weakref to avoid creating a reference cycle between the app and the view function (see #3761)"). `App.__init__` (`sansio/app.py:282-303`) registers nothing static — the app-side registration is concrete-`Flask`-only.
- **Blueprint, at registration** — `src/flask/sansio/blueprints.py:323-328`, inside `Blueprint.register`: `if self.has_static_folder:` → `state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")`. `BlueprintSetupState.add_url_rule` (`:87`) rewrites the rule with `url_prefix` and namespaces the endpoint (`f"{name_prefix}.{name}.{endpoint}"`) before calling the app's `add_url_rule`. This is why the path is deferred and why the endpoint surfaces as `admin.static`.

Observed asymmetry between the sites: the app route passes `host=static_host` and a weakref lambda; the blueprint route has no host option and passes the bound method `self.send_static_file`. Both are confirmed by the runtime probe: the `url_map` exposes exactly `['static', 'bp.static']` with rules `['/static/<path:filename>', '/bp/static/<path:filename>']`.

**3. Caching consistency comes from duplicated methods reading one config key, not from shared code.** Each component carries its own full copy of the caching logic — app side `get_send_file_max_age` (`app.py:281`) and `send_static_file` (`app.py:308`) in `class Flask`; blueprint side the same pair at `blueprints.py:55` and `blueprints.py:82` in `class Blueprint`. Both read the identical single source: `value = current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]` (`app.py:298`, `blueprints.py:72`), followed by identical `None → None` / `timedelta → int(total_seconds())` normalization (`app.py:300-306`, `blueprints.py:74-78`). There is no blueprint-local config to diverge: `Config` is created only on the app (`sansio/app.py:318`), `default_config` is a `Flask` class attribute (`app.py:178`), and a constructed `Blueprint("x", __name__)` has no `config` attribute (probe: `has .config attr: False`). The default is `"SEND_FILE_MAX_AGE_DEFAULT": None` (`app.py:201`, documented `docs/config.rst:250-259`). Both static views pre-resolve the value and pass it explicitly into `send_from_directory` — `max_age = self.get_send_file_max_age(filename)` (`app.py:325`, `blueprints.py:99`), with the in-source note "send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too." The `helpers._prepare_send_file_kwargs` fallback (`helpers.py:387-389`, `if kwargs.get("max_age") is None: kwargs["max_age"] = current_app.get_send_file_max_age`) is therefore *not* the consistency mechanism for static files — both static views already pass an explicit `max_age`; the fallback covers bare `send_file` / `send_from_directory` calls from user views. The operative mechanism is: two parallel implementations, one shared key, `current_app` as single source of truth.

Consistency is the **default, not an invariant**. `tests/test_blueprints.py:223` `test_default_static_max_age` subclasses `Blueprint` with `get_send_file_max_age -> 100`, sets a deliberately different `app.config["SEND_FILE_MAX_AGE_DEFAULT"]`, and asserts `cc.max_age == 100` — the per-blueprint override wins. Symmetrically, `tests/test_helpers.py::TestSendfile::test_static_file` (class at `test_helpers.py:33`; the bare node id in the plan did not exist, `EXIT=4`) shows an app subclass override (`-> 10`) winning on both the static handler and direct `send_file`.

Behavioral evidence for the shared-config link: `tests/test_blueprints.py:176` `test_templates_and_static` serves blueprint static over HTTP (`/admin/static/test.txt` → `b"Admin File"`, `/admin/static/css/test.css` → `b"/* nested file */"`), then sets `app.config["SEND_FILE_MAX_AGE_DEFAULT"] = 3600` and asserts `cc.max_age == 3600` on the blueprint's response — an *app* config value driving a *blueprint* static max-age. The independent live probe (not a re-run of the cited tests) confirms parity across value types: `default(None)` → `no-cache` on both; `int 3600` → `public, max-age=3600` on both; `timedelta 5min` → `public, max-age=300` on both; subclass override `100` → `max-age=100` on both while app config was `3600`.

**Data-backed status:** the three cited tests pass on this worktree's source with `PYTHONPATH=$PWD/src` (3 passed in 0.22s), and the two neighbouring files pass together (94 passed in 0.58s). The venv's editable install points at a different checkout path, so unpinned runs import another tree; `diff -rq` showed the trees byte-identical at the time of the run, so unpinned results were equivalent — a snapshot, not a guarantee.

**The one documented divergence between the two static endpoints is path precedence, not caching** (`docs/blueprints.rst:191-217`): a blueprint's static URL is `/admin/static`, its endpoint `blueprint_name.static`, and without a `url_prefix` the blueprint's `/static` is shadowed by the app's route — "Unlike template folders, blueprint static folders are not searched if the file does not exist in the application static folder." Precedence *at runtime* was not exercised.
