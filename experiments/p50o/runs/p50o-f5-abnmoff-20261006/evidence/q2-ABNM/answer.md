## Purpose of `Blueprint._got_registered_once`

The flag is the one-shot-setup latch for a blueprint. Its purpose is to turn a silent, partially-applied configuration mistake into an immediate hard error: once a blueprint has been registered on an app at least once, its queued setup functions have already been consumed, so any further setup call could not reach the apps that already registered it — or would reach only apps that register it later — producing a differently configured blueprint per app. The flag records "this blueprint's setup phase is over" and every setup surface refuses to run afterwards.

Mechanically, the flag is declared as a class attribute defaulting to `False` (`src/flask/sansio/blueprints.py:172`), checked by `Blueprint._check_setup_finished` (`:213-222`), and is set inside `Blueprint.register` at `:320` — immediately after the blueprint is recorded in `app.blueprints[name]` (`:319`) and immediately **before** the queued callbacks are replayed (`for deferred in self.deferred_functions: deferred(state)`, `:334-335`). Setting it before the replay is what leaves the registration machinery itself free to run while closing the door on user setup calls. The check is wired in through the `@setupmethod` decorator (`src/flask/sansio/scaffold.py:42-50`), which calls `self._check_setup_finished(f_name)` before every decorated body; `Scaffold._check_setup_finished` is abstract (`scaffold.py:220-221`), so the blueprint override is the one that fires. Because `register()` replays the queue on *every* registration (`:334-335`), and only `record_once` callbacks are gated on `state.first_registration` (`:232-243`), the invariant "configure once, register many times" is exactly what the flag protects.

The error message states the rationale verbatim (`blueprints.py:216-220`): *"The setup method '{f_name}' can no longer be called on the blueprint '{self.name}'. It has already been registered at least once, any changes will not be applied consistently. Make sure all imports, decorators, functions, etc. needed to set up the blueprint are done before registering it."* The executor reproduced this text at runtime for `route`, `add_url_rule`, `record`, and `before_request` when called after registration, while the same `@bp.route("/early")` before `register_blueprint` raised nothing and put `/early` into `app.url_map`.

The history confirms the intent was to make an existing warning strict: `CHANGES.rst:297-300` (2.2) says setup-after-registration "will show a warning. In the next version, this will become an error just like the application setup methods", and `CHANGES.rst:160-161` (2.3) records "Calling setup methods on blueprints after registration is an error instead of a warning."

**What it is not.** It is not a duplicate-registration guard: the same blueprint may deliberately be registered multiple times, which is why `BlueprintSetupState.first_registration` exists (`blueprints.py:46, 57-62, 246-253`) and why the message says "at least once" rather than "already registered". It is also not the app-level analogue `Flask._got_first_request` (`src/flask/sansio/app.py:411`), which keys on the app having handled a first *request*, not on a blueprint having been registered.
