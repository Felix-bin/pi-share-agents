## The dependency chain

Both copies of this test — `tests/test_testing.py::test_subdomain` (lines 302–319) and its mutant `flask_mut2_i417ar2x/mutated_test.py` (only difference: `subdomain_matching=False` on line 3 instead of `True`) — run the same five-stage chain. Nothing is mocked, so every stage is a real call into Flask/Werkzeug source.

**1. Configuration** (test lines 3–4 / 303–304)
- `flask.Flask(__name__, subdomain_matching=...)` → `Flask.__init__` (`src/flask/app.py:226`, param at `:233`) → `SansioApp.__init__` (`src/flask/sansio/app.py:289`) → `self.subdomain_matching = subdomain_matching` (`sansio/app.py:407`).
- `app.config["SERVER_NAME"] = "example.com"` is the second config input; it is read later at `app.py:451` (`create_url_adapter`) and at `src/flask/testing.py:66` (test `EnvironBuilder`).
- `self.subdomain_matching` has exactly one consumer in the whole source: `Flask.create_url_adapter` (`app.py:458`). Everything downstream hangs off that single read.

**2. Route registration** (line 7 / 307)
`@app.route("/", subdomain="<company_id>")` → `Scaffold.route` (`sansio/scaffold.py:336`) → `Flask.add_url_rule` (`app.py:605`) → `self.url_rule_class(rule, methods=methods, **options)` with `subdomain="<company_id>"` (`app.py:650`) → `self.url_map.add(rule_obj)` (`app.py:653`). The endpoint is the view function name `"view"`, which is what `url_for` later resolves. Note this stage never consults `subdomain_matching`: the rule carries a subdomain regardless of the flag.

**3. Request context creation and the first `create_url_adapter` pass** (lines 11–12 / 312–313)
- `app.test_request_context()` (`app.py:1423`) → `flask.testing.EnvironBuilder(self)` (`testing.py:27/49`), which with no `base_url` builds one from `SERVER_NAME` → environ host `example.com` (`testing.py:66–81`) → `builder.get_environ()` → `self.request_context(environ)` (`app.py:1475`) → `RequestContext.__init__` (`ctx.py:309`).
- `RequestContext.__init__` creates the request (`ctx.py:318`) and calls `app.create_url_adapter(self.request)` (`ctx.py:323`). Inside `create_url_adapter`: `server_name = self.config["SERVER_NAME"]` (`app.py:451`); then, because `subdomain_matching` is `False` in the mutant, `subdomain = self.url_map.default_subdomain or ""` i.e. `""` (`app.py:458–462`); then `self.url_map.bind_to_environ(environ, server_name=..., subdomain=...)` (`app.py:464`). With `subdomain_matching=True` the `subdomain` argument stays `None` and Werkzeug derives it itself by comparing the environ host with `SERVER_NAME` (`.venv/.../werkzeug/routing/map.py:308–345`); for `example.com` vs `example.com` that derivation also yields `""`. So both variants end up with a `MapAdapter` whose `subdomain` is `""`.
- `with ctx` → `RequestContext.push` (`ctx.py:367`), which also pushes an `AppContext` whose own adapter comes from `create_url_adapter(None)` (`ctx.py:247`), and ends with `self.match_request()` (`ctx.py:394`) — that match of `PATH_INFO "/"` against the subdomain rule is not asserted here.

**4. URL building** (line 12 / 313)
`flask.url_for("view", company_id="xxx")` (`src/flask/helpers.py:188`) → `current_app.url_for(...)` (`app.py:1003`) → `req_ctx` is not `None`, so `url_adapter = req_ctx.url_adapter` (`app.py:1060–1061`) and `_external` is set to `False` (`app.py:1075`, since `_scheme is None`) → `url_adapter.build(...)` (`app.py:1110–1115`) → `_partial_build` substitutes the rule subdomain → `domain_part = "xxx"` (`map.py:808–826`) → the internal-URL shortcut at `map.py:943–947` fails (`"xxx" != ""` in both variants), so the external form is built: `get_host("xxx")` → `"xxx.example.com"` (`map.py:696–715`) → result **`http://xxx.example.com/`**. This stage is identical with and without `subdomain_matching` — the flag does not change `url_for`'s output here.

**5. Client request, second `create_url_adapter` pass, and routing** (lines 15–16 / 315–316)
`with client:` → `FlaskClient.__enter__` (`testing.py:249`) → `client.get(url)` → `FlaskClient.open` (`testing.py:204`) → `EnvironBuilder` with `base_url="http://xxx.example.com/"`, i.e. environ host `xxx.example.com` → `super().open` → `Flask.wsgi_app` (`app.py:1479`) → `ctx = self.request_context(environ)` (`app.py:1506`) → `RequestContext.__init__` → `create_url_adapter(request)` again (`ctx.py:323`). **This is where the configuration flag finally bites**: with `subdomain_matching=True`, `bind_to_environ` derives `subdomain = "xxx"` from the host; with `False`, Flask forces `subdomain = ""` (`app.py:458–462`). Then `ctx.push()` (`app.py:1510`) → `match_request()` (`ctx.py:394`) → `self.url_adapter.match(return_rule=True)` (`ctx.py:362`) → route `/` with `subdomain="<company_id>"` either matches (setting `request.url_rule`/`view_args`) or raises `NotFound` and is stored as `request.routing_exception` (`ctx.py:364–365`). `full_dispatch_request` → `dispatch_request` (`app.py:879`) → `raise_routing_exception` for 404 (`app.py:889–890`), or `self.view_functions["view"](**view_args)` (`app.py:902`) returning `"xxx"`.

**Assertions** (lines 20–21 / 318–319) therefore depend on the last link only: `200` and `b"xxx"` are reachable only if `subdomain="xxx"` reached `MapAdapter.match`. The chain is `subdomain_matching` (constructor) → `self.subdomain_matching` (`sansio/app.py:407`) → `create_url_adapter` (`app.py:458–462`) → `bind_to_environ(subdomain=...)` (`app.py:464`) → adapter subdomain → `match_request` (`ctx.py:362`) → `dispatch_request` (`app.py:902`). Configuration (`SERVER_NAME`) and route registration feed the chain but are flag-independent; the request context is created twice, and only the second (`ctx.py:323`, inside `wsgi_app`) is flag-sensitive.
