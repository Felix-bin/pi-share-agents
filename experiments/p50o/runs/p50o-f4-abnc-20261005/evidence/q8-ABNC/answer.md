## Modular registration + static serving: how the two are kept separate and how caching stays consistent

The split is a **two-layer one**: a sans-IO core (`src/flask/sansio/`) that only records *what* is registered, and a WSGI layer (`src/flask/app.py`, `src/flask/blueprints.py`, `src/flask/helpers.py`) that is the only place static bytes are actually served.

**1. The shared base and the two components.** `Scaffold` (sansio/scaffold.py:52) is the common base for both the application and the modular component. It owns static configuration only — `_static_folder`/`_static_url_path` class attributes (72–73), `static_folder` property resolving relative to `root_path` (224–238), `static_url_path` defaulting to `"/" + basename(static_folder)` (249–269), `has_static_folder` (241–246) — plus the registration API (`route`/`get`/`post`/`errorhandler`/`register_error_handler`/…) guarded by `setupmethod` + `_check_setup_finished` (42–49, 220–221, 433 `add_url_rule` stub raising `NotImplementedError`). On top of it sit `App` (sansio/app.py:59), which holds the routing map, the `blueprints` registry and `register_blueprint` (sansio/app.py:570–597 — it merely calls `blueprint.register(self, options)`), and `Blueprint` (sansio/blueprints.py:119) with its `BlueprintSetupState` (34), deferred callbacks `record`/`record_once` (224–244), `make_setup_state` (246–253) and `register` (273). The concrete classes `Flask(App)` (flask/app.py:81) and `Blueprint(SansioBlueprint)` (flask/blueprints.py:18) add the I/O side.

**2. Where each static route is registered.** For the app, `Flask.__init__` registers `f"{self.static_url_path}/<path:filename>"` with endpoint `"static"`, `host=static_host`, guarded by `assert bool(static_host) == host_matching`, using a `weakref`-wrapped view function to avoid the app↔view reference cycle (flask/app.py:267–279, see comment citing #3761). For the component, registration is *deferred into the app*: `Blueprint.register` (sansio/blueprints.py:323–328) does `state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")`, and `BlueprintSetupState.add_url_rule` (87–115) applies `url_prefix` and namespaces the endpoint as `f"{name_prefix}.{name}.{endpoint}"` — i.e. `admin.static`, reachable via `url_for("admin.static", filename=...)` (tests/test_blueprints.py:208–212). The `# type: ignore[attr-defined]` on `self.send_static_file` at sansio/blueprints.py:326 is the marker of the design: the sans-IO `Blueprint` deliberately does **not** define the view, so nothing in the core layer can serve a file.

**3. What stays in the core and what does not.** Grepping the whole package, `src/flask/sansio/` contains no `send_from_directory`, no `send_static_file`, no `get_send_file_max_age`, and no `SEND_FILE_MAX_AGE_DEFAULT`; its only static references are the configuration properties in `scaffold.py:224–269` and the route record in `blueprints.py:323`. `sansio/README.md` states the constraint directly: the folder holds "code that can be used by alternative Flask implementations … cannot do any IO, nor be part of a likely IO path … cannot use the Flask globals." Static *serving* therefore lives entirely outside the framework core.

**4. Preserving consistent caching across both components.** Serving is one shared implementation, `flask.helpers.send_from_directory` (helpers.py:526–567) → `werkzeug.utils.send_from_directory`/`send_file`, parameterised by `current_app` (`use_x_sendfile`, `response_class`, `_root_path` in `_prepare_send_file_kwargs`, helpers.py:387–397). The cache hook is implemented **twice, identically**: `Flask.get_send_file_max_age` (flask/app.py:281–306) and `Blueprint.get_send_file_max_age` (flask/blueprints.py:55–80) both read `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]`, return `None` when it is `None`, and convert a `timedelta` to seconds; both docstrings say "Note this is a duplicate of the same method in the Flask class", and the default is `None` (flask/app.py:201) meaning conditional requests rather than a timed cache. The two view functions are the same three steps — RuntimeError if `has_static_folder` is false, `max_age = self.get_send_file_max_age(filename)`, then `send_from_directory(self.static_folder, filename, max_age=max_age)` (flask/app.py:308–328; flask/blueprints.py:82–102). Pre-resolving `max_age` is deliberate, and the reason is spelled out in both files: "send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too" (flask/app.py:323–324, flask/blueprints.py:97–98) — otherwise `_prepare_send_file_kwargs` (helpers.py:388–389) would bind `current_app.get_send_file_max_age` and the blueprint's own hook would be ignored. The behaviour is asserted in the repository's tests: blueprint static files honour `SEND_FILE_MAX_AGE_DEFAULT` in `Cache-Control` (tests/test_blueprints.py:194–206), a `Blueprint` subclass overriding `get_send_file_max_age` to `100` wins over a configured `3600`/`7200` (tests/test_blueprints.py:222–244), and `app.send_static_file` and bare `flask.send_file` agree both before and after changing the config (tests/test_helpers.py:44–72).

One observed asymmetry worth stating, because it qualifies the "separation" claim precisely: static *serving* is uniformly absent from the core, but static *route registration* is not — the blueprint registers its route inside sans-IO `Blueprint.register` (sansio/blueprints.py:323) precisely because that view must be supplied by the subclass, whereas the app registers its route in the concrete `Flask.__init__` (flask/app.py:267). Also, `Scaffold` declares no abstract `send_static_file`/`get_send_file_max_age`; consistency is maintained by identical duplication on the two concrete classes, not by a shared declaration.
