## Modular component registration for static assets, with shared caching

The static-serving concern is not one component but a stack of three separable layers, and caching is kept identical across the app and the modular component (blueprint) by a deliberately duplicated hook rather than by inheritance.

**1. One shared description of a static asset (`Scaffold`).** `sansio/scaffold.py:52` defines `Scaffold`, the base of both the app and the blueprint. It owns the static configuration: `static_folder` (`:224`) resolves the configured folder against `self.root_path` and its setter normalises via `os.fspath(...).rstrip(r"\/")` (`:233`); `static_url_path` (`:249`) falls back to `"/" + basename(static_folder)` when not configured, so "the rightmost part of the path is where it is exposed" (`docs/blueprints.rst:200`); `has_static_folder` (`:241`) is the gate used by every layer above. This layer carries no IO and no Flask globals — `sansio/README.md` states the folder must contain "code that can be used by alternative Flask implementations, for example Quart… cannot do any IO, nor be part of a likely IO path… cannot use the Flask globals."

**2. Registration is split between the framework and the component.** `sansio/app.py:285-298` `App(Scaffold)` only accepts and stores `static_url_path`/`static_folder` — the sansio app registers no route. The framework registers its own static route eagerly in the WSGI subclass, `Flask.__init__` (`flask/app.py:262-279`): `add_url_rule(f"{self.static_url_path}/<path:filename>", endpoint="static", host=static_host, view_func=lambda **kw: self_ref().send_static_file(**kw))`, using a `weakref` "to avoid creating a reference cycle between the app and the view function (see #3761)", and deliberately without checking that the folder exists. The component instead records its static route as a deferred registration step in the sansio blueprint: `Blueprint.register()` (`sansio/blueprints.py:273`) ends its setup with `if self.has_static_folder: state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")` (`:323-328`). `BlueprintSetupState.add_url_rule` (`:87-114`) then prefixes the rule with `url_prefix` and the endpoint with the blueprint name (`f"{name_prefix}.{name}.{endpoint}"`) when it reaches `app.add_url_rule`. So a blueprint carries its own static folder to whichever app registers it, `register_blueprint` is the only thing that materialises the route, and the same blueprint can be registered under different names (`tests/test_apps/blueprintapp/apps/admin/__init__.py` + `tests/test_apps/blueprintapp/__init__.py` show the working pattern, served at `/admin/static/test.txt` per `tests/test_blueprints.py:184-186`).

**3. Serving is separated from both.** The view functions are thin: `Flask.send_static_file` (`flask/app.py:308`) and `Blueprint.send_static_file` (`flask/blueprints.py:82`) are near-identical bodies — raise `RuntimeError("'static_folder' must be set to serve static_files.")` if `not self.has_static_folder`, resolve `max_age = self.get_send_file_max_age(filename)`, then `return send_from_directory(t.cast(str, self.static_folder), filename, max_age=max_age)`. The actual file handling is not in the framework class at all but in module-level helpers, `send_file`/`send_from_directory` (`flask/helpers.py:526`, `:565`), which are wrappers over `werkzeug.utils` and inject Flask-specific context (`environ`, `use_x_sendfile`, `response_class`, `_root_path`) in `_prepare_send_file_kwargs` (`:387-399`). Notably the sansio layer can only *name* the view it registers — the call at `sansio/blueprints.py:326` carries `# type: ignore[attr-defined]` because `send_static_file` exists only on the IO-layer subclass.

**4. Caching parity across the two components.** `get_send_file_max_age(filename)` is implemented separately on both `Flask` (`flask/app.py:281`) and `Blueprint` (`flask/blueprints.py:55`). Both bodies are identical: read `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]`, return `None` if unset, convert a `timedelta` via `int(value.total_seconds())`, otherwise return the value; and both docstrings declare the duplication explicitly ("Note this is a duplicate of the same method in the … class", plus `versionchanged:: 2.0` — None instead of 12 hours). The reason is stated inline in both `send_static_file` implementations: "send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too." The second half of the mechanism is the helpers fallback: `_prepare_send_file_kwargs` sets `kwargs["max_age"] = current_app.get_send_file_max_age` whenever `max_age is None` (`flask/helpers.py:388-389`). Consequence, following the code paths: a blueprint override that returns a value is authoritative (`tests/test_blueprints.py:223-244` `test_default_static_max_age` asserts `cc.max_age == 100` for a blueprint subclass even while the app config is 3600/7200), whereas a blueprint hook that returns `None` defers to the app's method — so an app-level subclass override propagates to blueprint-served assets too when the config is unset, which is what keeps the two components' default behaviour indistinguishable. The documented contract matches: `docs/config.rst:250-262` says to "Override this value on a per-file basis using `Flask.get_send_file_max_age` on the application or blueprint", and `CHANGES.rst:1291-1300` records the hook being added to both `Flask` and `Blueprint` together with `SEND_FILE_MAX_AGE_DEFAULT`. The parity is pinned by tests read here (not run by me): `tests/test_helpers.py::TestSendfile::test_static_file` asserts `app.send_static_file` and `flask.send_file` agree at default `None`, at 3600, with a `pathlib`-like path, and with an app subclass returning 10; `tests/test_blueprints.py::test_templates_and_static` asserts a blueprint's static route honours the config value.
