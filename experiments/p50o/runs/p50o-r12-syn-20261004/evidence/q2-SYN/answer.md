## Answer

`Blueprint._got_registered_once` is a **one-way latch that records "this blueprint has already been registered on an application at least once"**, and its purpose is to convert a class of *silent* setup-ordering mistakes into a loud failure. The reason it must be a latch rather than a per-app check is the shape of `Blueprint.register`: registration is not idempotent bookkeeping — it immediately (a) merges the blueprint's hooks/routes/error handlers into that app (`self._merge_blueprint_funcs(app, name)`, `src/flask/sansio/blueprints.py:332`) and (b) replays every recorded setup callback into that app (`for deferred in self.deferred_functions: deferred(state)`, `:334-335`). So a setup call made *after* that point (`@bp.route`, `bp.record(...)`, `@bp.before_app_request`, `bp.register_blueprint(child)`, …) can no longer reach the app the blueprint was already registered with; it would only ever be applied on some *later* registration, leaving two apps (or two workers) holding versions of the same blueprint that disagree with each other and with the blueprint object itself. The flag turns exactly that into `AssertionError`:

> "The setup method '{f_name}' can no longer be called on the blueprint '{name}'. It has already been registered at least once, any changes will not be applied consistently. Make sure all imports, decorators, functions, etc. needed to set up the blueprint are done before registering it." (`:215-220`)

Mechanism: every setup method is wrapped by `setupmethod` (`src/flask/sansio/scaffold.py:42-49`), whose wrapper calls `self._check_setup_finished(f_name)` before the body; `Scaffold._check_setup_finished` is an abstract stub (`scaffold.py:220-221`) overridden separately by `Blueprint` (`:213-221`, checking the blueprint flag) and by `Flask` (`src/flask/sansio/app.py:413-421`, checking `_got_first_request`). The flag itself is declared as a class-attribute default `False` (`blueprints.py:172`) and set to `True` inside `register()` at `:320` — immediately after `app.blueprints[name] = self` and *before* the replay loop — and it is never set back to `False` anywhere in `src/flask` (grep for `_got_registered_once` returns only `:172`, `:214`, `:320`).

The app-side analogue is deliberately similar but *not* identical: Flask's `_got_first_request` (per-app, "has handled its first request") **is** reset — declared `False` in `Flask.__init__` (`sansio/app.py:411`), set `True` in `full_dispatch_request` (`src/flask/app.py:911`), and reset to `False` in `run()`'s `finally` so an interactive/dev-server restart works (`app.py:667`). The blueprint flag has no such reset path, matching the documented blueprint semantics that a blueprint can be registered multiple times and cannot be unregistered (`docs/blueprints.rst:44-46`, `:119-121`).
