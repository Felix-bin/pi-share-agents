## Answer

The dual inheritance is not a taxonomy statement — it is an **audience-multiplexing decision**: in the debug-diagnostics layer, "unexpected unicode or binary data" is deliberately declared to belong to *both* the validation/invariant domain and the encoding domain, so that whichever layer is asked to handle it resolves the class without knowing `flask.debughelpers` exists. The separation between validation failures and encoding issues is therefore maintained by **where the class is placed in the layer/import graph**, not by giving it a distinct type; and the one separation the design does *not* keep — the boundary between "a Flask assertion fired" and "the payload had an encoding problem" at `ValueError` level — is a measured, demonstrated consequence of that choice, not a hypothetical.

### The decisions, each tied to evidence

**1. Collapse the two domains at the type level; carry only a message.** `class UnexpectedUnicodeError(AssertionError, UnicodeError)` — `src/flask/debughelpers.py:17` (re-verified in the worktree). Body is docstring only, no `__init__`/`__str__`: "Raised in places where we want some better error reporting for unexpected unicode or binary data." The base list is the whole design; the docstring frames the purpose as *reporting*, i.e. a message-bearing alias into two existing taxonomies rather than a new error kind.

**2. Base order encodes ownership, and it is a convention, not an accident.** MRO `(UUE, AssertionError, UnicodeError, ValueError, Exception, BaseException, object)` (probe check 4.1). Both `except`-clause matching and the `errorhandler` registry key off the same subclass relation and agree (checks 4.3/4.4): with both registered, the AssertionError handler wins **even when UnicodeError was registered first** (check 5(c3), raw in `unicode_boundary_probe.py.run1-raw`), so the priority is MRO-derived and registration-order-independent. The same module applies the opposite priority where the *data* identity should own the error — `DebugFilesKeyError(KeyError, AssertionError)` at `:23`, KeyError first, raised at `:98`; and `FormDataRoutingRedirect(AssertionError)` at `:50` is single-audience. Across the module's two multi-base classes the first base is consistently the layer that owns the diagnosis — the strongest available (though circumstantial) evidence that the ordering is intentional.

**3. The separation is a *layer* property: lazy load + debug gating + no export.** `import flask` does not put `flask.debughelpers` in `sys.modules` and does not expose the class as a `flask` attribute (probe check 4.7, subprocess-verified); no mention in `src/flask/__init__.py`, no `docs/` hit for `debughelpers`/`UnexpectedUnicode`/`DebugFilesKeyError`, no `CHANGES.rst` entry (its only `Unicode` hits, `:679`/`:826`, are unrelated). The three `debughelpers` consumers are all lazily imported inside gated branches: `app.py` (`FormDataRoutingRedirect`) behind `self.debug` + `RequestRedirect` + not 307/308 + non-GET/HEAD/OPTIONS; `wrappers.py` (`attach_enctype_error_multidict`) behind `current_app.debug` + non-multipart mimetype + empty `files`; and `templating.py` behind `EXPLAIN_TEMPLATE_LOADING` — **not** `debug` (a correction to the earlier reading). Flask's dispatch has no AssertionError branch: the only `AssertionError` occurrences in `src/flask` are raise sites (`ctx.py:268,429`, `sansio/blueprints.py:215`, `sansio/app.py:415,657`) plus a docstring line (`app.py:677`). So validation-vs-encoding separation is enforced by keeping the diagnostic helpers off the normal layer path, with the dual inheritance as the interface that lets a diagnostic message be handed to a handler written for either domain.

**4. The collapse is one-way, and its cost at the handler registry is measured.** A genuine decoding failure produced by `b"\xff\xfe".decode("utf-8")` is a `UnicodeDecodeError`, and `isinstance(real, UnexpectedUnicodeError)` and `isinstance(real, AssertionError)` are both `False` (checks 4.2 and 5(c2), run-2): the stdlib encoding hierarchy is untouched, and the class is a debug wrapper, never the encoding-error type itself. In the other direction the leak is real: `UnicodeError ⊂ ValueError`, so a bare `errorhandler(ValueError)` **silently swallows** `UnexpectedUnicodeError` (200 + handler body) while a plain `AssertionError` escapes to the test client — and the same asymmetry holds at `except ValueError:` level. Absent any handler both give 500 under `TESTING=False` (`rv_plain.status_code == rv_uue.status_code == 500`), so the dual inheritance changes *handler resolution*, not the no-handler HTTP outcome. A 400-code handler is not reached (check 4.6). This is the concrete price of "report to both audiences" over "keep the domains apart": no `ValueError`-level handler can distinguish this diagnostic from a real encoding failure.

**5. The decision is latent at this revision.** There is no raise site anywhere in `src/`, `tests/`, or `examples/`; the only whole-tree occurrence of the name is the definition line; the sibling test (`tests/test_basic.py:1106 test_enctype_debug_helper`) exercises `DebugFilesKeyError` only. So the architecture is reflected solely in the type graph and its import placement — no live behavior demonstrates the separation, and none can be claimed to.
