## Dual inheritance of `UnexpectedUnicodeError`: what the design decides, and what this worktree actually shows

`src/flask/debughelpers.py:17-20` defines the class as `class UnexpectedUnicodeError(AssertionError, UnicodeError)` with a docstring only — no `__init__`, no `__str__`, no other members (re-read and re-grepped this run: the name occurs exactly once in the tree, at the definition). The dual inheritance is therefore the entire design; everything else about the class is inherited.

**The decision it encodes.** The class is deliberately placed in two exception taxonomies at once:

- **Flask's debug/validation channel — `AssertionError`.** This is the repo's marker for internal-invariant and programming-state failures: `src/flask/ctx.py:268`, `:429`, `src/flask/sansio/app.py:415`, `:657`, `src/flask/sansio/blueprints.py:215` all raise `AssertionError(...)`, and the module's siblings `DebugFilesKeyError(KeyError, AssertionError)` (`:23`) and `FormDataRoutingRedirect(AssertionError)` (`:50`) use it to signal "this is a debug-mode diagnostic error". The whole `debughelpers` layer is debug-gated: `attach_enctype_error_multidict` is applied only under `current_app.debug` (`src/flask/wrappers.py:203-210`), and its `DebugFilesKeyError` path is the tested contract (`tests/test_basic.py:1107-1120`, `app.debug = True`).
- **Python's codec/encoding channel — `UnicodeError`** (itself a `ValueError` subclass), which classifies the *data* problem as an encoding/decoding failure rather than a Flask-internal one.

Because the class is empty, membership is the message: the two bases say "report an unexpected unicode/binary-data condition through the debug diagnostic channel while it remains a codec error". The base order is not cosmetic — the executor measured `__mro__` as `[UnexpectedUnicodeError, AssertionError, UnicodeError, ValueError, Exception, BaseException, object]`, `AssertionError` first, so assertion/validation identity is the primary resolution path and codec identity secondary; `except AssertionError`, `except UnicodeError` and `except ValueError` all catch it, and `__init__ is AssertionError.__init__`. The constructor is `AssertionError`'s, consistent with `AssertionError` being the leading base.

**Regarding the separation between validation failures and encoding issues.** The dual inheritance is the architectural *refusal to hard-separate the two categories*. A single-base design would force one classification: a Flask-internal `AssertionError` subclass would drop out of code that catches `UnicodeError`/`ValueError`, and a `UnicodeError` subclass would not read as a debug/validation failure. By inheriting both — and by mirroring the sibling `DebugFilesKeyError(KeyError, AssertionError)` idiom, where the underlying built-in stays first and `AssertionError` is appended to add debug semantics — the design keeps the original error family catchable while adding the debug diagnostic identity. Callers can still separate the two concerns by choosing which base to catch; the library does not. The ordering (`AssertionError` first) decides which identity wins when both would apply.

**Where this worktree contradicts the question's premise.** The question presumes this is "the debug-mode exception class for unexpected unicode or binary data" in an active layered path. The docstring supports that *purpose*, but nothing in this worktree raises, imports, tests or documents it: `grep UnexpectedUnicodeError` returns only the definition (plus `__pycache__` bytecode, not call sites), and there is no `UnicodeError` reference in `src/` outside lines 17/19. So the separation between validation failures and encoding issues is **not observable as exercised behavior here** — it exists as a hierarchy-level design intent, not an enforced code path. For contrast, the same debug module's *live* raise sites are the siblings (`DebugFilesKeyError` at `:98-99`, gated by `wrappers.py:203-210`; `FormDataRoutingRedirect` at `app.py:495-504`), and the encoding/serialization layer that actually runs uses `TypeError`, not `UnicodeError` (`src/flask/json/provider.py:121`), with `from_text`/`from_bytes` tested as ordinary return values (`tests/test_basic.py:1125-1133`). Any statement about how this class *behaves* on a request path would be invention.
