## What the dual inheritance encodes architecturally

`UnexpectedUnicodeError` is defined once, at `src/flask/debughelpers.py:17-20`, as `class UnexpectedUnicodeError(AssertionError, UnicodeError)` with no body, no `__init__`, and no `:meta private:` marker. The two bases are not redundant aliases — they sit on two independent classification axes, and giving the class citizenship in both is the decision:

- **`AssertionError` = Flask's internal "programmer error / broken invariant" tier.** In this tree that tier is exactly what Flask uses for surprises that are not the client's fault and must not become an HTTP status: `ctx.py:268` ("Popped wrong app context"), `ctx.py:429`, `sansio/app.py:415` and `:657` (setup method called after first request, endpoint view-function overwrite), `sansio/blueprints.py:215`. The debug-only diagnostics follow the same convention — `FormDataRoutingRedirect(AssertionError)` (`debughelpers.py:50`) and `DebugFilesKeyError(KeyError, AssertionError)` (`debughelpers.py:23`) are raised as assertions so they surface as tracebacks, and `tests/test_basic.py:1693-1707` / `:1106-1119` assert `pytest.raises(AssertionError)` / `pytest.raises(DebugFilesKeyError)` for them.
- **`UnicodeError` = Python's text/binary decoding tier.** Because `UnicodeError` is a `ValueError` subclass, the second base makes the diagnostic addressable by ordinary encoding-handling code as well.

So the architectural statement is: **an unexpected unicode/binary condition inside Flask is classified as an internal invariant violation, not as a request-validation failure.** It belongs to the exception-hierarchy tier, never to the HTTP-error tier.

### Which part of the layered architecture that separation lives in

The separation is not implemented by intercepting encoding errors somewhere; it is implemented by where the class lands in the dispatch machinery, which the executor exercised live:

1. **WSGI/dispatch layer** — `app.py:1505-1513` `wsgi_app` → `handle_exception`; `app.py:904-920` `full_dispatch_request` → `handle_user_exception` (`app.py:786-810`). The `HTTPException` branch is bypassed: `_get_exc_class_and_code` (`sansio/scaffold.py:694-697`) returns `(cls, None)` for any non-`HTTPException`, so the class can only ever match the `code=None` handler map. Executor confirmed `issubclass(UnexpectedUnicodeError, HTTPException) == False`.
2. **Propagation vs status decision** — `handle_exception` (`app.py:812-873`) sets `propagate = self.config["PROPAGATE_EXCEPTIONS"]`, defaulting to `self.testing or self.debug` at `:841-844`. Live probe: with propagation on the diagnostic escaped as a full traceback (`wsgi_app → handle_user_exception → full_dispatch_request → view`); with propagation off it produced **500, body `<!doctype html>…500 Internal Server Er…`** — never a 4xx. That is the separation made concrete: validation failures become client errors through `handle_http_exception`; this class never does.
3. **Handler-map layer** — `sansio/app.py:823-846` walks `for cls in exc_class.__mro__`, and `docs/errorhandling.rst:230-232` states "Error handlers still respect the exception class hierarchy." Because the MRO is `[UnexpectedUnicodeError, AssertionError (1), UnicodeError (2), ValueError, Exception, BaseException, object]`, **the base order is load-bearing**: if a handler is registered for both `AssertionError` and `UnicodeError`, the programmer-error handler wins. Flask chose programmer-error semantics to *dominate* encoding semantics wherever the two readings overlap. The same nearest-class rule is demonstrated by `tests/test_basic.py:995-1022` (`class E3(E1, E2)` with an `E2` handler yields `b"E2"`), and the executor confirmed a live `@app.errorhandler(AssertionError)` matched it (`599 b'handled as AssertionError'`).
4. **Encoding-seam layer** — the other half of the decision is keeping the two vocabularies joinable *at the boundary* while keeping them apart in the HTTP table. The seam is visible in `wrappers.py:212-219` `on_json_loading_failed(self, e: ValueError | None)`, whose parameter type is precisely the `UnicodeError` parent, and in a JSON layer that openly accepts bytes (`json/__init__.py:84`, `json/provider.py:62` and `:184`: "Text or UTF-8 bytes"). Because the class is catchable as `UnicodeError` and `ValueError` (executor-verified), a decoding failure can be re-expressed into the enclosing layer's own error type instead of escaping as a bare `UnicodeDecodeError`.
5. **API-design layer** — choosing a named subclass rather than raising bare `AssertionError`/`UnicodeDecodeError` gives users a stable type to register a value-specific handler against without matching every assertion in Flask; that is what makes the `docs/errorhandling.rst:230-232` hierarchy contract usable here.
6. **Family idiom** — dual inheritance is a recurring pattern, not a one-off: `DebugFilesKeyError(KeyError, AssertionError)` (`debughelpers.py:23`) pairs "the conventional Python bucket that best names the failure" with "the dispatch channel the diagnostic should be reachable through"; `FormDataRoutingRedirect(AssertionError)` carries only the dispatch channel. `UnexpectedUnicodeError` is the member of that family that bridges the encoding vocabulary instead of the lookup vocabulary.
