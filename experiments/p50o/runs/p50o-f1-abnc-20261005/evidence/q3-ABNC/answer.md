## The modular component registration architecture

The framework separates "registering a component" from "serving a static file" in three layers, and keeps caching identical across the two components by duplicating one hook rather than sharing it.

**1. Shared registration base — `Scaffold`.** `flask.sansio.scaffold.Scaffold` is documented as "Common behavior shared between `Flask` and `Blueprint`" (`src/flask/sansio/scaffold.py:50`). It owns the component-level state and mechanics: `import_name`/`root_path`, the `static_folder` setter (stringifies via `os.fspath`, strips trailing separators) and property (resolves relative to `root_path`), `static_url_path` (derived as `/{basename(static_folder)}` when not configured), `has_static_folder`, plus `add_url_rule`, the view-function/test/template registries and the `setupmethod` guard. Nothing here reads a file — it is configuration and URL registration only.

**2. Static serving is component-scoped, registered separately for each component.**

- The app registers its own route in `Flask.__init__` (`src/flask/app.py:262-279`): rule `f"{self.static_url_path}/<path:filename>"`, `endpoint="static"`, `view_func` a `weakref`-bound `self_ref().send_static_file` (the weakref exists, per the comment, to avoid a reference cycle between app and view — issue #3761), and `host=static_host` under the assertion `bool(static_host) == host_matching`.
- The blueprint — the modular component — registers its own route during `Blueprint.register()` (`src/flask/sansio/blueprints.py:323-328`): the same rule shape with `view_func=self.send_static_file` and `endpoint="static"` (exposed as `blueprint_name.static`), skipped entirely when `self.has_static_folder` is false. The registrations are independent: the app's `/static` route takes precedence, and unlike template folders, blueprint static folders are not searched as a fallback when a file is missing from the app's folder (`src/flask/sansio/blueprints.py:145-147`; `docs/blueprints.rst:212-217`).

**3. The serving implementation sits outside the framework core.** `src/flask/helpers.py` holds `send_file`/`send_from_directory` (thin wrappers over `werkzeug.utils`, re-exported from `flask/__init__.py:19-20`), and `_prepare_send_file_kwargs` (`helpers.py:387-399`) supplies the uniform defaults for every static response: `max_age = current_app.get_send_file_max_age` when none was passed, `USE_X_SENDFILE`, `current_app.response_class`, `_root_path=current_app.root_path`.

**4. Consistent caching comes from two identical hooks, not from one shared definition.** `Flask.get_send_file_max_age` (`app.py:281-306`) and `Blueprint.get_send_file_max_age` (`blueprints.py:55-80`) are the same implementation: read `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]`, return `None` when unset (which tells the browser to use conditional requests instead of a timed cache), otherwise convert a `timedelta` to seconds or return the number. Both `send_static_file` methods then compute `max_age = self.get_send_file_max_age(filename)` themselves and pass it explicitly into `send_from_directory`, because — as the identical comment in both files states — "send_file only knows to call `get_send_file_max_age` on the app, call it here so it works for blueprints too" (`app.py:322-328`, `blueprints.py:96-102`). Both docstrings likewise note "this is a duplicate of the same method in the Flask class". The effect: setting `SEND_FILE_MAX_AGE_DEFAULT` governs the app's static route and every registered blueprint's static route alike, while a subclass on either side (`class MyApp(Flask)` or `class MyBlueprint(Blueprint)`) can override the hook for just that component's files.

The reason the hook is duplicated instead of living on `Scaffold` is the sans-IO constraint: `src/flask/sansio/README.md` says that code may not do IO and may not use the Flask globals, whereas the hook reads `current_app` and the static view returns a `Response`. A tree-wide search confirms `get_send_file_max_age` and `send_static_file` exist only in the IO-side `flask/app.py` and `flask/blueprints.py`, with the sole sansio reference being the `view_func=self.send_static_file` registration in `sansio/blueprints.py:326`. (Note the asymmetry this produces: blueprint static *registration* lives in the sansio layer, while app static *registration* and both components' *serving* methods live in the IO layer.)

The design intent is recorded in `CHANGES.rst:1292-1300`: "`Flask` and `Blueprint` now provide a `get_send_file_max_age` hook for subclasses to override behavior of serving static files … The default max-age for `send_file` and static files can be configured through a new `SEND_FILE_MAX_AGE_DEFAULT` configuration variable, which is used in the default `get_send_file_max_age` implementation." The consistency is asserted in tests, not only in prose: `tests/test_helpers.py:40-85` (`TestSendfile::test_static_file`: default `max_age` None, config `3600`, `pathlib.Path`, subclass override `10`) and `tests/test_blueprints.py:195-206` and `:223-244` (blueprint static served at `/admin/static/css/test.css` honours `SEND_FILE_MAX_AGE_DEFAULT`, and a blueprint subclass override of `get_send_file_max_age` returning `100` wins over a config of 3600/7200).
