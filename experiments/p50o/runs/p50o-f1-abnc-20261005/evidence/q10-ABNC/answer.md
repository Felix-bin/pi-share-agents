## The dependency chain in the subdomain-routing test

The test with that shape is `tests/test_testing.py::test_blueprint_with_subdomain` (lines 117–139). Its steps form a chain where each link supplies something the next link reads:

1. **Configuration — `Flask(__name__, subdomain_matching=True)`.** Sets `App.subdomain_matching` (`src/flask/sansio/app.py:407`). This attribute is consumed only at request time, in `Flask.create_url_adapter` (`src/flask/app.py:458–462`): when it is false, the adapter is forced to `subdomain = self.url_map.default_subdomain or ""` instead of deriving the subdomain from the host. Nothing else in the test reads it.
2. **Configuration — `SERVER_NAME = "example.com:1234"`.** It feeds three separate consumers: the test client / context environ host (`src/flask/testing.py:66–70`), the `server_name` passed to `url_map.bind_to_environ` at request time (`src/flask/app.py:452`), and `url_for` outside a request, which raises `RuntimeError` unless it is set (`src/flask/app.py:468–476`).
3. **Configuration — `APPLICATION_ROOT = "/foo"`.** Becomes the environ's script root (`src/flask/testing.py:67,78`) and the adapter's `script_name` (`src/flask/app.py:470–474`). This is the link that puts `/foo/` at the end of the asserted URL.
4. **Route registration — `Blueprint("company", __name__, subdomain="xxx")` + `@bp.route("/")`.** Both are *deferred*: the blueprint stores the record and names the endpoint `company.index` (`src/flask/sansio/blueprints.py:103–116`). No rule exists in the URL map yet.
5. **Route registration — `app.register_blueprint(bp)`.** This is what materialises the rule: `BlueprintSetupState.add_url_rule` → `App.add_url_rule` → `url_map.add(Rule("/", subdomain="xxx", endpoint="company.index"))` (`src/flask/sansio/app.py:656–658`). Link 1 and 5 are the two prerequisites for any *match* to succeed.
6. **Request context creation — `ctx = app.test_request_context("/", subdomain="xxx")`.** `EnvironBuilder` composes the base URL from links 2 + 3 (`subdomain."SERVER_NAME"` + `APPLICATION_ROOT` → `http://xxx.example.com:1234/foo/`), then `Flask.request_context` → `RequestContext.__init__` → `create_url_adapter(request)` (`src/flask/ctx.py:317–325`). Because merely *creating* the context does not match a URL, the first assertion (`ctx.request.url == "http://xxx.example.com:1234/foo/"`) depends on links 2 + 3 only — not on route registration.
7. **Context push — `with ctx:`.** `RequestContext.push` pushes an app context and then calls `match_request()` (`src/flask/ctx.py:370–374, 391–394`), which is where the subdomain rule is selected and `request.url_rule`/`view_args` are set. The second assertion (`request.blueprint == "company"`) therefore depends on link 5 (the rule exists) *and* link 1 (subdomain matching enabled), and reaches its value through the endpoint name built in link 4 (`src/flask/wrappers.py:162–176`).
8. **Dispatch — `client.get("/", subdomain="xxx")`.** Rebuilds the same environ and repeats links 6–7 for a fresh request; the view returns `request.url`, so the final assertion depends on links 1, 2, 3 and 5 together.

Net chain: `subdomain_matching=True` → adapter keeps `subdomain=None` so `bind_to_environ` derives `"xxx"` from the host; `SERVER_NAME` → the name the subdomain is relative to; `APPLICATION_ROOT` → the `/foo/` script root; blueprint `subdomain` + `register_blueprint` → the rule the match can select; `test_request_context(subdomain="xxx")` → the environ carrying the subdomain; push → `match_request()` → `request.blueprint`; `client.get` → the same path end to end.

**The link that carries the "routing" half is `subdomain_matching` alone.** URL *construction* (`EnvironBuilder` and `create_url_adapter(None)`) produces the `xxx.` host regardless of it; only matching consults it.

**Same chain in the sibling test.** `tests/test_testing.py::test_subdomain` (lines 302–319) has the identical three phases with a variable subdomain: configuration (`subdomain_matching=True`, `SERVER_NAME`), route registration (`@app.route("/", subdomain="<company_id>")`), request-context creation (`with app.test_request_context():`, which exists to give `flask.url_for("view", company_id="xxx")` an app context and adapter). There the URL takes the place of the blueprint rule as the input to `client.get`. The script `flask_mut2_i417ar2x/mutated_test.py` is a copy of that test with `subdomain_matching=False`; reading the same code paths, disabling link 1 forces `subdomain=""` (`src/flask/app.py:458–462`) so `MapAdapter.match` is called with an empty domain part, which cannot match the rule's `<company_id>` domain segment — its compiled domain part is a single dynamic part (`[^/]+`, `werkzeug/routing/converters.py:25`, `rules.py:699–726`), so no rule matches and the response is 404.
