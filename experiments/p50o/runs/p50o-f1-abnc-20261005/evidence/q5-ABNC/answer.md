## The test and its chain

The test that verifies subdomain routing end-to-end through configuration, route registration and request-context creation is **`tests/test_testing.py::test_subdomain`** (`tests/test_testing.py:302-318`); the same body appears de-functioned as a module-level script in `flask_mut2_i417ar2x/mutated_test.py`, which is the artifact the recorded pytest run exercised. The chain has four dependent links, in this order:

**1. Configuration → `app.subdomain_matching` and `app.config["SERVER_NAME"]`** (`tests/test_testing.py:303-304`)
`flask.Flask(__name__, subdomain_matching=True)` stores the flag as `self.subdomain_matching` in `src/flask/sansio/app.py:407`, and `app.config["SERVER_NAME"] = "example.com"` supplies the base domain. Both are read much later, per request, not at construction time.

**2. Route registration → a rule carrying the subdomain pattern** (`tests/test_testing.py:307-309`)
The `@app.route("/", subdomain="<company_id>")` decorator resolves through `Scaffold.route` (`src/flask/sansio/scaffold.py:336-358`) into `add_url_rule`, which builds `Rule("/", subdomain="<company_id>", methods={...})` and calls `self.url_map.add(rule_obj)` and `self.view_functions[endpoint] = view_func` (`src/flask/sansio/app.py:650-661`). The endpoint is not passed, so it defaults to the function name `view` — the exact name the later `flask.url_for("view", ...)` depends on.

**3. Request-context creation → the URL adapter that both builds and matches** (`tests/test_testing.py:311-312`)
`with app.test_request_context():` calls `Flask.test_request_context` (`src/flask/app.py:1423`), which builds a Flask `EnvironBuilder` (`src/flask/testing.py:27`) whose base URL is composed from `PREFERRED_URL_SCHEME`, `subdomain`, `SERVER_NAME` and `APPLICATION_ROOT` (`src/flask/testing.py:65-80`), then `app.request_context(environ)` → `RequestContext(app, environ)` (`src/flask/app.py:1421`, `src/flask/ctx.py:311-325`). `RequestContext.__init__` immediately calls `app.create_url_adapter(self.request)` (`src/flask/ctx.py:323`); entering the block runs `RequestContext.push`, which pushes an `AppContext` (whose own `__init__` already built a `create_url_adapter(None)` adapter from `SERVER_NAME`/`APPLICATION_ROOT`/`PREFERRED_URL_SCHEME`, `src/flask/ctx.py:247`), opens the session, and calls `match_request()` → `url_adapter.match(...)` (`src/flask/ctx.py:367-394`, `357-365`).

`create_url_adapter` is the hinge of the chain (`src/flask/app.py:442-474`): with a request present it binds `url_map.bind_to_environ(environ, server_name=SERVER_NAME, subdomain=...)`, and it passes `subdomain = self.url_map.default_subdomain or ""` **only when `not self.subdomain_matching`** (`src/flask/app.py:458-462`); otherwise it lets the adapter derive the subdomain from the host relative to `SERVER_NAME`.

**4. URL building inside the context, then a real request** (`tests/test_testing.py:311-314`)
`flask.url_for("view", company_id="xxx")` (`src/flask/helpers.py:188`) delegates to `Flask.url_for` (`src/flask/app.py:1003`), which in a request context uses `req_ctx.url_adapter` (`src/flask/app.py:1063`), defaults `_external` to `False` (`src/flask/app.py:1075-1076`) and calls `url_adapter.build(...)` (`src/flask/app.py:1110`). Werkzeug then returns a bare path only if the rule's subdomain equals the adapter's subdomain, and otherwise returns an absolute URL (`werkzeug/routing/map.py:944-951`) — here `"xxx" != ""`, so the built URL is `http://xxx.example.com/xxx`. `with client: client.get(url)` sends that absolute URL through `FlaskClient` (`src/flask/testing.py:109-126`, `249-261`), so `wsgi_app` builds a **new** `RequestContext` for the environment whose host is `xxx.example.com`, `create_url_adapter` re-derives subdomain `"xxx"` against `SERVER_NAME`, and `url_adapter.match` selects the rule registered in link 2, invoking `view(company_id="xxx")` — satisfying `assert 200 == response.status_code` / `assert b"xxx" == response.data`.

**Dependency direction:** link 1 gates link 3 (`subdomain_matching` decides whether the adapter derives or forcibly blanks the subdomain) and link 3 gates both halves of link 4 (URL building needs the adapter; request matching needs the derived subdomain). Link 2 gates link 3's matching (no rule, no `subdomain="<company_id>"` to match) and link 4's `url_for` (the endpoint name must exist in `url_map`).
