## The interaction

`tests/test_cli.py:199-219` parametrizes one test (`test_locate_app_raises`, `def` at `:217`) over eight `(iname, aname)` pairs, and the pairs are chosen so that they split exactly along the two stages `locate_app` has, not along eight arbitrary failures. Four pairs pass `aname=None` and therefore never get past the import step; four pass an app-name string and therefore reach `find_app_by_string`. The consistency the test asserts is narrow and mechanical: whatever the branch, the call must surface `flask.cli.NoAppException` (`src/flask/cli.py:37`, a `click.UsageError` subclass), not a raw `ModuleNotFoundError`/`SyntaxError`/`AttributeError`/`TypeError` and not `None`. That holds because every failure branch in both stages explicitly converts its underlying cause into `NoAppException`, and because `find_app_by_string` closes with a catch-all `isinstance(app, Flask)` check (`cli.py:191-196`) that turns "the factory returned something that isn't an app" into the same type as every other failure. Runtime measurement confirms the funnel is real and single-valued: each of the eight pairs raises `NoAppException` from exactly one identified `raise` line, and two pairs share a line, so the parametrization exercises **six distinct failure surfaces across eight cases**:

### Why the eight cases stay independent

The fixture that feeds the parametrization is part of the interaction, not background. `tests/conftest.py:71-81` (`test_apps`) does `monkeypatch.syspath_prepend(.../tests/test_apps)` (`:73`) and, after the test, pops every `sys.modules` key that was not present before. The pairs deliberately reuse module names — `cliapp.factory` appears in three pairs, `cliapp` in six — so without that purge a successfully imported module would be served from the cache on the next parametrized case and the later branches would never execute. With the purge, each pair resolves `cliapp.*` fresh from `tests/test_apps`, which is what makes eight independent failure surfaces reproducible inside one parametrized test.

### The one conditional that decides raising vs not raising

`locate_app`'s `except ImportError` block is the only place where the function can *avoid* failing: it inspects traceback depth (`sys.exc_info()[2].tb_next`, `cli.py:249`) and only a depth-1, direct-import `ImportError` is returnable as `None` when `raise_if_not_found=False`; an `ImportError` raised inside the target module escalates to the traceback-embedding `NoAppException` at `:250`. The parametrization straddles both sides of that boundary on purpose — pair 7 (`cliapp.importerrorapp`, whose `tests/test_apps/cliapp/importerrorapp.py` does `raise ImportError()` at module top level) is the in-module side, pairs 1, 2 and 8 are the direct-import side — and `tests/test_cli.py:222-229` (`test_locate_app_suppress_raise`) pins the boundary explicitly: `raise_if_not_found=False` returns `None` for `"notanapp.py"`, `"cliapp/app"` and `"cliapp.message.txt"` (confirmed by the `locate_app(..., raise_if_not_found=False)` probes) yet still raises for `"cliapp.importerrorapp"`, matching the test's own comment `# only direct import error is suppressed`. So "fails consistently" has two halves in the evidence: within `test_locate_app_raises` every pair must raise the same type, and in the sibling test the same code must *not* raise for a subset of those same inputs under a different flag — consistency of the exception channel, not of the outcome.

### What the test itself does not pin down

- The assertion at `:218-219` is type-only — no `match=`, no message, no state. It cannot distinguish the six branches from one another; a pair landing on the wrong branch, or two pairs sharing a branch, would still pass. The per-pair branch attribution above is therefore an external measurement, not something the test states. (Pair 5's `# invalid identifier` comment mislabels it: the branch actually taken is the `ast.parse` `SyntaxError` conversion at `:131`.)
- Because all four `aname=None` pairs fail during import, **`find_best_app` is never reached** by this test (`cli.py:41`); its `NoAppException` surfaces — multiple Flask instances, and the `create_app`/`make_app` `TypeError` path — are covered by the sibling success test `test_locate_app` (`tests/test_cli.py:195-196`) instead.
- The conversion is not universal: at `cli.py:181`, a `TypeError` raised *inside* a factory body is re-raised bare (via `_called_with_wrong_args` returning `False`), i.e. deliberately not funnelled into `NoAppException`. No parametrized pair exercises that path — pair 4 is the wrong-arguments side, measured `_called_with_wrong_args(factory.create_app2) → True`.
- `raise ... from None` suppresses the display of the cause but does not erase it: the measured `__context__` of the raised `NoAppException` is still `ModuleNotFoundError` / `SyntaxError` / `AttributeError` / `TypeError` / `ImportError` as tabulated.
