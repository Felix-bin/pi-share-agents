# How blueprint-registered template functions become visible at render time

Four mechanisms, in the order they act, plus two sibling paths that reach rendering without touching `jinja_env`.

**1. Registration defers instead of writing immediately.** `Blueprint.add_app_template_filter` (`src/flask/sansio/blueprints.py:461-475`) does not touch any app; it defines a local `register_template(state)` whose body is `state.app.jinja_env.filters[name or f.__name__] = f` and hands it to `self.record_once(register_template)`. `add_app_template_test` (`:497-513`) and `add_app_template_global` (`:535-551`) are identical with `state.app.jinja_env.tests` and `state.app.jinja_env.globals`. The decorator forms `app_template_filter` / `app_template_test` / `app_template_global` (`:444-459`, `:480-496`, `:521-534`) only forward to those. So at decoration time the blueprint holds the function, and no environment exists yet.

**2. `record_once` is the deferral store, and it carries the once-only guard.** `record_once` (`:233-244`) wraps the callback so it runs only `if state.first_registration`, then stores the wrapper via `record` (`:224-230`), which is `self.deferred_functions.append(func)`; `deferred_functions` is created per blueprint at `:204`.

**3. `Blueprint.register` drains the deferred list against the app that will own the environment.** `register` (`:273-343`) computes `first_bp_registration = not any(bp is self for bp in app.blueprints.values())`, sets `_got_registered_once`, builds `state = self.make_setup_state(app, options, first_bp_registration)`, and at `:334-335` runs `for deferred in self.deferred_functions: deferred(state)`. `BlueprintSetupState.first_registration` is set at `:62` and `state.app` is the app passed to `make_setup_state` (`:246-253`). Nested blueprints are recursed at `:348-379` (`blueprint.register(app, bp_options)`), so a child blueprint's `register_template` callbacks also write into the same app.

**4. "Shared template environment" is literally one cached object, so what the callback mutates is what rendering reads.** `jinja_env` is `@cached_property` (`src/flask/sansio/app.py:469-477`) returning `create_jinja_environment()` (`src/flask/app.py:385-428`), which seeds `globals` with `url_for`, `get_flashed_messages`, `config`, `request`, `session`, `g`, etc. Rendering resolves through the same property: `app.jinja_env.get_or_select_template(...)` in `render_template` (`src/flask/templating.py:138-150`), `from_string` (`:158-162`), and both `render_template_string`/streaming variants (`:200-219`); `get_template_attribute` reads `current_app.jinja_env` too (`src/flask/helpers.py:308`). Because `state.app.jinja_env` is a property access, the first use creates and caches the instance; every later read is that same object, so the mutated `filters`/`tests`/`globals` dicts are the ones Jinja consults. The executor's run confirmed this identity empirically: the same `jinja_env` object before registration, after registration, and after render, with the registered callables present, identical objects, and served by an actual render (`{{ 'x'|bp_filter }}|{{ 7 is bp_test }}|{{ bp_global() }}` → `F:x|True|G42`).

Two enforcement details rather than mechanisms of visibility: `_check_setup_finished` (`:210-219`) plus `@setupmethod` on all three `add_app_template_*` methods raises `AssertionError` if you try to add template functions after the blueprint was registered, and the `first_registration` guard makes a second registration of the same blueprint a no-op for these callables (executor case C: registering the same blueprint twice leaves the env key set unchanged). Both exist so the deferred writes cannot land inconsistently.

## The paths that do not go through `jinja_env`

**Context processors** are merged, not written into the Jinja environment. `@bp.app_context_processor` uses `self.record_once(lambda s: s.app.template_context_processors.setdefault(None, []).append(f))` (`blueprints.py:584-591`), the deferred path again. `@bp.context_processor` is blueprint-local: `context_processor` appends to `self.template_context_processors[None]` (`src/flask/sansio/scaffold.py:542-557`), and `_merge_blueprint_funcs` re-keys blueprint entries with the dotted blueprint name — `extend(self.template_context_processors, app.template_context_processors)` where each key becomes `name if key is None else f"{name}.{key}"` (`blueprints.py:400-413`) — running only `if first_bp_registration or first_name_registration` (`:329-330`). At render time `update_template_context` iterates `names = (None, *reversed(request.blueprints))` and applies the matching lists (`src/flask/app.py:506-538`), which is why app-wide entries apply everywhere and blueprint-scoped ones only on that blueprint's pages. Executor case A/D: the `app_context_processor` value renders (`...|{{ cval }}` → `C`), the app-wide entry lands under key `None`, and the blueprint-scoped one is merged under the dotted name (`bp4` → `['_default_template_ctx_processor', 'local_ctx']`).

**Template sources** reach the same environment through the loader rather than through callbacks: `Environment.__init__` sets `options["loader"] = app.create_global_jinja_loader()` when none is given (`src/flask/templating.py:43-49`), which returns `DispatchingJinjaLoader(self)` (`src/flask/sansio/app.py:519-531`), whose `_iter_loaders` yields the app loader and then `blueprint.jinja_loader` for every `self.app.iter_blueprints()` (`src/flask/templating.py:97-110`).
