# How the application-context namespace object (`g` / `_AppCtxGlobals`) stays safe under concurrent access

Short answer: it maintains neither through locking nor through any synchronisation inside the namespace object. `_AppCtxGlobals` is deliberately lock-free, and the concurrency guarantee comes from *isolation* — one namespace instance per application context, reachable only through the current `ContextVar` — so two threads or tasks never touch the same dictionary in the first place.

## The mechanism, in order

**1. The namespace object itself has no synchronisation.** `src/flask/ctx.py:29` declares `class _AppCtxGlobals` with the docstring (lines 30–31) "A plain object. Used as a namespace for storing data during an application context." Every accessor reads or writes `self.__dict__` directly — `__getattr__` (`ctx.py:52`), `__setattr__` (`ctx.py:58`), `__delattr__` (`ctx.py:61`), `get` (`ctx.py:67`), `pop` (`ctx.py:78`), `setdefault` (`ctx.py:92`), `__contains__` (`ctx.py:104`), `__iter__` (`ctx.py:107`) — with no `Lock`, `RLock` or any other primitive in the class, and a repository-wide search for synchronisation primitives in `src/flask` returning only docstring prose. So the object is *not* internally thread-safe. Safety is not obtained by synchronisation.

**2. A fresh namespace is created once per application context.** `AppContext.__init__` (`ctx.py:245`) contains `self.g: _AppCtxGlobals = app.app_ctx_globals_class()` (`ctx.py:248`), and `app_ctx_globals_class` defaults to `_AppCtxGlobals` (`src/flask/sansio/app.py:185`). Distinct application contexts therefore never hold the same namespace object.

**3. Which namespace is reachable is decided by a `ContextVar`, not by a global.** `src/flask/globals.py:24`: `_cv_app: ContextVar[AppContext] = ContextVar("flask.app_ctx")`. `AppContext.push` binds the caller's execution context to that context instance and keeps the returned token: `self._cv_tokens.append(_cv_app.set(self))` (`ctx.py:253`). `AppContext.pop` restores the previous value — `ctx = _cv_app.get()` (`ctx.py:264`) then `_cv_app.reset(self._cv_tokens.pop())` (`ctx.py:265`) — and then asserts `ctx is self`, raising `AssertionError("Popped wrong app context. ...")` otherwise (`ctx.py:267-269`); `__enter__`/`__exit__` (`ctx.py:274`, `278`) are just `push`/`pop`. Because `ContextVar.set` writes into the *current* `contextvars.Context` — per OS thread, per `asyncio` task — the token stack makes push/pop correctly nested and reversible within one execution context.

**4. `g` is a lazy proxy, so each access re-resolves against the caller's own context.** `src/flask/globals.py:31-33`: `g: _AppCtxGlobals = LocalProxy(_cv_app, "g", unbound_message=_no_app_msg)`. Reading `g.x` is therefore `_cv_app.get().g.x`, evaluated at attribute-access time, and the documentation describes exactly this proxy behaviour — "Accessing `db` will call `get_db` internally" (`docs/appcontext.rst:136`, in the passage at lines 130–136 that recommends `LocalProxy` for building context locals). Two threads or tasks consequently reach two different `_AppCtxGlobals` objects; a write by one is invisible to the other by construction, and disjoint objects need no mutual exclusion. If no app context is bound, the same proxy raises the "Working outside of application context." message (`globals.py:16-21`) — an error path, not a race.

This matches the documented contract rather than contradicting it: `g` is "a simple namespace object that has the same lifetime as an application context" (`docs/appcontext.rst:89-101`), "unique for each request" (`docs/tutorial/database.rst:63`), and the context "is unique to each thread (or other worker type) … the other thread has a different context space" (`docs/reqcontext.rst:39-47`), which also names the implementation: "Context locals are implemented using Python's `contextvars` and Werkzeug's `LocalProxy`." The same section notes a worker "handles only one request at a time" (`docs/reqcontext.rst:21-22`), and for `async` views the isolation still holds because Flask runs the coroutine "on a separate thread instead of using an event loop on the main thread" (`docs/design.rst:190-196`).

## Where isolation ends

- **The namespace protects the slot, not the payload.** If a mutable value stored on `g` (a database connection, a list) is handed to another thread or task, that object's own thread-safety is unaffected by any of the above.
- **The `g` object belongs to the `AppContext` instance, not to the push.** If one `AppContext` instance were pushed from two threads at once, both threads' `_cv_app` would resolve to it and `g` would literally be the same object; per-context isolation is what the design guarantees, not per-thread isolation of a shared context. This is inferred from `ctx.py:248` (the namespace is built in `__init__`) and is not stated in the documentation.
- **Copying a context copies the `ContextVar` value by reference**, so a `copy_context()`-derived execution context sees the same `AppContext` and the same `g`.
- **No source text says locks are unnecessary** — the documentation asserts isolation ("unique to each thread", "different values for each request", `docs/api.rst:156-162`) without ever naming the absence of locking. The step "therefore no lock is needed" is an inference from `ctx.py:29-115` plus `ctx.py:248-253`, not a quoted contract.
