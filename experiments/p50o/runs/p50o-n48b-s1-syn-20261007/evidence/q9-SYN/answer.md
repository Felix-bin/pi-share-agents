# The dependency chain

The chain is a two-edge, three-node graph whose hinge is `FlaskCliRunner`. The Flask application instance is the value that travels; `ScriptInfo` is what re-materialises that value as an application context inside the command; `click.testing.CliRunner` is what makes the whole invocation happen in isolation.

**The chain, end to end**

1. **Application → base Click runner.** `Flask.test_cli_runner()` (`src/flask/app.py:727-742`) reads the override hook `cls = self.test_cli_runner_class` (`src/flask/sansio/app.py:277`), late-binds `FlaskCliRunner` if it is `None`, and calls `cls(self, **kwargs)` — the app is the first positional argument. `FlaskCliRunner.__init__` (`src/flask/testing.py:271-273`) does `self.app = app` and then `super().__init__(**kwargs)`, so all of click's isolation machinery is inherited, not reimplemented: `FlaskCliRunner` defines only `__init__` and `invoke`, with no `isolation`, `make_env`, or `make_context` override (`src/flask/testing.py:265-298`).

2. **Application → application loading helper.** `FlaskCliRunner.invoke` (`src/flask/testing.py:275-298`) does two things before delegating: `if cli is None: cli = self.app.cli` (line 293), so the default command group is the app's own Click group (set in `Flask.__init__` at `src/flask/app.py:256`), and `if "obj" not in kwargs: kwargs["obj"] = ScriptInfo(create_app=lambda: self.app)` (line 296). The closure captures the *same* app object stored on the runner.

3. **Helper → active application context.** Commands registered on `app.cli` are `AppGroup.command`-wrapped in `with_appcontext` unless `with_appcontext=False` (`src/flask/cli.py:415-432`). `with_appcontext` (`src/flask/cli.py:395-400`) executes `app = ctx.ensure_object(ScriptInfo).load_app()` and then `ctx.with_resource(app.app_context())`. That is the edge where the helper's app becomes the live Flask app context for the command body.

4. **Base runner → isolation.** `super().invoke(cli, args, **kwargs)` (line 298) positionally matches click's signature (`src/flask/testing.py:275`, `click/testing.py:423`). `CliRunner.invoke` runs `cli.main(args=args or (), prog_name=prog_name, **extra)` (`.venv/Lib/site-packages/click/testing.py:494`) inside `with self.isolation(input=input, env=env, color=color)` (line 480). `CliRunner.isolation` (`click/testing.py:276-350`) saves the old `sys.stdin/stdout/stderr`, sets `FORCED_WIDTH = 80`, applies `make_env(env)` over `os.environ`, rebinds the three streams to `_NamedTextIOWrapper`s, and restores them afterwards; the call returns a `Result` carrying `stdout_bytes`/`stderr_bytes`/`exit_code`/`exception` (lines 527-534). This is the sole source of stream/env/filesystem isolation — Flask contributes none of it.

**Why the three together produce "proper CLI command execution in isolation"**

The helper is the adapter that lets a Flask app be loaded by a Click-level runner: `ScriptInfo` (`src/flask/cli.py:293-376`) returns the memoized `self._loaded_app` (lines 338-339) or calls `self.create_app()` (lines 341-342), otherwise resolving `app_import_path` / `wsgi.py`/`app.py` and raising `NoAppException` if it cannot (line 364+). Because `FlaskCliRunner` always injects `create_app=lambda: self.app`, the loader never has to search the filesystem in tests — it returns the in-memory app. The app instance then supplies both the command group (`cli = self.app.cli`) and the context pushed by `with_appcontext`, so a command registered on `app.cli` runs with the app under test bound as `current_app`. Meanwhile click's `isolation` guarantees that whatever the command does to `sys.stdout` or `os.environ` does not escape the invocation, and that the result is captured. Other consumers of the same helper (`FlaskGroup.list_commands` → `info.load_app().cli.list_commands(ctx)`, `src/flask/cli.py:645`; `FlaskGroup.make_context` building `ScriptInfo(create_app=self.create_app, ...)` and setting `os.environ["FLASK_RUN_FROM_CLI"] = "true"`, lines 667-675) show the helper is not test-only, but they were not exercised by the executed step.

**Runtime check (executor).** The chain was not only read but executed. `uv run pytest tests/test_testing.py -k "cli" -q` exited 0 with `8 passed, 17 deselected in 0.12s`, and `uv` rebuilt/installed `flask` from this worktree, so `src/flask` itself was under test. An inline probe (no file written) reported: runner type `flask.testing.FlaskCliRunner`; `runner.app is app` True; `ScriptInfo(create_app=lambda: app).load_app() is app` True; memoized `_loaded_app` identical; default cli is `app.cli`; a registered command ran with `exit_code 0`, `output 'whoami-ran'`, `exception None`; **`current_app` inside the command body is the same app object**; `ctx.ensure_object(ScriptInfo).load_app()` inside the command returns it too; `sys.stdout` restored after `invoke`; `os.environ` keys unchanged. The `current_app` probe is the runtime confirmation of step 3, which the static read could only infer.

**Two corrections carried by the evidence.** (a) The plan's statement that "there is no `runner` fixture" holds for `tests/conftest.py` but not for the corpus: `tests/test_cli.py:36-38` defines a `runner` fixture returning a bare `CliRunner()` — that file exercises the helper/`FlaskGroup` path directly (`obj=ScriptInfo(...)` at lines 302-303, 307-317, 348-362), while `tests/test_testing.py` exercises it through `FlaskCliRunner`. (b) `-k "cli"` matches the substring `client`, so 8 tests were selected, not the 3 named; `test_cli_runner_class`, `test_cli_invoke`, and `test_cli_custom_obj` were among the 8 and all passed. Separately, `tests/test_cli.py:402, 417, 435` still try `CliRunner(mix_stderr=False)` behind an `except (DeprecationWarning, TypeError)`, a parameter click 8.2 removed, so the fallback branch is what executes.

**Still open.** No runtime check of a *cached* `ScriptInfo` reused across more than the two `load_app()` calls probed, and the production `FlaskGroup.make_context` path was not exercised. Nothing here establishes behaviour of `FlaskCliRunner` beyond forwarding — it has none.
