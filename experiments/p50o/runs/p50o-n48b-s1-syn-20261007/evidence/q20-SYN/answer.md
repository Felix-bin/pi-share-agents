# The callback ensures no such consistency — its job is a per-response write decision

The task's premise does not hold in this codebase. `SecureCookieSession` (`src/flask/sessions.py:52`) is the only class in the worktree that subclasses werkzeug's `CallbackDict`, and its `on_update` callback (`src/flask/sessions.py:74-82`, setting `modified = True` and `accessed = True`) does not synchronize anything between requests. It is a per-instance dirty flag that answers one question: **should this response re-serialize the session cookie?** It never compares in-memory state against the persisted cookie, never detects that another request changed the cookie, and never resolves a conflict between two in-flight copies.

**What the callback actually does, end to end.**

- `modified`/`accessed` default to `False` per instance (`src/flask/sessions.py:66,72`), overriding `SessionMixin`'s hard-coded `True` for backends that cannot detect changes (`:44-49`). Werkzeug's `CallbackDict.__init__` assigns `self.on_update` *after* `dict.__init__(initial)`, so populating a session from decoded cookie bytes in `__init__` fires nothing — a freshly loaded session reports `(False, False)`.
- Every mutating mapping operation (`__setitem__`, `__delitem__`, `clear`, `popitem`, `update`, `__ior__`) runs through `UpdateDictMixin`'s `@_always_update` wrapper and fires `on_update`; `setdefault`/`pop` are special-cased to fire only when the mapping actually changed. Reads — including `__getitem__`, `get`, `setdefault`, which are overridden at `src/flask/sessions.py:84-93` — set `accessed` alone.
- The documented blind spot (`src/flask/sessions.py:61-65`, `docs/api.rst:80-91`): mutating a nested mutable value (`session["objects"].append(42)`) fires nothing; the developer must set `session.modified = True` by hand.
- Consumption is entirely on the response side. `save_session` (`src/flask/sessions.py:351-399`) adds `Vary: Cookie` if `accessed`; deletes the cookie only if the session is empty *and* `modified`; returns early unless `should_set_cookie` (`:247-261`, i.e. `modified or (permanent and SESSION_REFRESH_EACH_REQUEST)`); otherwise dumps the **whole** dict and calls `set_cookie`. So the flag's only effect is whether this response writes a cookie, and every write is a full replacement.

**Why that cannot give cross-request consistency.** The default backend is stateless — the cookie *is* the store. `open_session` (`src/flask/sessions.py:337-349`) reads `request.cookies[name]`, verifies it with `s.loads(val, max_age=...)`, and returns `self.session_class(data)`, a private in-memory copy per request; `BadSignature` yields an empty session with no error and no mutation. `save_session` writes a full replacement cookie. Neither path reads or writes any shared server-side structure, so two requests opened from the same cookie each hold an independent copy and each overwrite the whole cookie. `src/flask/sessions.py:141-146` says exactly this as far as the code is willing to go: multiple requests with the same session may be handled concurrently, "consider whether reads or writes to the backing store must be synchronized," and "There is no guarantee on the order in which the session for each request is opened or saved, it will occur in the order that requests begin and end processing." No lock, mutex, version counter, or compare-and-swap appears anywhere in `src/flask/sessions.py` (a grep for `lock|mutex|threading|version` matches only `.. versionadded`/`.. versionchanged` changelog markers).

**Empirical confirmation (executed, not just read).** Running with `PYTHONPATH=src` (required: `.venv/Lib/site-packages/flask.pth` points outside this worktree, so a bare `import flask` does not load this source), python 3.13.9 / werkzeug 3.1.3, the full prediction table reproduced with no mismatch: init-time load `(False, False)`; `s["a"]=1` `(True, True)`; `update`/`pop`-present/`setdefault`-missing/`del`/`clear`/`popitem`/`|=` each `(True, True)`; no-op `pop(k, default)` `(False, False)`; present-key `setdefault` and all reads `(False, True)`; nested in-place mutation `(False, False)` while the stored list did change; flags strictly per instance, with class attributes staying `False`. A raw `CallbackDict` control recorded exactly 8 `on_update` calls for 8 mutating operations and 0 for 6 non-mutating/no-op ones. Two `test_request_context` blocks built from the *same* serialized cookie each loaded `{'user': 'alice'}` at `(False, False)`, wrote their own values, and neither observed the other's write — independent copies, no shared store. `pytest tests/test_basic.py -k "session"` → 13 passed. The worktree's own tests (`tests/test_basic.py:229-252` for the flag contract, `:520-595` for `Vary`/refresh) exercise the flags only; nothing drives two in-flight requests.

**The consistency that does exist, stated precisely.** The callback guarantees that a *single* response echoes that request's in-memory session faithfully — a change made in that request is marked and re-serialized, and an untouched loaded session is not rewritten. Across concurrent requests the code guarantees the opposite of consistency: `src/flask/sessions.py:141-146` explicitly disclaims ordering, and the observable resolution is last-write-wins by whichever `Set-Cookie` the client applies last. That last-write-wins resolution is an *inference* from the load/save paths (`:337-349` + `:351-399`) and the two-request probe; it is not asserted anywhere in the repository's prose, and no test or fixture here exercises truly simultaneous requests. Applications needing consistency must supply it themselves — a server-side session interface with synchronized backing-store access, as the note at `:141-146` directs.
