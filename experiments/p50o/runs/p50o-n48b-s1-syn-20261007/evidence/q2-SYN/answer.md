## Purpose of the flag

The flag is **`Blueprint._got_registered_once`**, and its purpose is to **freeze a blueprint's configuration once the blueprint has been registered on an application, so that setup changes made afterwards cannot silently apply to only some app instances.** It is a fail-loud guard against inconsistent configuration, not a state cache.

Concretely:

- The class the task calls the "blueprint collection class" is `Blueprint` in `src/flask/sansio/blueprints.py:119` — `class Blueprint(Scaffold)`, documented at line 120 as "a collection of routes and other app-related functions that can be registered on a real application later." No class literally named `Collection` exists; this docstring is the basis for the reading. The `Scaffold` base (`src/flask/sansio/scaffold.py:50`) defines the `setupmethod` decorator and the abstract `_check_setup_finished` hook but holds no registration flag itself. `_got_registered_once` appears in exactly three places in the tree, all in this class (`src/flask/sansio/blueprints.py:172`, `:214`, `:320`), so there is no competing owner.
- The flag is a class attribute defaulting to `False`: `_got_registered_once = False` (`src/flask/sansio/blueprints.py:172`).
- It flips to `True` inside `Blueprint.register` (`src/flask/sansio/blueprints.py:272`) at line 320, after the duplicate-name `ValueError` check and **before** `state = self.make_setup_state(...)` (line 321) and before the `for deferred in self.deferred_functions: deferred(state)` loop (lines 333-334). Because the flip precedes the deferred-function loop, the freeze covers not just user code after registration but the blueprint's own registration-time setup path.
- It becomes an error via `Blueprint._check_setup_finished` (`src/flask/sansio/blueprints.py:213-221`), which raises `AssertionError` when the flag is `True`. That method is not called directly by user code: `@setupmethod` (`src/flask/sansio/scaffold.py:42-49`) wraps every guarded method so that `self._check_setup_finished(f_name)` runs before the method body.
- The guarded methods on a blueprint are the ones decorated with `@setupmethod`: `record` (`:223`), `record_once` (`:232`), `register_blueprint` (`:255`), and the inherited-style setup methods in the `:412-624` range (`add_url_rule`, `route`, `before_request`, `after_request`, `errorhandler`, teardown hooks, `context_processor`, `url_value_preprocessor`, `url_defaults`, template filter/test/global). So calling `bp.route(...)` or nesting another blueprint via `bp.register_blueprint(...)` after registration fails, and the error names the offending method.

The rationale is stated in the code itself, at `src/flask/sansio/blueprints.py:215-220`:

> "The setup method '{f_name}' can no longer be called on the blueprint '{self.name}'. It has already been registered at least once, any changes will not be applied consistently. Make sure all imports, decorators, functions, etc. needed to set up the blueprint are done before registering it."

That message supplies both halves of the purpose: (1) the *why* — a change made after one registration would be picked up by apps that register the blueprint later but not by apps that already registered it, producing inconsistent configuration; (2) the *intended fix* — do all imports, decorators and function setup before registering. Since `Blueprint.register` can be called multiple times (once per app), "at least once" is accurate wording: the first call is what disables further setup.

The same pattern exists on the app class for a different lifecycle point, which confirms the design intent rather than contradicting it: `Flask._got_first_request` (`src/flask/sansio/app.py:411`, checked at `:414`) raises the matching assertion "It has already handled its first request, any changes will not be applied consistently." It is a separate flag with a separate trigger (first request, not first blueprint registration) and is even reset after `app.run()` returns (`src/flask/app.py:667`); no such reset exists for `_got_registered_once`.
