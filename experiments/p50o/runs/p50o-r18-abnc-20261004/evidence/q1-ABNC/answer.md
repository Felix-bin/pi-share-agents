# `ensure_ascii` and Unicode representation in JSON output

The control parameter is **`DefaultJSONProvider.ensure_ascii`**, declared as a class attribute with the value **`True`** at `src/flask/json/provider.py:144`. Its relationship to Unicode character representation is a **single text-level switch**: when `True`, non-ASCII code points in the serialized output are replaced by `\uXXXX` escape sequences (an ASCII-only string); when `False`, the literal Unicode characters are emitted into the serialized string. The provider's own docstring states the effect directly — *"Replace non-ASCII characters with escape sequences. This may be more compatible with some clients, but can be disabled for better performance and size"* (`provider.py:145-148`).

The switch is a **default, not a constraint**. In `DefaultJSONProvider.dumps` (`provider.py:167-179`) it is injected with `kwargs.setdefault("ensure_ascii", self.ensure_ascii)` (`provider.py:177`) before `return json.dumps(obj, **kwargs)`. Because it is `setdefault`, an explicit `ensure_ascii=` kwarg passed by a caller overrides the attribute value; the attribute only supplies the value when the caller is silent.

**Where the decision lands in the output path.** The escaping/raw choice is made inside stdlib `json.dumps`, i.e. while producing a `str`, *before* any `Response` exists. `DefaultJSONProvider.response` (`provider.py:~203-217`) then wraps that string: `self._app.response_class(f"{self.dumps(obj, **dump_args)}\n", mimetype=self.mimetype)`, with `mimetype = "application/json"` (`provider.py:163`). So the attribute determines the characters in the serialized text, and the response body inherits whichever form that text carried.

**Literal, text-level proof in the suite.** `tests/test_json.py:48-54` (`test_json_as_unicode`) parametrizes `[(True, '"\\u2603"'), (False, '"\u2603"')]` over the input `"\N{SNOWMAN}"`, sets `app.json.ensure_ascii = test_value`, and asserts `app.json.dumps("\N{SNOWMAN}") == expected`. I re-read those lines: `True` yields the six-character escape `\u2603`; `False` yields the literal snowman character. Corroboration extends beyond the provider object: `tests/test_testing.py:110-114` sets `app.json.ensure_ascii = False`, builds `EnvironBuilder(app, json="\u20ac")`, and asserts the *decoded* input stream equals `'"\u20ac"'`.

**Byte-level behavior (executor's live measurement, on this checkout).** With `PYTHONPATH` pinned to this tree's `src` (the venv's `flask.pth` editable install resolves outside the working tree, so an unpinned `import flask` is not this checkout), pytest 8.4.0 / Python 3.13.9 reported exit 0 with `3 passed` for the two named tests (param IDs `[True-"\\u2603"]` and `[False-"\u2603"]` displaying the expected strings). An independent one-liner showed: default `app.json.ensure_ascii = True`; `dumps(SNOWMAN)` → `'"\\u2603"'` (len 8); `ensure_ascii=False` → `'"\u2603"'` (len 3) with UTF-8 bytes `b'"\xe2\x98\x83"'`; and `Response.data` with `ensure_ascii=True` → `b'"\\u2603"\n'` versus `ensure_ascii=False` → `b'"\xe2\x98\x83"\n'`, both `content_type: application/json`. So the end-to-end consequence is: **ASCII-only body containing escape sequences** versus **a body containing the raw UTF-8 bytes of the Unicode characters**. This closes the byte-level gap the retriever had flagged as an inference.

**Reachability and lineage.** The parameter is not confined to the provider object: `flask.json.dumps` and `flask.json.jsonify` delegate to `current_app.json` (`src/flask/json/__init__.py:41` and `:170`), while the base `JSONProvider.dumps` raises `NotImplementedError` (`provider.py:~38`). Historically, `ensure_ascii` is the renamed successor of the removed `JSON_AS_ASCII` config key — deprecated in 2.2 and removed in 2.3 (`CHANGES.rst:152-153`, `:286-288`), added in 0.10 (`docs/config.rst:419`), with `docs/config.rst:441-443` recording that *"the default `app.json` provider has equivalent attributes instead."*

**Reported contradiction / correction between sources.** The retriever flagged that a plan paraphrase overstated `tests/test_testing.py:110-114` as asserting UTF-8 bytes `b'"\xe2\x82\xac"'`; the file actually asserts decode-equality (`eb.input_stream.read().decode("utf8") == '"\u20ac"'`), and the byte form is an inference. The executor's measurement later reproduced that byte form independently, so the two reports agree on the behavior while the retriever's textual correction stands.
