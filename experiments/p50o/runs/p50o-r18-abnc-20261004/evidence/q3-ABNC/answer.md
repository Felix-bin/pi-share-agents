## The modular registration architecture

**One shared, IO-free base holds the static-asset configuration; the two components reach it through parallel subclasses, and only the IO layer serves bytes.**

The shared base is `Scaffold` (`src/flask/sansio/scaffold.py:52`), documented in its own docstring as "Common behavior shared between `Flask` and `Blueprint`". It carries the static configuration as class defaults `_static_folder` / `_static_url_path` (`:72-73`), assigns them in `__init__` (`:87-88`), and exposes the derived state the rest of the framework reads: the `static_folder` property returning an absolute path or `None` (`:224-239`), `has_static_folder` as `self.static_folder is not None` (`:241-246`), and `static_url_path` defaulting to `f"/{os.path.basename(self.static_folder)}"` (`:249-267`). That code lives in `sansio/` because, per `src/flask/sansio/README.md` (whole file), that folder "cannot do any IO, nor be part of a likely IO path … cannot use the Flask globals" so alternative implementations can reuse it; consistently, `sansio/scaffold.py:11-19` imports neither `helpers.send_from_directory` nor `globals.current_app`.

The two components are siblings under that base, not one inside the other: `class App(Scaffold)` (`src/flask/sansio/app.py:59`) and `SansioBlueprint`, with the IO subclasses `class Flask(App)` (`src/flask/app.py:81`) and `class Blueprint(SansioBlueprint)` (`src/flask/blueprints.py:18`). `App.__init__` merely accepts and forwards `static_url_path` / `static_folder` to `super().__init__()` (`sansio/app.py:285-286, 297-298`) and registers no static route at all (no `add_url_rule` call in that file). The IO blueprint adds only a Click `AppGroup` plus the two send-file methods and forwards all ten arguments unchanged (`blueprints.py:23-56`), so constructor behaviour is identical between the two components.

**The registration chain** is: `App.register_blueprint` (`sansio/app.py:570-595`, inherited unchanged by `Flask`) → `blueprint.register(self, options)` → `Blueprint.register` (`sansio/blueprints.py:273`), which records `app.blueprints[name] = self`, builds a `BlueprintSetupState` (the temporary holder of `app`, `blueprint`, `options`, `first_registration`, `subdomain`, `url_prefix`, `name`/`name_prefix`, `:34-113`) and replays each deferred callback against it (`:329`). Nested blueprints defer via `self._blueprints.append((blueprint, options))` and are later registered in turn (`:256-270`, `:377`); self-registration is rejected with `ValueError("Cannot register a blueprint on itself")`. Lifecycle freezing is uniform too: `_check_setup_finished` is declared abstract at `scaffold.py:219-221`, implemented at `sansio/app.py:413`, and enforced by the shared `@setupmethod` decorator.

**Serving is separated from the framework core by two registration seams, with the view functions themselves outside the sansio layer.**

- App side, inside `Flask.__init__` (`src/flask/app.py:262-279`): `if self.has_static_folder:` then `self.add_url_rule(f"{self.static_url_path}/<path:filename>", endpoint="static", host=static_host, view_func=lambda **kw: self_ref().send_static_file(**kw))`, with the comment "Use a weakref to avoid creating a reference cycle between the app and the view function (see #3761)."
- Blueprint side, inside `Blueprint.register` (`src/flask/sansio/blueprints.py:323-327`): `if self.has_static_folder: state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")  # type: ignore[attr-defined]`.

The two seams differ observably: only the app's passes `static_host` and asserts `bool(static_host) == host_matching` (`app.py:268-271`); the app passes a weakref lambda, the blueprint a bound method. Endpoint naming also diverges because `BlueprintSetupState.add_url_rule` rewrites the endpoint to `f"{name_prefix}.{name}.{endpoint}"` (`sansio/blueprints.py:108-114`), so the app's route is `static` while the blueprint's is `blueprint_name.static` — matching `docs/blueprints.rst:191-223`, which also notes that a blueprint without a `url_prefix` cannot expose its static folder because "the application's `/static` route takes precedence".

**Where the plan's wording needs qualifying:** the *view function* is indeed IO-layer only — `send_static_file` is defined at `src/flask/blueprints.py:82` and referenced from sansio behind an explicit `# type: ignore[attr-defined]`. But the blueprint's static **route registration** is *not* in the IO layer; it sits in `sansio/blueprints.py:323-327`. So "static asset serving lives in the IO subclasses" is true of byte-serving and false of route bookkeeping. The sansio README forbids IO *execution* and Flask globals, and neither happens at registration time, so this is a documented seam rather than a violation — reported as observed code, not as a defect.

## How caching stays consistent across both components

Consistency is produced by **duplicating the same two method bodies on both components** and having both resolve through the *global* `current_app` config instead of per-object state:

- `Flask.get_send_file_max_age` (`app.py:281-306`) and `Blueprint.get_send_file_max_age` (`blueprints.py:55-79`) have identical bodies: `value = current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]`, `None` returned as `None` (meaning conditional requests rather than a timed cache), a `timedelta` converted via `int(value.total_seconds())`, otherwise the raw int.
- `Flask.send_static_file` (`app.py:308-327`) and `Blueprint.send_static_file` (`blueprints.py:82-101`) are likewise identical: `RuntimeError("'static_folder' must be set to serve static_files.")` when `has_static_folder` is false, then `max_age = self.get_send_file_max_age(filename)` with the comment "send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too" (`app.py:323-324`, `blueprints.py:97-98`), ending in `send_from_directory(t.cast(str, self.static_folder), filename, max_age=max_age)`.
- Because the read is `current_app.config[...]`, one app-level value governs both routes. The key is declared only in `Flask.default_config` (`app.py:201`, `"SEND_FILE_MAX_AGE_DEFAULT": None`) and is absent from `sansio/app.py`, so the knob belongs to the app/IO layer while the mechanism is copied onto both components.
- The plain `send_file` path is not bypassed either: `helpers.py:386-397` sets `kwargs["max_age"] = current_app.get_send_file_max_age` when no `max_age` was passed.

Tests and docs pin the contract: `tests/test_blueprints.py:195-207` sets `app.config["SEND_FILE_MAX_AGE_DEFAULT"] = 3600` and asserts the parsed `Cache-Control` max-age for `/admin/static/css/test.css`; `tests/test_blueprints.py:223-244` subclasses `flask.Blueprint`, overrides `get_send_file_max_age` to return `100`, and asserts the response honours `100` over config `3600`/`7200`. `docs/config.rst:250-262` states: "Override this value on a per-file basis using `Flask.get_send_file_max_age` on the application or blueprint."

The claim was also checked at runtime in this worktree (executor): with `static_folder=<repo>/tests/static` and one blueprint at `/bp`, `GET /static/index.html` and `GET /bp/static/index.html` both returned 200 with identical headers `public, max-age=2700` for a `timedelta(seconds=2700)` config and identical `public, max-age=3600` for the int control; bodies equal, length 22. So the consistent-caching property is observable, not merely structural.

## What it rests on, and what stays open

Rests on: `src/flask/sansio/scaffold.py`, `sansio/app.py`, `sansio/blueprints.py`, `sansio/README.md`, `src/flask/app.py`, `blueprints.py`, `helpers.py` (all line ranges above), `tests/test_blueprints.py:195-244`, `docs/config.rst:250-262`, `docs/blueprints.rst:191-223`, and the executor's single worktree run (exit 0, output quoted above).

Still open:
- **Identity of the two implementations is not established.** Both code copies and docstrings are byte-identical and the retriever found no test asserting the methods are equal — only tests and a runtime measurement asserting equal observed max-age behaviour. A shared 3600 value could mask a real divergence.
- **The docstring text is unexplained in one place.** "Note this is a duplicate of the same method in the Flask class" appears on the `Blueprint` copies (`blueprints.py:64, 88`) *and* on the `Flask` copies themselves (`app.py:290, 314`), where the self-reference is copied boilerplate; no comment or changelog entry read explains this.
- **Coverage limits.** Nothing was found outside `src/flask`, `tests`, `docs` (e.g. extension hooks re-implementing the same cache hook), and the runtime check covered only the two static routes — not plain `send_file` or a blueprint overriding `get_send_file_max_age` through a real request.
- **Environment caveat for reproduction.** The worktree's `.venv` editable install resolves `flask` to a different checkout; measurements are only valid after forcing this worktree's `src` onto `sys.path` (as the executor did).
- The `flask_mut2_i417ar2x/` artifact in the working directory was treated as out of scope by the plan and nothing was verified about it.
