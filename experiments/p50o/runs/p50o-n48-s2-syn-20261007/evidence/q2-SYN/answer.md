## It inherits because async support in this project is an adapter applied inside the one synchronous dispatch chain, not a second dispatch path

**The class the question names is a test fixture, and the library ships no async view class at all.** A worktree-wide search for `AsyncMethodView|AsyncView` matches only `tests/test_async.py:22` (`class AsyncView(View)`), `:30` (`class AsyncMethodView(MethodView)`), `:75` and `:76`. `src/flask/views.py` imports neither `asyncio` nor `asgiref` nor `iscoroutinefunction`; the library contains exactly `View` (`views.py:16`) and `MethodView(View)` (`views.py:138`). So "the asynchronous HTTP method view class" is `AsyncMethodView`, a test-defined subclass, sitting on the library's decision to give the existing sync classes async capability instead of adding new ones — `CHANGES.rst:473`: *"Support View and MethodView instances with async handlers. :issue:`4112`"*.

**The inheritance works because the two `ensure_sync` call sites compose, so dispatch needs no modification.** `View.as_view`'s generated closure calls `current_app.ensure_sync(self.dispatch_request)` — `views.py:110` when `init_every_request` is true, `:116` otherwise. For `AsyncMethodView`, `self.dispatch_request` is the inherited **sync** `MethodView.dispatch_request`, so `iscoroutinefunction` is false at that level and `ensure_sync` returns it unchanged (`app.py:975`). The inherited dispatch (`views.py:182-191`) then does its `getattr(self, request.method.lower())`, HEAD→GET fallback and `assert`, and calls `current_app.ensure_sync(meth)(**kwargs)` at `:191`, where `meth` is the bound `async def get`/`post`. Outer call passes a sync callable through, inner call wraps the coroutine. Both shapes are covered: `AsyncView` (async `dispatch_request`, `tests/test_async.py:22`) is handled by the outer hook alone, `AsyncMethodView` by the inner one, with one hook and one hierarchy.

**There is no independent async dispatch to implement, because `ensure_sync` is the framework's only coroutine-detection point and it is applied app-wide.** `Flask.ensure_sync` (`app.py:965-977`) bodies down to `if iscoroutinefunction(func): return self.async_to_sync(func)`, and `iscoroutinefunction` appears in `src/` only at `app.py:9` (import) and `app.py:975` (the check). `Flask.async_to_sync` (`app.py:980-1001`) lazily imports `asgiref.sync.async_to_sync` and raises `RuntimeError("Install Flask with the 'async' extra in order to use async views.")` when absent; dependency at `pyproject.toml:33` (`async = ["asgiref>=3.2"]`), test guard at `tests/test_async.py:11`. The same hook is used for view functions (`app.py:902`), before/after request (`:1291`, `:1314`, `:1319`), teardown (`:1356`, `:1382`), error handlers (`:777`, `:809`, `:860`), signals via `_async_wrapper` (`:840`, `:914`, `:943`), template rendering (`templating.py:129-176`) and context push/teardown (`ctx.py:191`, `:254`, `:272`). A forked async dispatch inside a view subclass would sit outside that hook — it would have to re-create the coroutine handling and stay consistent with every app-level hook that funnels through the same method. The architectural reason the chain must stay synchronous at its entry is stated in `docs/design.rst:187-203`: Flask runs coroutines on a worker thread rather than a main-thread event loop *"necessary for Flask to remain backwards compatible with extensions and code built before async was introduced"*, and class-based views are registered through the same WSGI-facing sync view function.

**Inheriting is also what buys automatic HTTP-method registration — the concrete behavioural payoff.** `MethodView.__init_subclass__` (`views.py:165-180`) collects `methods` from bases and, over `http_method_funcs` (`views.py:11-13` = `get, post, head, options, delete, put, trace, patch`), adds `key.upper()` when `hasattr(cls, key)`; `hasattr` is true for `async def get`. Execution confirmed it: `methods auto-detected: ['GET', 'POST']` and `registered methods on rule (no methods=): ['GET', 'HEAD', 'OPTIONS', 'POST']`, even though the route is registered without `methods=` (`tests/test_async.py:76`). An asynchronous class implemented independently of `MethodView` and its `__init_subclass__` would fall back to the default `GET, HEAD, OPTIONS`, would not answer `POST`, and would have had to re-implement the `getattr`/HEAD-fallback/`assert` mapping as well. Inheritance additionally carries per-request instantiation, `decorators`, `provide_automatic_options` and `view.methods` propagation through `as_view` (`views.py:86-135`).

**This is the project's documented design, not an accident.** `docs/async-await.rst:20-24`: *"Pluggable class-based views also support handlers that are implemented as coroutines. This applies to the `View.dispatch_request` method in views that inherit from the `flask.views.View` class, as well as all the HTTP method handlers in views that inherit from the `flask.views.MethodView` class."* Inheritance is the stated mechanism; no async view class is documented or offered.

**Verified behaviourally:** `PYTHONPATH=src .venv/Scripts/python.exe -m pytest tests/test_async.py::test_async_route -v` → exit status 0, `5 passed in 0.15s`, covering `/`, `/home`, `/bp/`, `/view`, `/methodview`; the `/view` and `/methodview` cases assert `b"POST"` (`tests/test_async.py:79-86`). `PYTHONPATH=src` is required: the venv carries an editable `flask.pth` that resolves `import flask` to a non-worktree path.

## What remains open

- **No explicit written justification for choosing inheritance over independent async dispatch exists in the worktree.** Issue `4112` is only cited by `CHANGES.rst:473`; its discussion and any design note or rejected-alternative record are not present. The causal account above is read off the code plus the two documentation statements — it establishes the mechanism and the documented capability, not a recorded deliberation.
- **Idempotence of a double `ensure_sync` is only exercised for the two shapes the tests hit** (sync `dispatch_request` outer, async handler inner). No test in the worktree calls `ensure_sync(ensure_sync(f))` for other callable shapes, so the general claim is limited to those shapes named in the docstring.
- **Documentation gap, not a design statement:** `docs/views.rst`, the class-based-view guide including its "Method Dispatching and APIs" section, contains no mention of `async`, `await` or `ensure_sync` (grep: no matches). The inheritance-based async story lives only in `docs/async-await.rst`.
- **Whether the library should ever ship a dedicated async view class is not answered by any artifact in the worktree** — nothing here bears on that design question either way.
