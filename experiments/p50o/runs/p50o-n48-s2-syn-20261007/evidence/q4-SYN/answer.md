## Why `open_resource` is read-only

**Short answer: the repository never states a reason.** No docstring paragraph, comment, changelog entry, or commit message in this worktree explains *why* the mode allowlist exists. The rationale has to be reconstructed from the design decision the restriction shipped with — and that reconstruction, plus the one argument usually assumed (safety/immutability), is inference rather than in-repo text.

The method is `Flask.open_resource` (`src/flask/app.py:330-361`); `Blueprint.open_resource` (`src/flask/blueprints.py:104-126`) is the blueprint-relative equivalent with the identical guard, so both are the same answer.

### What the code actually asserts

- The guard is the allowlist itself: `if mode not in {"r", "rt", "rb"}: raise ValueError("Resources can only be opened for reading.")` — `src/flask/app.py:353-354`, repeated verbatim at `src/flask/blueprints.py:120-121`. It is the *only* validation of `mode`; the path is then built as a raw `os.path.join(self.root_path, resource)` (`app.py:356`, `blueprints.py:123`) with no normalization or sandboxing.
- The docstrings state the restriction as the method's contract, not with a reason: `:param mode: Open the file in this mode. Only reading is supported, valid values are ``"r"`` (or ``"rt"``) and ``"rb"``.` (`app.py:345-346`; `blueprints.py:112-113`).
- A deliberate contrast sits immediately below in the same class: `Flask.open_instance_resource` (`app.py:363-386`) has **no** mode allowlist and its docstring says "Unlike :meth:`open_resource`, files in the instance folder can be opened for writing." So read-only is a property of *this* resource location, not of Flask's file-opening API in general.

### The reconstruction the in-repo evidence supports

1. **`root_path` points at the shipped package tree, not at writable runtime space.** It is derived from the app's import name (`src/flask/sansio/scaffold.py:95-100`: `root_path = get_root_path(self.import_name)`, commented "Absolute path to the package on the filesystem. Used to look up resources contained in the package."), i.e. the application's own installed source/package directory.
2. **Flask splits files by mutability, and the restriction is the read side of that split.** The 0.8 changelog entry (`CHANGES.rst:1352-1357`) introduces the two paths: a root path "where the resources and modules are located" and an instance path "which is the designated place to drop files that are modified at runtime (uploads etc.) … outside version control". `docs/config.rst:773-776` repeats it: the instance folder "is designed to not be under version control and be deployment specific. It's the perfect place to drop things that either change at runtime or configuration files." Under that split, reading shipped package data goes through `open_resource`; anything writable goes through `open_instance_resource`. The allowlist is what enforces the boundary in code.
3. **The two landed as one change.** `git show 187cb80d -- flask/helpers.py` adds the mode parameter *and* the guard `if mode not in ('r', 'rb'): raise ValueError('Resources can only be opened for reading')` to `_PackageBoundObject.open_resource`, and the same commit adds `Flask.open_instance_resource` ("Instance resources can also be opened for writing") and the `docs/config.rst` instance-folders section. Commit date 2011-08-10, subject "Documented instance root". So the guard was not a later hardening pass on top of an existing write-capable method; it was introduced simultaneously with the writable alternative. (Search hits: `187cb80d` oldest, then `9f7c602a` 2021 and `0ec7f713` 2023, which only moved/split the code.)
4. **The rule was never relaxed after that.** `CHANGES.rst:686-687` (issue 3163) records that `"rt"` was accepted but "still does the same thing as `"r"`", and the 3.1 `encoding` addition (`CHANGES.rst:35-37`) left the allowlist untouched.
5. **The originating commit message is empty** (`git show -s --format='%b' 187cb80d` prints nothing), so git history supplies the *what* and *when*, not the *why*. No `CHANGES` entry documents the introduction of the allowlist either.

The behavioural contract backs the scope of the rule: `tests/test_helpers.py:338-343` opens `static/index.html` in each of `r`/`rb`/`rt`; `:346-351` asserts `ValueError` for `w`/`x`/`a`/**`r+`**. The rejection of `"r+"` — which does not truncate — shows the intent is "no write capability at all", not merely "no destructive mode". The test asserts only the exception type, not the message text. Executed check: `.venv/Scripts/python.exe -m pytest tests/test_helpers.py -k open_resource -q` → **9 passed, 25 deselected**, and a direct probe against this worktree's source returned `FileNotFoundError` for `r`/`rb`/`rt` (guard not triggered) and `ValueError('Resources can only be opened for reading.')` — character-for-character the literal at `app.py:354` — for `w`/`x`/`a`/`r+`.

### What is *not* established

- **No explicit stated reason exists in this worktree.** The security/immutability argument — that allowing `"w"`/`"a"`/`"x"`/`"r+"` would permit writing into, or via `..` in `resource` outside, the installed package directory (which may be read-only at deployment, e.g. inside site-packages) — is a plausible inference from the raw `os.path.join` plus the guard being the sole validation, but no file in the repository states it. The retriever labelled it inference and the git-history check corroborates that label by finding an empty commit body. Treat the *design split* (package vs. instance) as evidence-backed and the *safety* motive as unverified.
- The first pytest invocation as literally written (`python -m pytest …`) fails here with `ModuleNotFoundError: No module named 'flask'` (system interpreter 3.14.0); the passing numbers come from `.venv` (Python 3.13.9, pytest 8.4.0), whose `flask.pth` by default loads a **byte-identical copy of `src/flask` from a different worktree path** (verified: only an extra `__pycache__` .pyc differs; `src/flask/app.py` sha256 `5c6aa015…20a7` in both). Re-running with `PYTHONPATH="$PWD/src"` forces this worktree's source and also passes, so the result is not affected — but the default run was not importing from this directory.

### Part of the task answered vs. open

- **Answered:** which method (both `Flask.open_resource` and `Blueprint.open_resource`), what the restriction is, and what in-repo evidence implies about its purpose (enforcing the root_path = shipped/readable vs. instance_path = writable split; write access deliberately routed to `open_instance_resource`, introduced in the same commit `187cb80d`).
- **Open / legacy-carried:** an explicit, quotable rationale sentence. None exists in the repository, so any "because it is a security measure" answer goes beyond the evidence available here.
