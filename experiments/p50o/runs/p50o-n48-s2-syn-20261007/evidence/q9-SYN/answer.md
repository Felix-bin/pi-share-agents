# Why repeated calls to `get_signing_serializer` cost, and how far "bottleneck under high concurrency" actually holds

The method is `SecureCookieSessionInterface.get_signing_serializer` (`src/flask/sessions.py:317`), the default session persistence handler being `SecureCookieSessionInterface` (`src/flask/sessions.py:298`). The reason repetition costs anything at all is that the method is a pure factory with **no memoization**: `grep` for `lru_cache|cached_property|functools|_cache` in `src/flask/sessions.py` returns nothing, and the method's only early exit is `if not app.secret_key: return None` (`:318`). Its inputs are app-level constants (`app.secret_key`, `SECRET_KEY_FALLBACKS`, `self.salt`, `self.key_derivation`, `self.digest_method`), and it ends by returning a brand-new `URLSafeTimedSerializer(keys, salt=self.salt, serializer=self.serializer, signer_kwargs={...})` at `:327`. So an object that is invariant for the life of an app is rebuilt on every use instead of being built once.

Three pieces of evidence turn "rebuilt every use" into a load-proportional cost:

1. **It sits on the critical path of every request.** The exhaustive call sites in production are `open_session` (`sessions.py:338`) and `save_session` (`sessions.py:387`); `open_session` is invoked once per request-context push (`src/flask/ctx.py:384-386`) and `save_session` once per response (`src/flask/app.py:1321-1322`). The executor's monkeypatched counter on the real test client confirms the frequency: **1 construction** for a request that does not modify the session, **2 constructions** for a mutating write and for a permanent-session read the refresh path re-cookies (`SESSION_REFRESH_EACH_REQUEST` default true). The skip guards that reduce the count are real but narrow — `save_session` returns before `:387` only when `if not session:` or `not self.should_set_cookie(...)` (`sessions.py:365-379`).
2. **Each call is expensive relative to what it produces.** Measured min/median: fresh build 5037/5332 ns versus 18/19 ns to return an already-built instance — roughly **285x**. A construction is ~9.0% of the session's own `dumps`+`loads` cycle (52.5/59.1 µs) and ~2.9% of a `/mutate` request through the test client (327.6/368.8 µs).
3. **The dominant part of that build is one probe serialization.** itsdangerous' `Serializer.__init__` calls `self.is_text_serializer = is_text_serializer(serializer)` (`.venv/Lib/site-packages/itsdangerous/serializer.py:222`), whose body is `return isinstance(serializer.dumps({}), str)` (`serializer.py:41`). Flask passes `serializer=self.serializer` = `session_json_serializer`, a `TaggedJSONSerializer` created once at import (`sessions.py:287`), so every construction actually serializes `{}` through the tag serializer and `json.dumps`. The executor's attribution run isolates it: constructing with `session_json_serializer` costs 4840 ns median versus 1808 ns with `serializer=json`, i.e. **~3.0 µs of the ~4.8 µs build is the probe**. That is also why the once-per-import `session_json_serializer` is not itself the per-request cost — the cost is the wrapper that re-probes it.

Under concurrency the multiplication is straightforward and was measured, not inferred: 400 mutating requests across 8 threads produced 800 constructions (2.00/request), the same ratio as 50 requests in 1 thread (100 constructions). Nothing is shared or amortized between requests or threads, so the fixed per-request build work is paid independently by every in-flight request, and aggregate spend grows **linearly with request rate** — there is no threshold or contention cliff, and no lock is taken, so the pattern is "repeated identical work multiplied by concurrency", not superlinear degradation. The kernel of the task's premise is therefore right in kind: the repetition is systematic, avoidable, on the critical path, and it scales with concurrency.

What is **not** established is the strength of the word "bottleneck". The absolute size is small: ~10.6 µs of avoidable work per mutating request, ~2.9% of a test-client request. The same session path spends more on the work that cannot be avoided (`one.dumps` 22.0/27.6 µs, full round trip 52.5/59.1 µs), and no production-server latency/throughput measurement, no ranking of this cost against signing/hashing or framework overhead, and no async or multi-process model was exercised. So "the serializer rebuild is the bottleneck under high concurrency" is **not supported**; "an uncached, invariant-value rebuild is paid on every request and multiplies with concurrency" is supported by code and measurement.

One attribution in the underlying evidence needs correcting, and it matters for what caching could recover. The retriever placed `Signer.__init__`/`HMACAlgorithm` setup inside the per-call construction cost. In this venv's itsdangerous 2.2.0, construction (`Serializer.__init__`, `serializer.py:192`) only copies the key list (`_make_keys_list`, `:210`), converts `salt` (`:213`), runs the probe (`:222`) and copies `default_fallback_signers` (`:231-232`); the signer is built by `self.make_signer(salt)` inside `Serializer.dumps` (`serializer.py:311-316`), i.e. per sign/verify and unavoidable even with a cached serializer. Only the wrapper build, the key-list copy and dict/list copies, and the ~3 µs probe are recoverable by caching. Also, the retriever's itsdangerous line numbers (`:265`/`:271-274`/`:279`/`:187`) do not match this worktree's copy; the verified positions are the ones above. Its signer.py numbers (`:67-73`, `:129`, `:56`) do match, and `url_safe.py`/`timed.py` do define no `__init__`, so construction does resolve to `Serializer.__init__`.
