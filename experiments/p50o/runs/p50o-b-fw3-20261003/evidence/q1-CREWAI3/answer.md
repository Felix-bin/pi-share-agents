## Answer

**Relationship: `DefaultJSONProvider.ensure_ascii` is the control parameter, and it determines whether non-ASCII characters appear in the serialized JSON text as `\uXXXX` escape sequences or as literal Unicode characters.**

Detail, with sources:

- **The parameter.** `ensure_ascii = True` is a class attribute of `DefaultJSONProvider` (`src/flask/json/provider.py:144-148`), documented as: "Replace non-ASCII characters with escape sequences. This may be more compatible with some clients, but can be disabled for better performance and size." It defaults to `True`. It is **not** declared on the base `JSONProvider`; the base class's `dumps` raises `NotImplementedError`, so the attribute is a `DefaultJSONProvider` contract only.
- **How it reaches the serializer.** `DefaultJSONProvider.dumps` forwards it: `kwargs.setdefault("ensure_ascii", self.ensure_ascii)` (`src/flask/json/provider.py:177`, in `dumps` at `:166-179`), which then calls `json.dumps(obj, **kwargs)`. So the attribute is a default for `json.dumps`'s own `ensure_ascii` parameter. Because of `setdefault`, an explicit per-call `ensure_ascii=` kwarg **overrides** the class attribute (code-level fact, confirmed by probe).
- **The observable effect.** With `True`, a non-ASCII character in serialized output is replaced by its `\uXXXX` escape sequence, leaving ASCII-only JSON text; with `False`, the literal Unicode character is emitted into the returned `str`. The in-tree demonstration is `tests/test_json.py:48-54` (`test_json_as_unicode`): `app.json.ensure_ascii = test_value; rv = app.json.dumps("\N{SNOWMAN}")` asserting `'"\\u2603"'` for `True` and `'"☃"'` for `False`. That parametrized test **passes** (exit 0, with `test_environbuilder_json_dumps`; and the whole `tests/test_json.py` passes).
- **Representation only, not the decoded value.** Both forms decode to the same value: `loads` never consults `ensure_ascii` — `loads` is a bare `json.loads(s, **kwargs)` with no `setdefault` (`src/flask/json/provider.py:181-187`), and the module-level `flask.json.loads`/`load` wrappers likewise don't set it (`src/flask/json/__init__.py:102-105`, `:132-135`). A probe confirmed round-tripping is equal for both forms (`loads` of escaped text and of literal text both give `☃`).
- **It is serialization-only, and the only in-tree consumer.** Grep over the worktree finds `ensure_ascii` read in exactly one place in `src/flask`: `provider.py:177`; the other hits are the declaration (`:144`), a docstring mention (`:171`), two tests, and vendored packages (`itsdangerous`, `_pytest`). No `loads` path and no second in-tree serialization path consumes it.
- **It propagates to HTTP responses.** `response()` builds its body via `f"{self.dumps(obj, **dump_args)}\n"` (`src/flask/json/provider.py:213-214`); `dump_args` carries only `indent`/`separators` (`:206-211`). So response JSON inherits the attribute, reached from `src/flask/app.py:1230-1231` (`rv = self.json.response(rv)` for dict/list returns). The base-class `JSONProvider.response` also calls `self.dumps(obj)` (`:105`), so both implementations share the path. Probe: `response()` with attribute `True` → `'{"\\u2603":"\\u2603"}\n'`, with `False` → `'{"☃":"☃"}\n'`; both decode equal, both `Content-Type: application/json` with no charset parameter.
- **Other paths that inherit it.** `app.json` is a `DefaultJSONProvider` by default (`src/flask/sansio/app.py:230`, `:329`; reassignable at `:334-336`). Under an app context, the legacy module-level `flask.json.dumps` delegates to `current_app.json.dumps` (`src/flask/json/__init__.py:40-41`), and the Jinja `json.dumps_function` policy is bound to `self.json.dumps` (`src/flask/app.py:422`) — so the `|tojson` filter inherits the attribute (probe: `tojson` with attribute `False` → `'"☃"'`). `tests/test_testing.py:110-114` (with the bridge at `src/flask/testing.py:88-94`) shows the setting also reaching test-client request bodies.
- **The docstring's compatibility/performance wording is prose only.** No benchmark, test, or comment in the worktree measures it. It must be attributed to the docstring (`provider.py:145-147`), not asserted as established fact.

## On the ambiguous term "Unicode character representation"

The plan resolves it by default reading: it means the **escaped-ASCII vs literal-Unicode textual form of non-ASCII characters in the serialized output string** — evidenced by the attribute's own docstring ("Replace non-ASCII characters with escape sequences") and by the snowman assertion. This is the reading the evidence supports best, and it is the only reading supported by anything in the tree: grep for `Unicode` in `src/` returns zero hits, `as_unicode` returns only the test's function name (`tests/test_json.py:51`), and `charset` returns no hits in `src/`.

The alternative reading: if "representation" meant the response's **byte encoding / charset** on the wire, `ensure_ascii` would be irrelevant — it changes only which characters appear in the JSON text, and both forms are UTF-8-encodable. Nothing in the worktree ties `ensure_ascii` to `content_type` or charset; probe shows `application/json` with no charset in both settings. (That is an observation of absence, not proof of the phrase's original intent — the phrase appears nowhere in the tree.)
