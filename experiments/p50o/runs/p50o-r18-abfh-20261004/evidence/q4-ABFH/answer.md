# What the dual inheritance reflects architecturally

`class UnexpectedUnicodeError(AssertionError, UnicodeError)` (`src/flask/debughelpers.py:17-20`, docstring: "Raised in places where we want some better error reporting for unexpected unicode or binary data") encodes four decisions about where debug reporting sits relative to Flask's other layers.

**1. Widen the original error family, don't replace it.** `UnicodeError` is kept as a base, so any existing `except UnicodeError` site still catches the debug replacement; `AssertionError` is *added* as a second classification. This is the module's uniform pattern, not a one-off: `DebugFilesKeyError(KeyError, AssertionError)` (`debughelpers.py:23`) and `FormDataRoutingRedirect(AssertionError)` (`:50`). The intended use is visible in the one exercised sibling: `debughelpers.py:88-99` wraps `request.files.__getitem__` and, inside `except KeyError as e:`, raises `DebugFilesKeyError(request, key).with_traceback(e.__traceback__) from None` — the debug helper is substituted for the underlying error *at the point of failure*, while remaining an instance of the underlying error's type. Applied to the unicode case, the decision is: a place that catches an encoding problem and wants a better message swaps in a class that is still a `UnicodeError`.

**2. `AssertionError` is the marker that separates developer/validation failures from protocol failures.** In this tree `raise AssertionError` appears at `ctx.py:268`, `ctx.py:429`, `sansio/app.py:415` (`_check_setup_finished`), `sansio/app.py:657`, `sansio/blueprints.py:215`, plus bare `assert` at `sansio/scaffold.py:705` and `views.py:190` — all framework-core programming/setup mistakes, none an `HTTPException`. The second base therefore places the unicode debug helper on the validation/programming side, even though its subject matter (undecodable data) is an encoding issue: origin classification (`UnicodeError`) is preserved for the data layer, reporting classification (`AssertionError`) marks it as a developer-facing failure.

**3. Debug reporting is a layer injected from the layer where the problem occurs, only under debug.** `app.py:495` gates on `not self.debug` and raises `FormDataRoutingRedirect` at `:504` (imported at `:502`); `wrappers.py:198-209` installs `attach_enctype_error_multidict` only when `current_app.debug`; `wrappers.py:212-219` re-raises `BadRequest` only in debug. So `debughelpers` is not a global exception layer — the app/request-parsing layers opt into it when debug is on, and each helper's bases determine which handlers still catch it. The dual base is consistent with a helper meant to be raised from such a debug-gated request/parsing site and still be caught by normal encoding-error handling.

**4. It does *not* create an HTTP-vs-non-HTTP split — the separation is elsewhere.** Neither base is an `HTTPException` (executor's in-worktree runtime check: `issubclass(U, AssertionError/UnicodeError/ValueError/Exception) = True`, `HTTPException = False`; MRO `[UnexpectedUnicodeError, AssertionError, UnicodeError, ValueError, Exception, BaseException, object]`, `AssertionError` first). At dispatch (`app.py:779 handle_user_exception`, `isinstance(e, HTTPException)` at `:801`) only HTTP exceptions branch to `handle_http_exception`; everything else goes to a registered handler or re-raises, and `handle_exception` (`:811`) re-raises under `PROPAGATE_EXCEPTIONS` (default `self.testing or self.debug`, `:843-844`) or returns `InternalServerError(original_exception=e)`. Either base lands in that same non-HTTP, 500-class/debug-surfaced path. The separation the dual base expresses is **encoding-error identity vs. validation/debug classification**, not "HTTP response vs. server error"; the response-vs-exception split is performed by the `HTTPException` check, which this class deliberately stays outside of.

**Inference, explicitly not observed.** The consistent reading of points 1–3 is that a debug reporter for undecodable data must remain catchable through the ordinary `UnicodeError` path so a caller's generic `except UnicodeError` cannot silently drop the debug report, while Flask's propagate/500 path treats it as an assertion-class debug failure. That reading fits the module pattern but is stated in no docstring, changelog or test in this worktree.

**What the class does *not* currently demonstrate.** The dual-inheritance decision is a preserved hook, not an exercised behaviour: exactly **1 source reference** (the definition at `debughelpers.py:17`), **0 raise sites**, 0 tests, 0 docs and 0 `CHANGES.rst` references, 0 dynamic/indirect references, and no export from `flask/__init__.py`. The only `debughelpers` consumers are `app.py:502`, `templating.py:83`, `wrappers.py:208`. There is also no `except AssertionError` and no `except UnicodeError` anywhere in `src/flask`, so no current catch site in this tree depends on either base of this class. Who consumes the widened type is therefore not established — the architectural intent above is read off the declaration plus the sibling pattern, not off runtime behaviour.
