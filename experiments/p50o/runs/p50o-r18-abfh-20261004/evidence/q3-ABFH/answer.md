## Static-asset serving is split across two components that share one base and duplicate one caching contract

In this worktree (stock Flask 3.2.0.dev per `pyproject.toml:2-3`), the module that separates static serving from the main app framework is the **`Blueprint`**. Both `Flask` and `Blueprint` inherit a common base, **`Scaffold`**, which holds all the static configuration; each then registers its own `"static"` route and serves it with its own copy of the same view + cache hook. The architecture has four parts:

**1. The shared base hoists the static configuration out of the app.** `class Scaffold:` (`src/flask/sansio/scaffold.py:52`) is documented as *"Common behavior shared between :class:`~flask.Flask` and :class:`~flask.blueprints.Blueprint`"* (lines 53-54). Its `__init__` stores `static_folder` / `static_url_path` (`scaffold.py:78-88`) with class-level defaults at `72-73`, and exposes `static_folder` (`224-238`, joins `root_path`), `has_static_folder` (`241-246`, `return self.static_folder is not None`), and `static_url_path` (`249-269`, falling back to `f"/{basename}"`). The MRO confirms both components sit on it: `Flask(App)` (`app.py:81`) with `App(Scaffold)` (`sansio/app.py:59`), and `Blueprint(SansioBlueprint)` (`blueprints.py:18`) with `Blueprint(Scaffold)` (`sansio/blueprints.py:119`). So the *inputs* to static serving are defined once for both.

**2. The app registers its static route at construction time.** Inside `Flask.__init__` (`app.py:225`), at `app.py:257-275`, `if self.has_static_folder:` it calls `self.add_url_rule(f"{self.static_url_path}/<path:filename>", endpoint="static", host=static_host, view_func=lambda **kw: self_ref().send_static_file(**kw))`. The comment at `257-261` records the deliberate choice not to check that the folder exists (it may be created while the server runs).

**3. The blueprint registers the same route lazily, at registration time.** Inside `Blueprint.register` (`sansio/blueprints.py:273`), at `319-324`, after `app.blueprints[name] = self` and `state = self.make_setup_state(...)`: `if self.has_static_folder: state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")`. `BlueprintSetupState.add_url_rule` (`104-122`) applies the blueprint's `url_prefix` and namespaces the endpoint to `f"{name_prefix}.{name}.{endpoint}"` — which is why the route surfaces as `/admin/static/...` with endpoint `admin.static`. This is the modular move: a self-contained component carries its own static folder and contributes its own route into the app at registration, rather than the app hosting it.

**4. Consistency is preserved by two identical implementations of the cache contract rather than by inheritance.** There are exactly two definitions each of `send_static_file` and `get_send_file_max_age`, and none under `sansio/`: `app.py:281`, `app.py:308`, `blueprints.py:55`, `blueprints.py:82`. Both `get_send_file_max_age` bodies read `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]` (default `None` at `app.py:201`; `None`→`None`, `timedelta`→`int(total_seconds())`, else the value). Both `send_static_file` bodies raise `RuntimeError` without a static folder, then take `max_age = self.get_send_file_max_age(filename)` and pass it into `send_from_directory`. The **byte-level diff run by the executor confirms the two pairs are `IDENTICAL`, not merely similar**. The explicit `max_age=` is what makes the two agree: `helpers.py:387-389` (`_prepare_send_file_kwargs`) would otherwise default `max_age` to the *app's* `get_send_file_max_age`, and `helpers.py:566-567` `send_from_directory` delegates to Werkzeug with those kwargs; the blueprint resolves its own `max_age` first, so its static responses honour the same `SEND_FILE_MAX_AGE_DEFAULT` as the app's. The in-tree tests assert this directly — `tests/test_blueprints.py:195-206` (`test_templates_and_static`, asserting `cc.max_age` for `GET /admin/static/css/test.css`) and `tests/test_helpers.py:50-73` (`TestSendfile::test_static_file`).

**A second reading is also evidenced: the no-IO `sansio/` layer vs the runtime layer.** `src/flask/sansio/README.md:1-6` states that folder *"cannot do any IO, nor be part of a likely IO path … cannot use the Flask globals."* Consistent with that, the blueprint's *registration* logic lives in `sansio/blueprints.py` but the *view that serves bytes* lives in the runtime `src/flask/blueprints.py:82-107` (it imports `send_from_directory` / `current_app`), and the sansio `register()` reaches it only through `self.send_static_file  # type: ignore[attr-defined]`. The app likewise imports `from .helpers import send_from_directory` (`app.py:43`) while `App`/`Scaffold` do not. The task weights "across both components" toward the Flask/Blueprint pair, so the answer above is given under that reading; the layer reading is a real second sense of "separates static serving from the main framework" and the evidence does not rank it away.
