# Purpose of `Blueprint._got_registered_once`

**The "blueprint collection class" is `class Blueprint(Scaffold)`** — its docstring calls it "a collection of routes and other app-related functions that can be registered on a real application later" (`src/flask/sansio/blueprints.py:118-121`) — and the registration-tracking flag on it is `_got_registered_once` (`blueprints.py:172`).

**Its purpose: it is a one-way, per-instance latch whose only job is to let the blueprint refuse further setup work once it has been registered, so that late setup fails loudly instead of being applied inconsistently.** The flag records "this blueprint has been registered at least once" — not "this blueprint is fully configured". It is set unconditionally at `blueprints.py:320` inside `Blueprint.register`, immediately after `app.blueprints[name] = self` and before the setup state is built, the blueprint funcs are merged (line 332), and the recorded deferred callbacks are drained (`for deferred in self.deferred_functions: deferred(state)`, line 334). That drain is exactly why a late change is unsafe: the deferred functions are a one-shot list consumed at registration, so a route or callback added afterwards cannot reach the application state that was already built — it would only ever take effect on some *later* registration, i.e. the blueprint's behaviour would differ between apps. The flag makes that situation impossible to enter silently.

**How it is enforced.** `Blueprint._check_setup_finished` (`blueprints.py:213-221`) reads the flag and raises `AssertionError` with the message: "The setup method '…' can no longer be called on the blueprint '…'. It has already been registered at least once, any changes will not be applied consistently. Make sure all imports, decorators, functions, etc. needed to set up the blueprint are done before registering it." Every setup entry point reaches that check through the `setupmethod` decorator's trampoline (`src/flask/sansio/scaffold.py:42-49`: `self._check_setup_finished(f_name)` before calling the wrapped function). The guarded blueprint methods include `record`, `record_once`, `register_blueprint`, `add_url_rule`, the `app_template_filter`/`test`/`global` pair (decorator and `add_*` form), `before_app_request`, `after_app_request`, `teardown_app_request`, `app_context_processor`, `app_errorhandler`, `app_url_value_preprocessor`, `app_url_defaults`, plus the inherited route/`before_request`/`after_request`/`errorhandler` family in `scaffold.py`.

**Behaviour was confirmed at runtime, not just by reading.** With `PYTHONPATH=src` on the tree's Python 3.14.0, registering `Blueprint("bp")` on a `Flask` app flips the flag `False → True`; calling `add_url_rule` or `before_request` after that raises the assertion above, and a nested `register_blueprint` after registration raises it through the same trampoline. The latch lands in the instance `__dict__` while `Blueprint._got_registered_once` (the class attribute) stays `False`, and a fresh blueprint reads `False` — consistent with the flag being per-blueprint-instance state, with the class attribute only supplying the default. Crucially, **the same blueprint still registers successfully on a second application**: the guard message says "at least once", and the code never forbids re-registration. So the flag is a *consistency* guard, not a lifetime or single-use guard.

**Why "consistency" is the stated reason, in the project's own words.** The blueprint message mirrors the application-side check, which uses a different flag, `App._got_first_request` (`src/flask/sansio/app.py:409-421`), with parallel wording: "It has already handled its first request, any changes will not be applied consistently." The rationale prose is in `docs/lifecycle.rst:33-48`: setup must be complete before serving because WSGI servers split work across workers or machines, and a change made in one worker cannot be made consistent with the others; `docs/lifecycle.rst:50-56` adds that out-of-order setup "is not possible for Flask to detect all cases" and warns against mutating `Flask`/`Blueprint` objects from view functions.

**History of the check.** It began as a warning: `CHANGES.rst:297-300` (2.2.0) — using blueprint setup decorators/functions after registering "will show a warning. In the next version, this will become an error just like the application setup methods. :issue:`4571`". `CHANGES.rst:160-161` (2.3.0, under "Remove previously deprecated code. :pr:`4995`") records "Calling setup methods on blueprints after registration is an error instead of a warning. :pr:`4997`". So the flag's current hard-failure behaviour is the deliberate end state of a two-release deprecation, chosen for parity with the app-side check.

**Limits on the claim.** The flag does not mean the blueprint is "fully set up", and no evidence supports reading it as a thread-safety mechanism — it is a plain boolean set at registration time. Nested blueprints have no separate latch: the executor read the whole `register()` body (through the nested loop ending at line 377), and nested blueprints latch through the same `blueprint.register(app, bp_options)` path, which the runtime test confirms.
