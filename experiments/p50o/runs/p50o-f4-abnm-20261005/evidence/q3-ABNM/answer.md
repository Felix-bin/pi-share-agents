## No separate static-asset component exists in this codebase; static serving is a shared base-class capability registered twice, and cache parity is maintained by deliberate code duplication

There is no component-registration architecture here that separates static asset serving from the application framework, and there is no registry of "components" at all — the word appears only in unrelated prose (`CHANGES.rst:1373`, `docs/index.rst:19`, `src/flask/sansio/app.py:210`). What the code actually contains is:

**1. One shared abstraction, not a separate component.** `Scaffold` (`src/flask/sansio/scaffold.py:52`) is documented as "Common behavior shared between `Flask` and `Blueprint`" and holds all static *configuration*: the `static_folder` property that joins it to `root_path` (223–239), `has_static_folder` (240–246), and `static_url_path`, which is derived from the folder basename when not set (248–268). `add_url_rule` and `_check_setup_finished` are `NotImplementedError` stubs (221, 433), so `Scaffold` supplies the static configuration but does not own registration or serving.

**2. Registration happens at two independent sites.**
- App: `Flask.__init__` (`src/flask/app.py:263–279`) adds `f"{static_url_path}/<path:filename>"` with the literal endpoint `"static"`, a weakref'd lambda to avoid an app↔view reference cycle, and an assertion tying `static_host` to `host_matching`.
- Blueprint: `Blueprint.register` (`src/flask/sansio/blueprints.py:323–328`) adds the same rule shape with `view_func=self.send_static_file`, only when `has_static_folder`; `BlueprintSetupState.add_url_rule` (`sansio/blueprints.py:92–109`) then applies `url_prefix`/`subdomain` and name-prefixes the endpoint, giving `blueprint_name.static` (`docs/blueprints.rst:206–210`).

**3. The genuine module boundary (`sansio/`) is not that boundary.** It separates WSGI-dependent from framework-agnostic code: `App(Scaffold)` sits in `src/flask/sansio/app.py:59` with the generic `add_url_rule` (604+) and the static constructor arguments (281–299), while `Blueprint` is split across `sansio/blueprints.py` and `src/flask/blueprints.py:23–102`, the latter adding `cli`, `get_send_file_max_age`, `send_static_file`, and `open_resource`. Static asset handling is spread across that split rather than isolated by it.

**4. Caching consistency comes from duplication plus a shared config key, not from shared serving code.** `Flask.get_send_file_max_age` (`app.py:281–299`) and `Blueprint.get_send_file_max_age` (`blueprints.py:55–80`) are identical: both read `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]` at request time, return `None` for conditional caching, convert a `timedelta` with `total_seconds()`, and otherwise return the int. Both docstrings state verbatim "Note this is a duplicate of the same method in the Flask class" (`app.py:290`, `blueprints.py:64`). `send_static_file` is duplicated the same way (`app.py:308–328`, `blueprints.py:82–102`), and each copy computes `max_age = self.get_send_file_max_age(filename)` and passes it explicitly to `send_from_directory`, with the comment "send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too." That is the mechanism that makes behaviour consistent: `helpers._prepare_send_file_kwargs` (`helpers.py:386–390`) defaults `max_age` to `current_app.get_send_file_max_age` — the *app's* hook — so a blueprint's own override would be bypassed unless the blueprint's view injects its own value.

The parity is a documented promise and is tested per component, never for both at once: default `None`, per-file override via `get_send_file_max_age` "on the application or blueprint" (`docs/config.rst:249–263`); the hook was introduced in 0.9 for "`Flask` and `Blueprint`" alongside `SEND_FILE_MAX_AGE_DEFAULT` (`CHANGES.rst:1291–1300`); app side in `tests/test_helpers.py:50–90` (default `None`, config `3600` honoured by both `send_static_file` and `send_file`, subclass override `10`); blueprint side in `tests/test_blueprints.py:191–206` (blueprint static honours the app config) and `223–244` (blueprint subclass override `100` wins over config).

**Known asymmetries and limits.** `send_file`/`send_from_directory` called *directly* from a blueprint view still use the app's hook, not the blueprint's (`helpers.py:388–389`) — only blueprint static views get the blueprint hook. A blueprint static folder is unreachable without a `url_prefix`, because the app's `/static` rule takes precedence and blueprint static folders are not searched as a fallback (`docs/blueprints.rst:212–217`). Registration timings differ (constructor vs. `register()`), though both funnel through `setupmethod`/`add_url_rule`, so the `static` endpoint cannot be registered twice.

**What is answered vs. open.** The "consistent caching behavior across both components" half is answered and verified: one config key, one conversion rule, one explicit-`max_age` injection pattern, mirrored identically in `Flask` and `Blueprint`. The "modular component registration architecture that separates static asset serving from the main application framework" half is **not established** — no such component, module, or registry exists; the observed design is a shared `Scaffold` base class for static configuration plus knowingly duplicated serving/caching hooks in `app.py` and `blueprints.py`.
