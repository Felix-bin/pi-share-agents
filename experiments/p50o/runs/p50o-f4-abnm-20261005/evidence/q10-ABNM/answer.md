## The test and its dependency chain

The test is `tests/test_testing.py::test_subdomain` (lines 302–318); the copy at `flask_mut2_i417ar2x/mutated_test.py` is that same test line for line with `subdomain_matching=False`, which is what pins the subject to this test rather than to the blueprint variant (see the note at the end). The chain it depends on, in order, is:

1. **App-level configuration.** `flask.Flask(__name__, subdomain_matching=True)` carries the flag through `src/flask/app.py:233,245` into `App.__init__`, which sets `self.subdomain_matching = subdomain_matching` (`src/flask/sansio/app.py:407`) next to `self.url_map = self.url_map_class(host_matching=False)` (`sansio/app.py:405`).
2. **Server-name configuration.** `app.config["SERVER_NAME"] = "example.com"` (default `None`, `src/flask/app.py:188`; `APPLICATION_ROOT` defaults `"/"`, line 189). This single value is later read twice: once to build the test environment host (`src/flask/testing.py:66`) and once as the adapter's `server_name` (`src/flask/app.py:452`).
3. **Route registration.** `@app.route("/", subdomain="<company_id>")` → the `Scaffold.route` decorator calls `self.add_url_rule(rule, endpoint, f, **options)` (`src/flask/sansio/scaffold.py:336–363`) → `App.add_url_rule` (`sansio/app.py:605`) creates `self.url_rule_class(rule, methods=..., subdomain="<company_id>")` (line 650), adds it to `url_map` (line 653) and records the view under endpoint `"view"` (line 661). The placeholder lives in the *subdomain*, not the path, so its value can only arrive through the host — that is the link that ties route registration to configuration.
4. **Request-context creation.** `with app.test_request_context():` → `Flask.test_request_context` (`src/flask/app.py:1423`) builds `EnvironBuilder(self)` (line 1472); with no `subdomain` argument the host comes from `SERVER_NAME` (`src/flask/testing.py:65–76`) → `self.request_context(builder.get_environ())` (line 1475) → `RequestContext.__init__` (`src/flask/ctx.py:309`) → `app.create_url_adapter(self.request)` (`ctx.py:323`).
5. **Adapter binding — where configuration and context meet.** `create_url_adapter` (`src/flask/app.py:425`) sets `subdomain = None` and `server_name = config["SERVER_NAME"]`; because `host_matching` is false and `self.subdomain_matching` is true, the "force the subdomain to the default/empty" branch (`app.py:458–462`) is skipped, and `url_map.bind_to_environ(environ, server_name="example.com", subdomain=None)` (line 464) computes the current subdomain by comparing `HTTP_HOST` with `server_name` — `""` for `example.com` (Werkzeug `routing/map.py:321–339`, adapter `350–359`).
6. **URL building inside that context.** `flask.url_for("view", company_id="xxx")` (`src/flask/helpers.py:188`) → `Flask.url_for` (`app.py:1003`), which finds an active request context and therefore uses `req_ctx.url_adapter` with `_external` defaulting to `False` (`app.py:1078–1081`) → `MapAdapter.build` / `Rule.build` fills the subdomain placeholder with `"xxx"`; since that domain part differs from the adapter's subdomain, the in-request shortcut at Werkzeug `routing/map.py:944–948` does not fire and an absolute `http://xxx.example.com/` is produced (`map.py:950–951`).
7. **Only the URL crosses the boundary.** The context is popped at the end of the `with` block, so the string in `url` is the single artifact handed to the request half of the test.
8. **Request → view.** `client.get(url)` (`FlaskClient`, `src/flask/testing.py:125`) puts `xxx.example.com` into `HTTP_HOST` because the URL is absolute; `wsgi_app` (`app.py:1506`) builds a *second* request context through the same `create_url_adapter` path, `bind_to_environ` again resolves the subdomain to `"xxx"` (`map.py:321–339`, matcher uses it as the domain part at `598–600`), the registered rule matches, and `view` receives `company_id="xxx"` from the host.
9. **Assertions:** status `200` (`tests/test_testing.py:317`) and body `b"xxx"` (line 318) — the second assertion is only reachable because the placeholder was in the subdomain and the view returns its argument.

Which links are genuinely load-bearing: the flag from step 1 is required only at step 8, i.e. for *request-side matching* — with `subdomain_matching=False`, `create_url_adapter` forces `subdomain = ""` (`app.py:458–462`), so the request's domain part becomes `""` and the rule keyed on the subdomain `<company_id>` cannot be selected, because the default `UnicodeConverter` regex is `[^/]+` and needs at least one character (Werkzeug `routing/converters.py:25`). Step 6 is *not* affected by the flag: the built URL is identical either way, since `Rule.build` derives the subdomain from the passed values and the shortcut compares it against an adapter subdomain that is `""` in both cases. So in the mutant at `flask_mut2_i417ar2x/mutated_test.py` the break lands on the request half (the `200` assertion), not inside `url_for` — that reading comes from the sources above; I did not re-execute the mutant in this session, so the exact observed failure point is not something I am asserting.

`test_blueprint_with_subdomain` (`tests/test_testing.py:117–138`) exercises the same three elements — configuration (`SERVER_NAME`, `APPLICATION_ROOT`), route registration (blueprint `@bp.route("/")` + `register_blueprint`), request context (`test_request_context("/", subdomain="xxx")`) — and `test_subdomain_basic_support` (`tests/test_basic.py:1754`) covers the same behaviour by passing the subdomain through the client's host instead of `url_for`; neither is the subject here, because `route` + "request context creation" and the mutation copy both point at `test_subdomain`.
