## `_got_registered_once` on `Blueprint`: a one-way latch that freezes the blueprint's setup API

**The purpose.** `Blueprint._got_registered_once` is a boolean that starts `False` as a class attribute (`src/flask/sansio/blueprints.py:172`) and is flipped to `True` exactly once, inside `Blueprint.register`, at the moment the blueprint is first attached to an application object (`src/flask/sansio/blueprints.py:319-320`). From then on, any call to a *setup* method on that blueprint raises an `AssertionError` instead of taking effect. It exists to turn a **silent, partially-applied** setup mutation into a **loud, immediate failure**, with a message that tells the developer what to do instead: do all imports, decorators and function definitions *before* registering the blueprint (`src/flask/sansio/blueprints.py:213-221`).

**How it is wired up.** `Blueprint` is the class documented as "a collection of routes and other app-related functions that can be registered on a real application later" (`src/flask/sansio/blueprints.py:120-121`), and every method that mutates that collection is wrapped by the `setupmethod` decorator, whose only job is to call `self._check_setup_finished(f_name)` before the real body runs (`src/flask/sansio/scaffold.py:42-49`). `Scaffold._check_setup_finished` is abstract (`src/flask/sansio/scaffold.py:220-221`); `Blueprint` overrides it to test this flag (`src/flask/sansio/blueprints.py:213-214`). The flag is therefore the sole state behind the check — the whole repository contains only three references to it: the declaration (`:172`), the test (`:214`) and the assignment (`:320`). Nothing else reads it, so it carries no routing, dispatch or lifecycle semantics: it is purely a developer-facing guard.

**Why the guard is needed (the inconsistency it prevents).** A blueprint is not a live app: it stores work in two places, and they behave differently at registration.

- Deferred callbacks in `deferred_functions` are *replayed on every* `Blueprint.register` call (`src/flask/sansio/blueprints.py:334-335`), and they run against a `BlueprintSetupState`, which has its own non-`setupmethod` `add_url_rule` (`src/flask/sansio/blueprints.py:99-118`) — so the replay path deliberately bypasses the setup lock.
- The blueprint's `Scaffold`-level collections — `error_handler_spec`, `view_functions`, `before_request_funcs`, `after_request_funcs`, `teardown_request_funcs`, `url_default_functions`, `url_value_preprocessors`, `template_context_processors` — are copied into the app only on the *first* registration of the blueprint object or of that name (`self._merge_blueprint_funcs(app, name)` guarded by `if first_bp_registration or first_name_registration`, `src/flask/sansio/blueprints.py:316-317, 331-332`, implementation at `:379-408`).
- Callbacks recorded through `record_once` (e.g. template filters/tests) additionally run only when `state.first_registration` is true (`src/flask/sansio/blueprints.py:233-246`, `:36-74` of `BlueprintSetupState`).

So a route, `before_request`, error handler or template filter added *after* the blueprint has been registered would either never reach the application that already holds the merged copies, or only reach it under the narrow condition of a later registration under a *new name*. That is the "changes will not be applied consistently" wording of the error (`src/flask/sansio/blueprints.py:216-221`). The flag makes that class of bug fail at the point of the mistake rather than at request time.

**Design context and history.** The behaviour was introduced as a *warning* in 2.2.0 and hardened into an *error* in 2.3.0: "Use Blueprint decorators and functions intended for setup after registering the blueprint will show a warning. In the next version, this will become an error just like the application setup methods." (`CHANGES.rst:297-300`) then "Calling setup methods on blueprints after registration is an error instead of a warning." (`CHANGES.rst:160-161`). The application-level counterpart of the same guard is `App._check_setup_finished`, driven by `_got_first_request` rather than a registration flag (`src/flask/sansio/app.py:409-423`) — the app is locked once it starts *serving*, whereas a blueprint is locked at *registration*, because registration is the moment its accumulated state is copied into an app. The stated motivation for both is that setup must be complete before serving, since WSGI servers split work across workers or machines and late changes cannot be kept consistent (`docs/lifecycle.rst:31-51`).

**Boundaries of what the flag does.** It only blocks further *setup* calls on the blueprint; it does not prevent the same blueprint object from being registered on additional apps, and it is set at `:320`, before the deferred callbacks are replayed at `:334-335`, so a recorded callback that tried to call a setup method on its own blueprint would also be rejected. Because `register_blueprint` is itself a `setupmethod` (`src/flask/sansio/blueprints.py:255-271`), nested blueprints must be attached before the parent is registered. There is no companion reset path — the flag is never set back to `False` — which matches the documented fact that a blueprint cannot be unregistered from an app once it has been added (`docs/blueprints.rst:44-46`).
