## What the dual inheritance decides

`class UnexpectedUnicodeError(AssertionError, UnicodeError)` (`src/flask/debughelpers.py:17`, docstring: *"Raised in places where we want some better error reporting for unexpected unicode or binary data."*) reflects a **bridge, not a split**. The two bases encode two orthogonal properties, and the design keeps validation failures and encoding issues in one error space rather than two disjoint hierarchies:

**1. `UnicodeError` preserves the error's identity at the encoding layer.** `UnicodeError` is a `ValueError` subclass, and Flask's own data-level error contract is typed in those terms — `Request.on_json_loading_failed(self, e: ValueError | None)` (`src/flask/wrappers.py:221`) accepts the `ValueError` family. So a debug diagnostic raised in place of an encoding failure is still caught by every `except UnicodeError` / `except ValueError` handler between it and the WSGI/bytes boundary: the message is improved without changing what the surrounding layer considers a handled data error. Without that base, turning debug on would convert a normally-handled encoding failure into an unhandled 500.

**2. `AssertionError` is Flask's marker for "the developer did something wrong", not "the data was wrong".** The framework raises `AssertionError` for misuse at every layer — setup after first request (`src/flask/sansio/app.py:415`), overwriting an endpoint (`sansio/app.py:657`), re-registering a blueprint (`sansio/blueprints.py:215`), popping the wrong context (`src/flask/ctx.py:268`, `429`) — and *every* diagnostic in this same module uses it: `DebugFilesKeyError(KeyError, AssertionError)` (`debughelpers.py:23`) and `FormDataRoutingRedirect(AssertionError)` (`debughelpers.py:50`). It is also what makes the condition loud in tests and under `app.testing` (`src/flask/app.py:673-679`).

The resulting rule, which `UnexpectedUnicodeError` follows and `DebugFilesKeyError` demonstrates, is: **keep the base of the exception the caller would otherwise catch, and add `AssertionError` as the "programmer error, debug-only reporting" tag.** Role (assertion) and category (encoding/`KeyError`) are layered onto one class instead of being separated into different exception families.

**3. The layer separation is enforced by module and guard, not by exception hierarchy.** `debughelpers` is an optional overlay imported lazily from the layer above only when debugging is on: `wrappers.py:202-210` (`# In debug mode we're replacing the files multidict with an ad-hoc subclass that raises a different error for key errors`, guarded by `current_app.debug`) and `app.py:502` for `FormDataRoutingRedirect`. The core never imports the debug helpers at import time, and no debug class needs the core to know about it — inheritance-compatible substitution is what makes that possible.

**4. Ordering carries no stated intent.** `DebugFilesKeyError` lists the runtime type first (`KeyError, AssertionError`) while `UnexpectedUnicodeError` lists the marker first (`AssertionError, UnicodeError`). Neither overrides `__init__` or any method, so the order affects only `__mro__` / the repr of the bases, not catchability. I report this as an undocumented inconsistency rather than a decision.
