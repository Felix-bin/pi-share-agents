## Static serving as a registered component, not a framework special case

The architecture is a two-layer split: one shared, I/O-free configuration/registration base, and a per-component view function that is registered on the URL map like any other route.

**Layer 1 — shared base.** `Scaffold` (`src/flask/sansio/scaffold.py`, "Common behavior shared between `Flask` and `Blueprint`") owns only the *configuration* of static assets, no serving: `static_folder` (absolute path joined onto `root_path`, lines 223‑238), the `static_folder` setter, `has_static_folder` (241), and `static_url_path` (derived from the folder basename when not given, 249‑262). It lives in the `sansio` package, which by its own README contains "code that can be used by alternative Flask implementations … cannot do any IO" (`src/flask/sansio/README.md`). Both components inherit it: `Blueprint` → `Scaffold` (`src/flask/sansio/blueprints.py:119`) and `App` → `Scaffold` (`src/flask/sansio/app.py:59`), with `Flask(App)` (`src/flask/app.py:81`) and `Blueprint(SansioBlueprint)` (`src/flask/blueprints.py:18`) adding the I/O-capable layer. So the static-asset *contract* is shared; the WSGI machinery is not.

**Layer 2 — component-owned serving.** Serving is implemented as `send_static_file(filename)` on each component and registered as an ordinary view at endpoint `static` with rule `{static_url_path}/<path:filename>` — never as a branch inside request dispatch:

- App: registered eagerly in `Flask.__init__` via `self.add_url_rule(f"{self.static_url_path}/<path:filename>", endpoint="static", host=static_host, view_func=lambda **kw: self_ref().send_static_file(**kw))`, using a `weakref` explicitly to avoid an app↔view-function reference cycle (`src/flask/app.py:262-279`). This is the only static path that takes a `static_host`.
- Blueprint: registered lazily at registration time in `Blueprint.register` via `state.add_url_rule(f"{self.static_url_path}/<path:filename>", view_func=self.send_static_file, endpoint="static")` (`src/flask/sansio/blueprints.py:323-328`), where `BlueprintSetupState.add_url_rule` prefixes the endpoint with `{name_prefix}.{name}.`, applies `url_prefix`/`subdomain`, and forwards to `app.add_url_rule` (`src/flask/sansio/blueprints.py:87-113`). Because both use the bare endpoint `static`, a blueprint's static route needs a `url_prefix` or the app's static route takes precedence (documented at `src/flask/sansio/blueprints.py:145-147`).

Consequently the framework core stays static-agnostic: the same `add_url_rule`/routing/endpoint machinery handles assets and application views, and either component can be dropped or used without the other (app without a static folder, blueprint without a static folder).

## How caching stays consistent across the two components

Both `send_static_file` implementations (`src/flask/app.py:308`, `src/flask/blueprints.py:82`) funnel into the shared helper chain `helpers.send_from_directory` → `_prepare_send_file_kwargs` (`src/flask/helpers.py:387-399`) → `werkzeug.utils.send_file`, whose defaults are `conditional=True` and `etag=True`. The HTTP-level caching behaviour (ETag/Last-Modified, conditional 304 and range handling, `Cache-Control: no-cache` when `max_age is None`, `public` with a max-age otherwise) is therefore identical for app and blueprint assets because it comes from one code path.

The timing value is handled explicitly and symmetrically:

- `_prepare_send_file_kwargs` only supplies `max_age` from `current_app.get_send_file_max_age` when the caller passed none (`src/flask/helpers.py:388-389`). Werkzeug would otherwise always ask the *app*, so each component resolves it first: `max_age = self.get_send_file_max_age(filename)` and `send_from_directory(..., max_age=max_age)` — the in-code comment says exactly this ("send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too", `src/flask/app.py:323-325`, `src/flask/blueprints.py:97-99`).
- Each component defines its own `get_send_file_max_age` (`src/flask/app.py:281`, `src/flask/blueprints.py:55`). Both read the same single key `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]` at request time (default `None`, `src/flask/app.py:201`) and normalise `timedelta` to seconds, so one config value drives both components, and both remain subclass-overridable per component.
- Consistency is maintained by **duplication, not by a shared implementation**: the two methods are copy-identical, and both docstrings mark it — "Note this is a duplicate of the same method in the Flask class." (`src/flask/blueprints.py:59` and `:88`; `src/flask/app.py:314`, where the note is self-referential because the text was copied from the blueprint side). There is no shared base-class method for max-age resolution, so a change to the caching rule must be applied twice.
- Tests pin the behaviour per component: `tests/test_helpers.py::TestSendfile::test_static_file` (default `None` → no `max_age`, then config `3600` for both `app.send_static_file` and `flask.send_file`, then a `Flask` subclass override returning `10`); `tests/test_blueprints.py::test_templates_and_static` (a blueprint static response's `Cache-Control` max_age follows `SEND_FILE_MAX_AGE_DEFAULT`); `tests/test_blueprints.py::test_default_static_max_age` (a `Blueprint` subclass override of `get_send_file_max_age` returning `100` wins over the app config).
