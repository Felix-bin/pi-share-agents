# Why the dotted-blueprint-name test guarantees a `ValueError`

**The test asserts a constructor-time exception, and the constructor is where the dot guard lives.** `tests/test_blueprints.py:254` defines `def test_dotted_name_not_allowed(app, client):`, whose entire body is a `with pytest.raises(ValueError):` block (`:255`) wrapping one statement — `flask.Blueprint("app.ui", __name__)` (`:256`). Because `pytest.raises` fails the test if nothing is raised, and because the only statement in the block is a `flask.Blueprint` **construction** (no `app.register_blueprint`, no route, no client call), the test guarantees a `ValueError` exactly at object creation. "Modular route component" is read as `flask.Blueprint`: the test calls `flask.Blueprint` directly, `src/flask/__init__.py:3` exports `Blueprint` from `.blueprints`, and `docs/blueprints.rst` is the Blueprint chapter.

**The exception originates in `Blueprint.__init__`'s eager dot guard.** `src/flask/sansio/blueprints.py:174` is the `__init__` signature with `name: str` at `:176`; the guard is `if "." in name:` at `:198` followed by `raise ValueError("'name' may not contain a dot '.' character.")` at `:199`, sitting immediately after the empty-name guard (`:195` `if not name:`, `:196` `raise ValueError("'name' may not be empty.")`) and before `self.name = name` (`:201`). The concrete class forwards into it: `src/flask/blueprints.py:18` `class Blueprint(SansioBlueprint)` with `__init__` at `:19` calling `super().__init__(name, import_name, ...)` at `:32`. Runtime confirmation (step 4, run in this worktree): `test_dotted_name_not_allowed` reports `1 passed`; direct construction of `flask.Blueprint("app.ui", __name__)` raises `ValueError: "'name' may not contain a dot '.' character."`, with exactly three traceback frames — `<module>` → `src/flask/blueprints.py:32` → `src/flask/sansio/blueprints.py:199` — and `flask.Blueprint("app_ui", __name__)` is created without error. The traceback is what pins the raise to the *dot* guard rather than the empty-name guard, since `"app.ui"` is non-empty. Note that the test asserts only the exception *type* (`ValueError`), not the message; the message match is established by the traceback and by step 2's source line.

**Because the guard is in `__init__`, the test needs no app, routes or client.** `register()` starts at `src/flask/sansio/blueprints.py:272` and `register_blueprint` at `:255`; neither appears in the traceback, so the failure precedes both. This also explains the otherwise odd signature `(app, client)` in a body that never uses them — both fixtures exist (`tests/conftest.py:44` `app`, `tests/conftest.py:66` `client`), the test simply doesn't need them, which is consistent with the observed `1 passed`.

**The reason the dot is reserved, not stylistic: it is the separator the registration layer composes.** `CHANGES.rst:504-506` (in the `Version 2.0.1` section) states: "Show an error when a blueprint name contains a dot. The ``.`` has special meaning, it is used to separate (nested) blueprint names and the endpoint name. :issue:`4041`". That separator is built at registration time in two places: `src/flask/sansio/blueprints.py:304` `name = f"{name_prefix}.{self_name}".lstrip(".")` (with `name_prefix` at `:302` and `self_name = options.get("name", self.name)` at `:303`), and endpoint assembly in `BlueprintSetupState.add_url_rule` at `:112` `f"{self.name_prefix}.{self.name}.{endpoint}".lstrip(".")`. Nested blueprints are registered with the parent's name as their prefix (`src/flask/sansio/blueprints.py:376` `bp_options["name_prefix"] = name`), and the docstrings name the semantics (`:290-292` "Nested blueprints are registered with their dotted name..."; `:294-298` the `name` option changes the "(pre-dotted)" name; the same option text on `Flask.register_blueprint` is `src/flask/sansio/app.py:588`). The docs agree: generated rules "are also prefixed with the name of the blueprint and separated by a dot (``.``)" (`docs/blueprints.rst:106`), and "prefix the URL endpoint with the name of the blueprint and a dot (``.``)" (`docs/blueprints.rst:270`, example `url_for('admin.index')`). The supported inference — flagged as inference, since `CHANGES.rst` claims only "special meaning" — is that a dot in the constructor `name` would be indistinguishable from the separator the registration layer injects, so the constructor reserves it.

**The counter-evidence that dots in *endpoint* names are legitimate is consistent with this.** `tests/test_blueprints.py:264-278` `test_dotted_names_from_app` constructs `flask.Blueprint("test", __name__)` (no dot in the constructor name), registers it, and relies on `flask.url_for("test.index")` and a cross-blueprint `url_for("app_index")`; the dots in those endpoint names are added by the app/registration side, not supplied by the caller. The near-miss tests confirm the boundary is elsewhere: `test_route_decorator_custom_endpoint_with_dots` (`tests/test_blueprints.py:327-341`) builds `bp = flask.Blueprint("bp", __name__)` and puts `pytest.raises(ValueError)` around `bp.route("/", endpoint="a.b")`, `bp.add_url_rule("/", endpoint="a.b")` and a `view.__name__ = "a.b"` case — that is a *different* guard, `src/flask/sansio/blueprints.py:428` (`'endpoint' may not contain a dot '.' character.`) and `:431` for `view_func.__name__`, enforcing the same reserved-separator rule at the endpoint level. Likewise `test_empty_name_not_allowed` (`tests/test_blueprints.py:257-259`) is the sibling of the target test for the empty-name guard. All four of these tests pass (`4 passed`), which is exactly the pattern the mechanism predicts.

**Answer to the question:** the test ensures a `ValueError` because it calls the `Blueprint` constructor inside `pytest.raises`, and the constructor eagerly rejects any dotted `name` at `src/flask/sansio/blueprints.py:198-199` before any app, registration or request is involved; that rejection exists because the dot is the reserved separator composed from `name_prefix` + blueprint name at registration (`:304`) and from blueprint name + endpoint at route setup (`:112`), as recorded in `CHANGES.rst:504-506` (issue 4041) and `docs/blueprints.rst:106,270`.
