# Why `Flask.open_resource` rejects write modes

**The method:** `Flask.open_resource` (`src/flask/app.py:330-361`) — docstring "Open a resource file relative to :attr:`root_path` for reading" (`app.py:333`), path built with `path = os.path.join(self.root_path, resource)` (`app.py:356`). `Blueprint.open_resource` (`src/flask/blueprints.py:104-128`) is the same body with the same guard and wording, so it behaves identically. `open_instance_resource` is excluded: it joins `self.instance_path` (`app.py:378`) and is explicitly documented as the writable counterpart (`app.py:366-368`).

**The restriction itself** is a literal closed-set guard, `src/flask/app.py:353-354`:

```python
if mode not in {"r", "rt", "rb"}:
    raise ValueError("Resources can only be opened for reading.")
```

matching the parameter doc "Only reading is supported, valid values are `"r"` (or `"rt"`) and `"rb"`" (`app.py:345-346`). It is not a binary/text distinction and not a filesystem permission check: even `r+`, which reads, is refused (see the runtime check below).

**The reason the code and docs support.** `root_path` is the directory of the application's own module/package — "the root path where the resources and modules are located" (`CHANGES.rst:1352-1354`), derived from the `__name__` passed to `Flask(...)` so that Flask "can properly load resources relative to your module" (`docs/design.rst:53-59`). It is therefore the location of the shipped code artifact, whose data files are inputs to the running app, not storage the app owns. In the deployed case the worktree's own documentation places that directory inside the Python installation — for an "Installed module or package" the root is `$PREFIX/lib/pythonX.Y/site-packages/myapp` while the instance goes to `$PREFIX/var/myapp-instance` (`docs/config.rst:801-805`), and `src/flask/sansio/scaffold.py:757-777` shows the code detecting exactly that `site-packages` case from `sys.prefix`. Flask's stated design answer to "where do files that change go" is the instance folder: "the designated place to drop files that are modified at runtime (uploads etc.)", "outside version control", "the perfect place to put configuration files" (`CHANGES.rst:1352-1357`), "designed to not be under version control and be deployment specific ... the perfect place to drop things that either change at runtime or configuration files" (`docs/config.rst:769-776`). Consistent with that split, `open_resource` exposes only read modes, and the write-capable accessor is the instance one — `open_instance_resource` carries no mode guard (`app.py:378-383`) and is documented as "Unlike :meth:`open_resource`, files in the instance folder can be opened for writing" (`app.py:366-368`), advertised as the shortcut for exactly this (`docs/config.rst:827-839`). The one later widening of the accepted set stayed inside read semantics: `open_resource` accepts `"rt"`, which "still does the same thing as ``"r"``" (`CHANGES.rst:686-687`).

So the short answer: the method opens files that ship with the application's code, so Flask treats them as read-only inputs and rejects write modes outright; anything mutable at runtime is deliberately routed to `instance_path` via the method documented as writable. The `open_resource` docstring's own example is a read of a shipped `schema.sql` (`app.py:341-342`), and the tutorial frames the method as opening files that are next to the package and whose location "you won't necessarily know ... when deploying the application later" (`docs/tutorial/database.rst:141-143`).

**Corroborated at runtime by the executed step.** `.venv/Scripts/python.exe -m pytest tests/test_helpers.py -k open_resource -q` (with `PYTHONPATH=src`) exited 0 with `9 passed`: `test_open_resource[r|rb|rt]` pass and `test_open_resource_exceptions[w|x|a|r+]` pass, the latter asserting `ValueError` (`tests/test_helpers.py:338-351`). That confirms "read-only" is exactly `{r, rt, rb}` and that the guard is about opening for modification, not about text vs. binary. Import was verified to resolve to this working directory's `src/flask`. Caveat on that run: the plan's literal command (`python -m pytest ...`) fails here with `ModuleNotFoundError: No module named 'flask'`, and the repo `.venv` without `PYTHONPATH=src` resolves `flask` to a different checkout — the passing result depends on both `PYTHONPATH=src` and the repo interpreter.

## What still does not hold, and what stays open

- **No explicit statement of the reason exists in the tree.** A case-insensitive search for `read-only|read only|writab|immutab|site-packages` and for the guard's message returns only the guard and docstrings themselves (`app.py:353-354`, `app.py:366-368`, `blueprints.py:120-121`); no comment, design note, or changelog entry explains why the guard exists. The explanation above is reconstructed by joining the documented root-path/instance-path split (`CHANGES.rst:1352-1357`, `docs/config.rst:769-776`, `801-805`, `docs/design.rst:53-59`), not quoted as a rationale. In particular, "writes to site-packages are not guaranteed so they are disallowed" is an inference; the tree states the layout, never a write-permission argument.
- **Those docs describe intent, not a mechanical cause.** Nothing in the codebase prevents a developer from calling builtin `open()` against `root_path`; the guard on this one API is the only enforcement, and `open_instance_resource` passes arbitrary modes straight to `open` (`app.py:380-383`). The docs are the surrounding design framing of the guard, not its source.
- **Provenance is absent.** The issue/PR/commit that introduced the `ValueError` is not in the tree — `CHANGES.rst` records only the later `rt` addition (`CHANGES.rst:686-687`) and the `encoding` parameter (`CHANGES.rst:35-37`). If the question meant historical motivation, that part is unanswered from this working directory.
- **Not answered here (product/API decisions left out deliberately):** whether the restriction should be relaxed, whether `r+` should be allowed, and any change to `open_instance_resource` or the blueprint mirror.
