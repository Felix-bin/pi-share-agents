## Why `ScriptInfo` loads the app lazily through a cached `_loaded_app` instead of in `__init__`

**The mechanism.** `ScriptInfo` (`src/flask/cli.py:293`, docstring 294–304: the helper "used internally in the dispatching to click") ends its `__init__` with `self._loaded_app: Flask | None = None` (`src/flask/cli.py:331`) — construction seeds the cache and discovers nothing. `load_app()` (`src/flask/cli.py:333`) opens with the guard `if self._loaded_app is not None: return self._loaded_app` (338–339), then discovers: caller-supplied `create_app()` (342), else `app_import_path` → `prepare_import`/`locate_app` (344–351), else a cwd scan of `("wsgi.py", "app.py")` (352–356); on failure it raises `NoAppException` with the "Use the 'flask --app' option, 'FLASK_APP' environment variable…" text (358–364), and on success memoizes with `self._loaded_app = app` (371) before `return app` (372). Those two lines (331, 371) are the *only* assignments to the attribute anywhere in the worktree; the docstring states the caching contract outright: "Loads the Flask app (if not yet loaded) and returns it. Calling this multiple times will just result in the already loaded app to be returned." (334–337).

**Reason 1 — the app target does not exist yet when the helper is constructed (this is the structural reason).** `ScriptInfo` is created inside `FlaskGroup.make_context` (`def make_context` at 657) at `src/flask/cli.py:670`, guarded by `if "obj" not in extra…` (669), and the *only* things passed are `create_app`, `set_debug_flag`, `load_dotenv_defaults` (671–674). `app_import_path` defaults to `None` (307, 313). The value that decides *which* app to load is written later, from `-A/--app`, by `_set_app`: `info = ctx.ensure_object(ScriptInfo)` / `info.app_import_path = value` (444–445); `FLASK_APP` reaches the same option only through the env-var mapping `auto_envvar_prefix="FLASK"` (585) on `_app_option` (453–463); and for the no-args/`--help` path `FlaskGroup.parse_args` replays the options manually via `_env_file_option.handle_parse_result(ctx, {}, [])` / `_app_option.handle_parse_result(ctx, {}, [])` (684–686). So "loading during initialization" is not merely undesirable, it is impossible in the general case: at `__init__` time there is nothing to load from. The runtime instrumentation confirms this directly — with `-A mypkg:create_app` on the command line, the `__init__` snapshot still shows `app_import_path=None`, and only by `load_app()` time does the object hold `mypkg:create_app`. One honest limit: the ordering "`make_context` runs before click parses parameters" comes from click's command lifecycle, whose source lives outside this worktree; the in-repo corroboration is that a click parameter callback, `_env_file_callback`, reads `ctx.obj.load_dotenv_defaults` while parameters are being processed (`src/flask/cli.py:509-510`), i.e. the `ScriptInfo` already exists mid-parse.

**Reason 2 — discovery must be *fallible*, so it cannot be hoisted into construction (this is the only rationale stated as prose in the repo).** `FlaskGroup.get_command` loads plugin commands first and returns built-ins/plugins *before* ever trying the app, with the comment "Look up built-in and plugin commands, which should be available even if the app fails to load." (610–616), then wraps the app lookup as "showing an error and continuing if the app couldn't be loaded" (620–621) with `try: app = info.load_app() / except NoAppException as e: click.secho(f"Error: …", err=True)` returning `None` (622–626). `list_commands` repeats the pattern with a two-way split: `NoAppException` prints the message without traceback (646–649), any other exception prints `traceback.format_exc()` (650–651). `--version` never touches `ScriptInfo` at all (`version_option` at 283–289 is eager; `get_version` at 267–280 only reads `importlib.metadata.version`). The tests pin exactly this: `tests/test_cli.py:413-425` (`--help` → exit 0, loading error on stderr), `401-411` (unknown command → exit 2, `"FLASK_APP" in stderr`), `428-436` (`--help` still exit 0 when the factory raises). Runtime: with no `app.py`/`wsgi.py` and `FLASK_APP` unset, `flask --version` exited 0 with only the version lines, `flask --help` exited 0 and still listed `routes`/`run`/`shell` with the `NoAppException` text on stderr only, and `flask routes` / `flask run` / `flask shell` exited 2 with that text and no traceback (`NoAppException` subclasses `click.UsageError`, `src/flask/cli.py:37`). Nuance the runtime exposed: `--help` *does* call `load_app()` via `list_commands`, so "deferred" means "its failure is non-fatal and it never blocks built-in commands or `--version`", not "never called before dispatch".

**Reason 3 — discovery imports user code, so it waits until a command actually needs the app (effect demonstrated; motive inferred).** The effect is verified: `flask --app flask_mut2_i417ar2x.mutated_test --version` exited 0 printing only version lines with the module never imported, while the `routes` invocation imported it, the traceback running `cli.py:397 app = …load_app()` → `cli.py:349 locate_app` → `cli.py:245 __import__(module_name)` → the module's own top-level code. The *motive*, however, is nowhere stated: no comment or docstring says deferral exists to avoid import side effects. The nearest in-repo support is the flag the CLI sets in `make_context` immediately *before* constructing the `ScriptInfo`: "Set a flag to tell app.run to become a no-op. If app.run was not in a `__name__ == __main__` guard, it would start the server when importing, blocking whatever command is being called." (664–667). That documents that importing user code is dangerous; it does not state that deferral is motivated by it. **Inferred, unsupported as a stated rationale.**

**Reason 4 — the cache makes `load_app()` idempotent across several call sites (stated).** The docstring plus the guard/assignment (334–339, 371) exist precisely because `load_app()` is called from multiple dispatch paths: `with_appcontext` (`app = ctx.ensure_object(ScriptInfo).load_app()`, 397 — and indirectly `shell_command`/`routes_command` via `@with_appcontext`, 1000/1060), `FlaskGroup.get_command` (623), `FlaskGroup.list_commands` (645), and `run_command` (955). Without the cache each of these would re-run the factory or re-import the module, and a later failure would surface inconsistently. Tests `tests/test_cli.py:247-286` assert `obj.load_app() is app` on repeat calls and that a bare `ScriptInfo()` raises `NoAppException`, and `289-308` asserts the object's app is the current app; all five related cases (`scriptinfo`, `app_cli_has_app_context`, `help_echo_loading_error`, `no_command_echo_loading_error`, `help_echo_exception`) were run and passed.

**Net answer.** The cache is not an alternative to initializing; it is a consequence of the construction order and of failure tolerance. `ScriptInfo` is built before the parameters that name the app exist (670 vs. 445/585/684–686), so there is nothing to load at `__init__`; discovery is also an operation that may legitimately fail, and the CLI is designed so that failure is survivable (611–612, 622–626, 646–651), which a mandatory `__init__` call could not be; and the multiple, mutually independent call sites (397, 623, 645, 955) need one shared instance, which the `_loaded_app` guard supplies. The first reason is mechanically decisive in the code; the second is the one the repository actually says out loud; the third is real in effect but not a documented motive.

### Contradictions and caveats carried forward
- **Docs contradict the code on working directory.** `docs/cli.rst:44-46` claims `--app src/hello` sets the cwd to `src`, and `FlaskGroup`'s docstring says `load_dotenv` "will also change the working directory…" (543–545), but `chdir` occurs nowhere in `src/`, `prepare_import` only inserts into `sys.path` (223–224), and `load_dotenv`'s own note says the cwd is *not* changed (721–723). The "cwd default" limb must therefore be stated as the cwd-relative `wsgi.py`/`app.py` scan performed at call time (352–356), not as a directory change.
- **No doc or changelog states the deferral rationale.** `docs/api.rst:703` is only `.. autoclass:: ScriptInfo`; `docs/cli.rst` "Application Discovery" describes what `--app` values mean, never why loading is delayed; `CHANGES.rst` hits are feature entries only. The single explicit intent sentence is Reason 2's "should be available even if the app fails to load".
- **The alternative target class is ruled out.** `FlaskGroup` (`src/flask/cli.py:531`) does participate in discovery but caches only plugin commands (`_loaded_plugin_commands`, 598/601/607) and delegates app loading to the `ScriptInfo` it puts on `ctx.obj` (670, 623, 645). No other class in `src/` owns a lazy *app* attribute.
- **Runtime environment caveat.** The venv's `flask.pth` points at a different worktree, so every run used `PYTHONPATH=$PWD/src`; un-overridden, this venv's `flask` would exercise that other copy. Any future runtime check must repeat the override. Also noted in passing: `_path_is_ancestor` (691–696) is defined and referenced nowhere.
