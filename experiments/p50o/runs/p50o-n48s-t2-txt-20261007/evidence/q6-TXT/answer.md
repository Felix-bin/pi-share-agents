# Why "unconditional `accessed` tracking" does not slow signed-cookie string conversion — and what it actually costs

**Verdict: the premise is false as stated.** The unconditional `self.accessed = True` stores in the dict read methods do not ride on the signed-cookie conversion at all. In `SecureCookieSessionInterface.save_session`, `val = self.get_signing_serializer(app).dumps(dict(session))` (`src/flask/sessions.py:387`) copies the session via CPython's dict fast path, which never calls the overridden `__getitem__`. The instrumented run measured **0 method calls and 0 `accessed` stores** for `dict(session)` on a 50-key session, with a control `dict` subclass that overrides `__getitem__` also reporting 0, and `SecureCookieSession.__iter__ is dict.__iter__` true. So "per-key tracking write rides along the pre-signing copy" is not what happens; the stores are per *call*, not per *key*, and none of them fire during signing.

## The causal chain as it actually is

1. **Where the unguarded stores live.** `__getitem__` at `:85`, `get` at `:89`, `setdefault` at `:93` each begin with a bare `self.accessed = True` and then delegate to `super()`; the mutation hook `on_update` (`:78-80`, wired via `super().__init__(initial, on_update)` at `:82`) sets both `self.modified = True` (`:79`) and `self.accessed = True` (`:80`). None of the three read-method assignments is guarded — there is no `if not self.accessed:` in the file. `accessed` is `False` on the class (`:72`), so the first store is an instance-`__dict__` insertion after a class-attribute lookup; every later call re-stores unconditionally.
2. **The only consumer is the `Vary` decision.** A grep of `src/flask` for `\.accessed` returns exactly `sessions.py:80,85,89,93,363`. The single read is `if session.accessed:` (`:363`) feeding `response.vary.add("Cookie")` (`:364`). Nothing about serialization reads it.
3. **How a store reaches the save path.** It gets there indirectly through the `permanent` property (`:29-31`), which returns `self.get("_permanent", False)` (`:30`) and therefore dispatches to the overridden `get` at `:89`. `should_set_cookie` reads `session.permanent` at `:260` (only when `session.modified` is falsy, since `return session.modified or (...)` short-circuits), and `get_expiration_time` reads it again at `:243` (reached after `should_set_cookie` passes at `:383`). Instrumented end-to-end `save_session` counts: non-permanent, `modified=False` → 1 store, 1 `get`; permanent, `modified=False` → 2 stores, 2 `get`s; permanent, `modified=True` → 1 store, 1 `get`. In every case the `dict(session)` copy at `:387` contributed 0.
4. **Nothing else reads through the tracked methods.** `SecureCookieSession` overrides `__setitem__`/`__delitem__`/`clear`/`pop`/`popitem`/`update` not at all; those go through `on_update` (`:79-80`) and set both flags together. `__contains__`, `__len__`, `__iter__`, `keys`, `items`, `values` are not overridden, so iteration, `"k" in session`, and `len(session)` produce 0 stores (harness items (f)-(h)). `NullSession` aliases `setdefault` to `_fail` (`:110`), but its inherited `__getitem__`/`get` still store — irrelevant to `Vary`, because `save_session` is skipped for null sessions (`SessionInterface.is_null_session`, `:182-190`, called at `app.py:1322`).

## The magnitude (step 3, executed)

Timings on the actual signing expression, 50 keys, interleaved round-robin batches, medians, against a variant with the assignments removed:

| variant | median `dumps(dict(session))` | delta vs removed |
|---|---|---|
| unconditional | 48 759 ns | **+154 ns (0.32 %)** |
| guarded `if not self.accessed` | 48 618 ns | +13 ns (0.03 %) |
| assignments removed | 48 605 ns | — |
| bare `dumps(plain 50-key dict)` | 46 518 ns | — |

The 154 ns delta is **inside the run's own spread** (individual batches ranged roughly 47–104 µs), so on the signing path the effect is **within noise** — consistent with the 0-store finding. On a *forced* per-key read path (`[s[k] for k in s]` then `dumps`), the store costs ~22–48 ns/key, i.e. **measurable but small** (~2 % of that combined time); per-key signing cost is ~930 ns, so a store would be ~3 % of it — but that combination never arises, because the copy at `:387` bypasses the override. An isolated store measures ~27 ns and the guard check ~26 ns, so the guarded form is **not a CPU win**: on the forced path guarded measured slightly *slower* (2 681 ns vs 2 416 ns), within noise of each other. The honest label is **real but negligible, and off the signing path**.

## The frequency driver and the real impact

The genuine consequence of the unconditional store is the `Vary: Cookie` semantics, not CPU time. Any read — `session[...]`, `session.get`, `session.setdefault` — must still yield `Vary: Cookie`; `test_session_vary_cookie` pins this with `expect("/get")`, `expect("/getitem")`, `expect("/setdefault")` (`tests/test_basic.py:568-570`) and requires `Vary` to appear exactly once; `expect("/no-vary-header", None)` (`:573`) pins that an untouched session emits no `Vary`. `test_session` (`:234-254`) pins that a read flips `accessed` but leaves `modified` false (`:246-249`). The repeated-conversion driver is separate: when a session is permanent and `SESSION_REFRESH_EACH_REQUEST` is true, `should_set_cookie` (`:260`) is true, so `save_session` does not return at `:383` and re-runs `dumps(dict(session))` at `:387` on **every** request even when the view never touches the session (`test_session_refresh_vary`, `:581-595`; the matrix at `:481-518`). That is the high-frequency path; its cost is itsdangerous `TaggedJSONSerializer` + base64 + HMAC on the whole payload, and it is independent of the tracking attribute. Where "impact" means the caching effect of `Vary: Cookie` being emitted for any request that merely read the session (and for every permanent-refresh request), that is the effect the code and tests actually pin.

All three assignments are unguarded and always have been, but they were not introduced by one commit: `git log --follow -S "self.accessed = True"` attributes the `on_update`/`__getitem__`/`get` stores to `671c67aa` (Mihir Singh, 2014-04-16, "Append a 'Vary: Cookie' header...") and the `setdefault` store to `5d9dd0b3` (David Lord, 2017-05-20, "set session accessed for setdefault"); `git log --all -S "if not self.accessed"` returns no matches, i.e. no commit ever guarded them. HEAD is the detached `85c5d93c`.

**Closest accurate restatement:** setting `accessed` unconditionally in `__getitem__`/`get`/`setdefault` costs roughly one attribute store (~20–50 ns) per view-level read and one to two stores per `save_session` call via `session.permanent`; it does **not** add per-key work to `dumps(dict(session))`, because `dict(session)` copies the internal table without invoking the override. The measurable impact during frequent reads is therefore the forced `Vary: Cookie` (a caching/staleness constraint), not conversion CPU time; if the concern is CPU, the guarded form would not help, since the guard costs about as much as the store it would skip.

## What this rests on, and what remains open

- Rests on: `src/flask/sessions.py:29-31, 72, 78-93, 110, 178-190, 243, 260, 362-364, 383, 387` (verified by direct read and grep); the instrumented store/call counts and timings from the executor run on Python 3.13.9, Flask 3.2.0.dev (HEAD `85c5d93c`); `tests/test_basic.py:234-254, 481-518, 520-578, 581-595` and `docs/api.rst:67-101` via the retriever inventory; the git attribution above.
- The `accessed` attribute is not documented in `docs/api.rst` (only `new`, `modified`, `permanent`); the `Vary: Cookie` behavior traces to `CHANGES.rst` 2.0.0 (`:pr:`2288``) and was extended in 2.2.4/2.3.2.
- Open / uncertain: the guard's own ~26 ns cost masks any clean guarded-vs-unconditional CPU saving, so that comparison cannot be resolved by timing; the timing VM was noisy (some interleaved batches ran ~2× slow), so the µs-level deltas are medians with wide spread, not precise constants; and nothing beyond the observed CPython dict fast path was established about werkzeug internals, since the vendored source was not readable to the read-only tools.
- Not evidence for this question: `flask_mut2_i417ar2x/mutated_test.py`, which exercises `SERVER_NAME`/subdomain routing, not sessions, and must not be cited as the mutation under discussion.
