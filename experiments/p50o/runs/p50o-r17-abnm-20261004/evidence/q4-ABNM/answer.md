## What the dual inheritance reflects

`UnexpectedUnicodeError` is defined at `src/flask/debughelpers.py:17` as `class UnexpectedUnicodeError(AssertionError, UnicodeError)` with a docstring-only body. I re-read the definition and re-grepped the symbol in this worktree to confirm both the base order and that no file other than line 17 mentions it. Four architectural decisions are readable from it, and one of them is only intent.

**1. One exception object, two independently catchable failure categories — not a merge of them.** Runtime inspection in the repo's own `.venv` (Python 3.13.9, `PYTHONPATH=src`) gives the MRO `UnexpectedUnicodeError → AssertionError → UnicodeError → ValueError → Exception → BaseException → object`, with `isinstance`/`issubclass` true for `AssertionError`, `UnicodeError` and `ValueError`. So `except UnicodeError`, `except ValueError` and `except AssertionError` all catch it, on separate axes. The decision is that an encoding-family fault is *also* typed as Flask's internal-contract fault, while each category stays individually selectable by an `except` clause.

**2. The primary identity is deliberately the contract/diagnostic one.** `AssertionError` is written **first**, and the live check shows `AssertionError` is the first MRO class supplying `__init__` (the class's only surviving behaviour is therefore `AssertionError`'s; it defines no `__init__` or `__str__` of its own, and `__str__` resolves to `BaseException`). That is the reverse of the sibling in the same module, `DebugFilesKeyError(KeyError, AssertionError)` (line 23), where the native family leads. So this class is not "a `UnicodeError` that happens to be assertable" — it is framed as an assertion about unexpected data that still preserves the encoding family secondarily.

**3. It is tagged with `AssertionError` because that is Flask's internal-programming-contract channel, not the client-error channel.** The same signal is used across the framework for contract violations: "Popped wrong app context" / "Popped wrong request context" (`src/flask/ctx.py:268-270`, `429-431`), setup methods called too late (`src/flask/sansio/app.py:415-418`, `src/flask/sansio/blueprints.py:215-217`), view symbol overwriting an endpoint (`src/flask/sansio/app.py:657-660`). All of those are developer-side faults, never a 4xx to a client. Tagging `UnexpectedUnicodeError` with `AssertionError` files it in that family, and through `PROPAGATE_EXCEPTIONS` (resolved to `testing or debug` at `src/flask/app.py:843-846`) such exceptions are re-raised to the debugger rather than being converted into a 500 response.

**4. Encoding/parse failures get converted into the HTTP validation layer — this class sits on the debug side of that line.** The concrete boundary is `Request.on_json_loading_failed` (`src/flask/wrappers.py:212-220`): a werkzeug `BadRequest` from the JSON load is re-raised only when `current_app.debug`, otherwise a clean `BadRequest()` is raised instead. The always-on layers are separate: `handle_http_exception` (`src/flask/app.py:744`) passes werkzeug `HTTPException` through or to a registered handler, and `handle_user_exception` (`app.py:779-802`) forwards `HTTPException` there. `debughelpers` as a whole is debug-only and lazily imported: `FormDataRoutingRedirect` is imported after the `not self.debug` guard (`app.py:494-508`), `attach_enctype_error_multidict` only when `current_app.debug` and the request is not multipart (`wrappers.py:200-208`), `explain_template_loading_attempts` on the template-miss path (`templating.py:83`). Consistent with that, the class is not publicly exported — `hasattr(flask, "UnexpectedUnicodeError")` is `False`. So the separation is: bad client data ⇒ werkzeug `BadRequest` ⇒ HTTP layer; unexpected unicode/binary data in a debug diagnostic ⇒ `AssertionError`-tagged exception that propagates to the developer. The dual inheritance is what lets a single raise satisfy both type systems.

**What the evidence does not support.** The class has **no raise site in this revision**. A full (non-shallow, 5439-commit) history shows exactly two commits touching the symbol: `2b885ce4` (2012-10-30, "Added better error reporting for unicode errors in sessions") introduced it *and* raised it in `flask/sessions.py` `TaggedJSONSerializer._tag` under `except UnicodeError:`; `5e1ced3c` (2017-06-01) deleted that raise during the serializer refactor into `flask/json/tag.py`. Nothing afterwards touches it. The class has been dormant for ~8 years, so the separation described above is **design intent inferred from the sibling pattern, the MRO facts and the dispatch code — not behaviour observed on any live path**. No docstring, comment, docs page or commit message in the worktree states the intent (the plan's `docs/debugging.rst` does not exist), and nothing states why the class was kept after its raise was removed.
