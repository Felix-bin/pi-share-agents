## Dependency chain

The chain runs one direction, from the Flask application instance to the application-loading helper, and the isolation is supplied by the base Click runner at the bottom of it. Each hop is a real code edge, not an inference:

`Flask.test_cli_runner()` → `self.test_cli_runner_class` → `FlaskCliRunner.__init__(app)` stores the app → `FlaskCliRunner.invoke` injects `ScriptInfo(create_app=lambda: self.app)` → `CliRunner.invoke` runs inside `CliRunner.isolation()` → the command's `ctx.ensure_object(ScriptInfo).load_app()` returns that same `Flask` instance, memoized.

**1. Application instance → runner class (the plugin seam).** `Flask.test_cli_runner()` (`src/flask/app.py:727-744`) reads `cls = self.test_cli_runner_class`; when it is `None` it imports `FlaskCliRunner` lazily from `.testing` and returns `cls(self, **kwargs)`. The attribute itself is declared as `test_cli_runner_class: type[FlaskCliRunner] | None = None` on the shared base class (`src/flask/sansio/app.py:277`), whose docstring states the class is "the `click.testing.CliRunner` subclass, by default `flask.testing.FlaskCliRunner`" and that its `__init__` must take a Flask app first. So the default is resolved at call time in `Flask`, not bound at class-definition time — the app instance is what makes the runner concrete, and replacing the attribute swaps in the runner without touching the call site.

**2. Runner class → base Click runner (inheritance).** `src/flask/testing.py:12` `from click.testing import CliRunner`; `src/flask/testing.py:265` `class FlaskCliRunner(CliRunner):`. The Flask runner adds only the app-carrying behaviour; all isolation mechanics are inherited from Click.

**3. Application instance → application-loading helper (the bridge).** `FlaskCliRunner.__init__` stores `self.app = app` and calls `super().__init__(**kwargs)` (`src/flask/testing.py:272-275`). `FlaskCliRunner.invoke` then defaults `cli = self.app.cli` when no command is passed, and, when `"obj"` is not already in `kwargs`, sets `kwargs["obj"] = ScriptInfo(create_app=lambda: self.app)` before delegating with `super().invoke(cli, args, **kwargs)` (`src/flask/testing.py:289-298`). That lambda is the single point where the live app object crosses from `testing.py` into `cli.py`.

**4. Helper → application instance (loading, resolved through the injected callable).** `ScriptInfo` (`src/flask/cli.py:293`) holds `create_app`, `app_import_path`, and `self._loaded_app: Flask | None = None` (`cli.py:316`, `cli.py:327`). `load_app()` (`cli.py:333-372`) returns `self._loaded_app` immediately if set (`cli.py:338-339`); otherwise it prefers `self.create_app()` (`cli.py:341-342`), falls back to `locate_app` via `app_import_path`, then to `wsgi.py`/`app.py` discovery, raises `NoAppException` if nothing is found, applies `app.debug = get_debug_flag()` when `set_debug_flag` is true, and caches with `self._loaded_app = app; return app` (`cli.py:370-372`). Because the runner injected `create_app=lambda: self.app`, the first branch fires and every later call returns the identical object — the memoization is what keeps one app instance behind all commands in a run.

**5. Helper is reached from commands via the Click context.** Commands obtain it with `ctx.ensure_object(ScriptInfo).load_app()` (`src/flask/cli.py:397`, and likewise at `444`, `618`, `640`); `pass_script_info = click.make_pass_decorator(ScriptInfo, ensure=True)` (`cli.py:377`) is the decorator form. At line 397-398 the loaded app is also entered as `ctx.with_resource(app.app_context())`, so the app context, not only the app object, is scoped to the command invocation.

**6. Isolation is the base runner's.** `CliRunner.invoke` wraps the whole call — `cli.main(args=args or (), prog_name=prog_name, **extra)` — inside `with self.isolation(input=input, env=env, color=color) as outstreams:` (`.venv/Lib/site-packages/click/testing.py:423`, `:460-480`). `CliRunner.isolation()` (`click/testing.py:276-420`) replaces `sys.stdin`/`sys.stdout`/`sys.stderr` with `StreamMixer`-backed `_NamedTextIOWrapper` streams, applies the `env` mapping to `os.environ`, patches `termui.visible_prompt_func` / `hidden_prompt_func` / `termui._getchar` / `utils.should_strip_ansi` / `_compat.should_strip_ansi`, and sets `formatting.FORCED_WIDTH = 80`; the `finally` block restores every one of those, including the original `os.environ` values. This version of Click does **not** `chdir` to a temporary directory (verified by reading the full `isolation()` body). So "proper execution in isolation" resolves, on the literal base-runner anchor, to stream, environment, prompt and ANSI-width isolation, with the app instance itself supplied through the helper rather than through the isolation context.

**7. No import cycle.** `src/flask/testing.py:17` `from .cli import ScriptInfo`, while `src/flask/cli.py` contains no `from .testing` / `import testing` / `FlaskCliRunner`. The arrows are `cli ← testing ← app`, with `app` reaching `testing` only through the lazy import inside `test_cli_runner`.

**8. Production twin.** At real `flask` runtime there is no `FlaskCliRunner`: `FlaskGroup.make_context` sets `extra["obj"] = ScriptInfo(create_app=self.create_app, set_debug_flag=self.set_debug_flag, load_dotenv_defaults=self.load_dotenv)` unless an `obj` is already present (`src/flask/cli.py:669-674`), and commands reach the app through the same `ctx.ensure_object(ScriptInfo).load_app()` call. The test path and the CLI path therefore differ only in who constructs `ScriptInfo`; the helper-`load_app` hop and the app instance it yields are shared.
