## Answer

The parametrization in the exception-raising test is not a list of eight ways to fail the same way — it is a **pairwise `(iname, aname)` table** (`tests/test_cli.py:199-213`) whose two fields feed **two disjoint phases of `locate_app`**, and the reason all eight rows "fail consistently" is that every phase of that function terminates in a dedicated `raise NoAppException`. The consistency lives in the function's error semantics (each distinct failure mode is normalized to the one exception type); the parametrization's job is to drive one row into each of those normalizing sites. A third element is what makes the guarantee unconditional: the test body at `:217-219` calls `locate_app(iname, aname)` with only two arguments, so `raise_if_not_found` keeps its default `True` (`src/flask/cli.py:241`) for all eight rows, closing the one branch that would return `None` instead of raising (`:256-257`).

**Why the two fields partition the work.** Inside `locate_app`, `module_name` is consumed only by `__import__` (`:246`) and `app_name` only by the dispatch at `:261` (`None` → `find_best_app`, non-`None` → `find_app_by_string`). The parameters touch separate parts of the function, so which branch is *reachable* is a function of the combination, not of either field alone: a row with `aname=None` can only fail consistently if its module *also* fails to import — a successful import plus `aname=None` would route to `find_best_app` and return a `Flask` (the success semantics the sibling test `test_locate_app` at `:195` relies on). Conversely, every non-`None` `aname` row imports successfully first and must fail inside `find_app_by_string`.

**The exception-handling semantics that make each route a raise.**

- **Import funnel** — `except ImportError:` at `:247` absorbs both import failure shapes and converts each to `NoAppException`: `sys.exc_info()[2].tb_next` at `:249` distinguishes "the module body raised" (non-`None` → `:250`, "While importing …") from "the module name did not resolve" (`None` → `:255`, "Could not import …"). Only the direct branch consults `raise_if_not_found`; the nested branch raises unconditionally. This is the exact distinction `test_locate_app_suppress_raise` (`:222-228`) encodes with its comment `# only direct import error is suppressed`.
- **App-name funnel** — `find_app_by_string` normalizes every failure shape to `NoAppException`: `SyntaxError` from `ast.parse` (`:131`), a call target that is not an `ast.Name` (`:142`), `ValueError` from `ast.literal_eval` (`:159`), an unexpected AST node (`:163`), `AttributeError` from `getattr` (`:170`, `from e`), a `TypeError` from invoking a factory (`:183`) gated by `_called_with_wrong_args` (`:94-118`), and the tail for a value that is not a `Flask` (`:194`). The `_called_with_wrong_args` check is what separates "the call itself was wrong-arity" (converted) from "the factory raised `TypeError` internally" (re-raised bare).

**The observed row → site mapping** (executed via `uv run python -m pytest tests/test_cli.py::test_locate_app_raises -v` → `8 passed`, plus a per-row instrumentation run; sites are the last `cli.py` frame in the traceback):

| # | (`iname`, `aname`) | phase that fails | raise site | normalization |
|---|---|---|---|---|
| 1 | `notanapp.py, None` | import, direct | `:255` | `from None` — `Could not import 'notanapp.py'.` |
| 2 | `cliapp/app, None` | import, direct | `:255` | `from None` — `Could not import 'cliapp/app'.` |
| 3 | `cliapp.app, notanapp` | app name, lookup | `:170` | `from e` (cause `AttributeError`) |
| 4 | `cliapp.factory, 'create_app2("foo")'` | app name, call | `:183` | `from e` (cause `TypeError`), after `_called_with_wrong_args` → `True` |
| 5 | `cliapp.factory, "create_app("` | app name, parse | `:131` | `from None` (cause `SyntaxError`) |
| 6 | `cliapp.factory, "no_app"` | app name, return check | `:194` | plain `raise` (no cause) — `no_app()` returned `None`, not a `Flask` |

So the interaction is: the combination selects the raise site, and the semantics guarantee that whichever site is selected raises the same exception type — nothing escapes unconverted and no row can return.

**Two pairs are deliberate controls, which is where the parametrization does more than breadth-testing.** Row 4 (`'create_app2("foo")'`) is the wrong-arity twin of the success row `("cliapp.factory", 'create_app2("foo", "bar")', "app2_foo_bar")` at `:189-190`; differing only in argument count, it proves the observed `TypeError` is the arity error being *converted* by the `:180-182` gate rather than propagating. Rows 7 and 8 hold `aname=None` and the default `raise_if_not_found=True` constant while varying only the module name, so they exercise the two halves of the `tb_next` depth check side by side — and `test_locate_app_suppress_raise` independently confirms that this same depth check, not anything about app names, decides suppressibility.

**The limit of what "consistently" means here.** The body is `with pytest.raises(NoAppException): locate_app(iname, aname)` with no `match=` (`:218`), so the test asserts only the exception **type**. It does not discriminate which of the raise sites fired, and the executor's compiled messages were recorded by instrumentation, not compared by the test. The established guarantee is therefore "any of these eight argument shapes raises `NoAppException`"; the site-level mapping above is established by source-reading plus execution, not by the test's own assertion. A final consequence of the phase split: `find_best_app` is never reached by any of the eight rows (every `aname=None` row also fails at `__import__`), so the mirrored `_called_with_wrong_args` guard at `:76-85` is not exercised by this test, and the observable role of `aname=None` in the table is negative — it is the value paired with un-importable module names, not the trigger of any branch.
