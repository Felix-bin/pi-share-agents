## The hidden coupling: one name string, written by one path and re-derived by another

The only thing linking the decorators' state to the response lifecycle is the **registered blueprint name string**. There is no object reference joining the two halves: a URL rule does not point at its blueprint, and a hook list does not point at the blueprint object it came from. Hook state is written at decoration time under the literal sentinel key `None`; `Blueprint.register` renames that key to the blueprint's dotted registered name when copying it into the app; and the request lifecycle independently re-derives the same dotted name from the matched rule's endpoint. Nothing enforces that the two compositions agree, and when they disagree the failure is silent — the hook simply never runs.

**Where the state is written — decoration time, immediate.** `Blueprint` does not override the hook decorators (only `add_url_rule`, `sansio/blueprints.py:413`), so it inherits the `Scaffold` implementations, which store under the literal key `None` on the blueprint itself: `before_request` `scaffold.py:483`, `after_request` `:504`, `teardown_request` `:538`, `context_processor` `:555`, `url_value_preprocessor` `:580`, `url_defaults` `:597`; and `view_functions[endpoint]` inside the `endpoint` decorator `:454`. All carry `@setupmethod`, so `_check_setup_finished` runs first. This is an immediate write, unlike the route path: `Blueprint.route`/`add_url_rule` ends in `self.record(lambda s: s.add_url_rule(...))` (`sansio/blueprints.py:436`), i.e. a closure in `deferred_functions` (`:230`) replayed only at `:334`.

**Where the key is renamed — registration time.** `Blueprint.register` composes `name = f"{name_prefix}.{self_name}".lstrip(".")` (`:302-304`), raises `ValueError` if that name is already in `app.blueprints` (`:307-315`), sets `_got_registered_once = True` (`:320`), builds `state = self.make_setup_state(app, options, first_bp_registration)` (`:321-322`), then `if first_bp_registration or first_name_registration: self._merge_blueprint_funcs(app, name)` (`:331-332`). `_merge_blueprint_funcs` (`:379-402`) *is* the rename: `key = name if key is None else f"{name}.{key}"`, extended into the app's `before_request_funcs`, `after_request_funcs`, `teardown_request_funcs`, `url_default_functions`, `url_value_preprocessors`, `template_context_processors`; `error_handler_spec` gets the same rename by assignment; `view_functions` is copied **verbatim, with no prefix** (`:399-400`).

**Where the key is re-derived — request time.** The name is reconstructed from the matched rule, not from the blueprint object: `Request.blueprint → endpoint.rpartition(".")[0]` (`wrappers.py:162-176`), `Request.blueprints → _split_blueprint_path` walking the dotted path upward (`:181-195`). Consumers: `app.py:1281` `names = (None, *reversed(request.blueprints))` for `url_value_preprocessors` then `before_request_funcs`; `app.py:1316` `chain(request.blueprints, (None,))` with `reversed(self.after_request_funcs[name])` in `process_response`; `app.py:1353` the same in `do_teardown_request`; `app.py:521` for template context processors; `app.py:774/804/857` for error handlers; `app.py:902` `view_functions[rule.endpoint]`.

**The sentinel does double duty.** At request time `None` means *app scope*. At decoration time it means *a blueprint that has not been registered yet*. Blueprint-level app-wide hooks are written under `None` **on the app** through `record_once` (`blueprints.py:558-559`, `:568-569`, `:578-579`, `:590-591`, `:619-620`, `:629-630`, `:604-607`), so they are recovered by the `None` entry of the request-time name list.

### What nested registration does to it

1. A nested blueprint's hooks live under the dotted key `parent.child` while each ancestor is a separate key, so the lifecycle must walk the dotted path upward at read time — the hook list is addressable only through the name its endpoint encodes.
2. The child's `name_prefix` is injected by the parent at registration, `bp_options["name_prefix"] = name` (`blueprints.py:376`). The *endpoint* prefix is composed by `BlueprintSetupState.add_url_rule` (`:112` `f"{self.name_prefix}.{self.name}.{endpoint}".lstrip(".")`, fields `:79-80`) while the *hook* key is composed by `Blueprint.register`/`_merge_blueprint_funcs` (`:302-304`, `:384`). Two different functions derive related keys from the same options dict, and any divergence produces no error at all — a hook that never fires.

### What conditional registration does to it

1. The merge gate at `:331` mixes **two different notions of "first"**: `first_bp_registration` (`:316`, per blueprint object) and `first_name_registration` (`:317`, per composed name). Because `first_name_registration` is computed *after* the `ValueError` guard at `:307-315`, it is necessarily `True` whenever it is reached, which makes the composite gate always true as written. The clauses are nevertheless not interchangeable: for a blueprint nested a second time under a different parent, `first_bp_registration` is `False` and only the `first_name_registration` clause keeps the merge running — runtime-confirmed, hooks still merge under `'p2.shared'`.
2. `record_once` uses a **third** notion of "first". Its wrapper tests `state.first_registration` (`:240-242`), which is the `first_bp_registration` handed to `make_setup_state` at `:321-322`. On that same second nesting it is `False`, so `record_once`-wrapped app-level hooks do *not* re-run — runtime-confirmed, `len(app.before_request_funcs[None])` stays `1` after the second parent registration. Per-blueprint hooks merge again; app-level hooks do not. The two families answer "is this the first registration?" differently, from the same `Blueprint.register` call.
3. Because hook state is written immediately while route state is deferred, registration order constrains what may be decorated: decorating after registration is a hard failure (`_check_setup_finished`, `blueprints.py:213-221`, reached via `_got_registered_once`), and `register_blueprint` after the app's first request is likewise refused, leaving any late route at 404. Hooks registered *before* registration do follow a `name=` remap — runtime-confirmed, the hook fires with `request.blueprint == 'renamed'`.

### The one place the invariant is knowingly broken

`@bp.endpoint("bar")` puts the view into `view_functions`, which is merged verbatim (`:399-400`), while `BlueprintSetupState.add_url_rule` would have prefixed the endpoint. Runtime-confirmed: rules `[('/foo','bar')]`, `GET /foo → 200`, `GET /bp_prefix/bar → 404`. Since `"bar"` carries no dot, `Request.blueprint` returns `None` (`wrappers.py:173-176`), so the request-time key is the app-scope `None` and the blueprint's own hooks never attach to that route. This asymmetry is pinned by `tests/test_blueprints.py::test_endpoint_decorator:346-360`.

*Small correction to the executor's account:* it reported the endpoint-derived key for `'bar'` as `''`. Per `wrappers.py:173-176` the key is `None` (no dot ⇒ `None`), which is why app-level hooks rather than `''`-keyed hooks resolve.

*Contradiction between the two evidence sets, resolved:* the retriever concluded the gate at `:331` is "effectively always true / vestigial" (its item 11), while the executor called `first_name_registration` "the live half of the gate" needed to save the second nesting. These are not actually opposed: the whole expression is always true (retriever, correct), and on the multi-parent path it is the `first_name_registration` clause that makes it so (executor, correct). What the retriever's reading overstates is rem *ovability* — dropping that clause would change the second-nesting merge, so the always-true expression is load-bearing but has no live false branch.
