## Modular component registration with static serving and shared caching

The repository implements this as a **three-layer split**: a shared sans‑IO base carries static *configuration* and the registration contract, the I/O subclasses carry static *serving*, and both subclasses implement the same caching hook so that app-served and blueprint-served assets behave identically.

**1. Shared base — configuration and registration only (`src/flask/sansio/scaffold.py`)**
`Scaffold` owns everything static-related that is not serving: `_static_folder`/`_static_url_path`, the `static_folder`, `has_static_folder` and `static_url_path` properties (including deriving the URL prefix from the folder basename), and `jinja_loader` (`sansio/scaffold.py:224-269`). It also owns the registration machinery used by both components — the `setupmethod` guard (`scaffold.py:42`) and `add_url_rule` (`scaffold.py:368`). Both `App` (`sansio/app.py`) and `Blueprint` (`sansio/blueprints.py:118`) derive from it. The sans-IO split itself is the 3.0.0 change "Restructure the code such that the Flask (app) and Blueprint classes have Sans-IO bases" (`CHANGES.rst:100-101`).

**2. Serving lives on the two I/O components, not on the base**
`Flask.send_static_file` / `Flask.get_send_file_max_age` (`src/flask/app.py:281-328`) and `Blueprint.send_static_file` / `Blueprint.get_send_file_max_age` (`src/flask/blueprints.py:55-102`) are the only static-serving code. Both delegate to `flask.helpers.send_from_directory` (`src/flask/helpers.py:503+`), which is a thin Flask-specific wrapper over Werkzeug's `send_file` passing `environ`, `USE_X_SENDFILE`, the app's `response_class` and `_root_path` (`helpers.py:387-395`). So the file-serving engine is separated out of the app/blueprint framework classes entirely.

**3. Registration differs by component — eager for the app, deferred for the blueprint**
- *App*: registered eagerly in `Flask.__init__` when `has_static_folder`. The rule is `f"{self.static_url_path}/<path:filename>"` with `endpoint="static"` and `host=static_host`, guarded by `assert bool(static_host) == host_matching`; the view function is a lambda over a `weakref.ref(self)` so no reference cycle forms between app and view (`app.py:262-278`).
- *Blueprint*: registered lazily. `Blueprint.add_url_rule` records a deferred function instead of touching an app (`sansio/blueprints.py:413-445`, appended at `:230`); those are replayed in `Blueprint.register(app, options)` (`sansio/blueprints.py:273`), which `App.register_blueprint` calls (`sansio/app.py:570-591`, re-exported at `app.py:570`). If `has_static_folder`, `register` adds `f"{self.static_url_path}/<path:filename>"` with `view_func=self.send_static_file, endpoint="static"` (`sansio/blueprints.py:323-327`). `BlueprintSetupState.add_url_rule` then applies `url_prefix`, `subdomain` and `url_defaults` and prefixes the endpoint with the blueprint name — `f"{self.name_prefix}.{self.name}.{endpoint}"` (`sansio/blueprints.py:87-117`). That is why the app's static file resolves as `static` and a blueprint's as `admin.static` (`tests/test_blueprints.py:210-214`).
- *Consequence, explicitly documented*: if the blueprint has no `url_prefix`, the app's static route takes precedence and the blueprint's static files are not reachable (`sansio/blueprints.py:144-147`).
- Registering the same blueprint twice under one name is an error, and the "first registration" flags decide whether blueprint funcs are merged into the app (`sansio/blueprints.py:305-334`).

**4. How caching stays consistent across both components**
- Both classes define `get_send_file_max_age(filename)` reading `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]` (default `None`, `app.py:201`), converting a `timedelta` to seconds and otherwise returning the value (`app.py:281-301`, `blueprints.py:55-76`). `None` means `no-cache` plus conditional requests rather than a timed cache (`helpers.py:446-449`).
- Each `send_static_file` **calls its own** `get_send_file_max_age` and passes the result as `max_age` into `send_from_directory`, with the explicit in-code rationale: "send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too." (`app.py:323-328`, `blueprints.py:97-102`). This pre-resolved `max_age` is what lets a *blueprint* override take effect even though Werkzeug would only consult the app.
- Direct `send_file` / `send_from_directory` calls fall back to the same app hook: `_prepare_send_file_kwargs` sets `max_age` to `current_app.get_send_file_max_age` when none was passed (`helpers.py:387-389`), which the `send_file` docstring also states (`helpers.py:498`).
- Consistency is achieved by **deliberate duplication, not shared code**: the two `get_send_file_max_age` bodies are equivalent and both docstrings say so — "Note this is a duplicate of the same method in the Flask class." (`app.py:285-286`, `blueprints.py:62-63`; in `app.py` the sentence names `Flask` while inside `Flask` itself).
- Both extension points are exercised by tests: config value applied to a blueprint's static file (`tests/test_blueprints.py:194-206`), a blueprint subclass returning `100` unaffected by `SEND_FILE_MAX_AGE_DEFAULT` (`tests/test_blueprints.py:220-244`), and an app subclass returning `10` for both `app.send_static_file` and `flask.send_file` (`tests/test_helpers.py:40-90`).
- The design intent is recorded in the 0.9 changelog: `Flask` and `Blueprint` both provide the `get_send_file_max_age` hook, with `SEND_FILE_MAX_AGE_DEFAULT` feeding the default implementation (`CHANGES.rst:1292-1300`).
