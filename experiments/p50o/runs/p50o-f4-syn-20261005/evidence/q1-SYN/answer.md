## The relationship

The ASCII-only control is a single boolean switch — `DefaultJSONProvider.ensure_ascii`, default `True` (`src/flask/json/provider.py:144`) — that determines, one-for-one, whether non-ASCII characters appear as escape sequences or as themselves in serialized output. Nothing else in serialization depends on it.

**It is consumed at exactly one site.** `DefaultJSONProvider.dumps` does `kwargs.setdefault("ensure_ascii", self.ensure_ascii)` and then calls the stdlib `json.dumps(obj, **kwargs)` (`src/flask/json/provider.py:177`, with `import json` at line 5). So the switch is not interpreted by the framework at all; it is handed to Python's encoder, and all Unicode representation follows stdlib `json.dumps` semantics. A literal grep for `ensure_ascii` over `src/` returns only the attribute definition (line 144) and this forwarding line (line 177). Because the value is applied via `setdefault`, an explicit `ensure_ascii=` keyword argument (e.g. `app.json.dumps(obj, ensure_ascii=False)`) overrides the attribute.

**Default behaviour is ASCII-only.** `json_provider_class` is `DefaultJSONProvider` (`src/flask/sansio/app.py:230`) and `self.json = self.json_provider_class(self)` (`src/flask/sansio/app.py:329`), so `app.json.ensure_ascii` is `True` unless changed — escaping is the out-of-the-box path, raw Unicode is the opt-out. The attribute also exists only on `DefaultJSONProvider`, not on the base `JSONProvider`; a provider substituted through `json_provider_class` need not have it.

**Both output paths inherit it, through that one site.** `response()` builds the body via `self.dumps(...)` (`src/flask/json/provider.py:216-218`), so `jsonify` and response serialization are governed by the same switch; `flask.json.dumps` forwards to `current_app.json.dumps` when an app context exists (`src/flask/json/__init__.py:13-43`), hitting the same line. Without an app context it falls back to stdlib `json.dumps`, whose own default is also `ensure_ascii=True` — consistent, but not driven by the attribute.

**Observed behaviour, measured in this worktree** (executor run with `PYTHONPATH=src`, Python 3.13.9):

- `ensure_ascii=True` on `"\N{SNOWMAN}"` → the 8-character ASCII string `"\u2603"`; `str.isascii()` is `True`; the response body is `b'"\\u2603"\n'` with all bytes < 0x80.
- `ensure_ascii=False` → the 3-character string `"` + U+2603 + `"`; the response body is `b'"\xe2\x98\x83"\n'`, i.e. the UTF-8 bytes of the literal character plus the trailing `\n` that `response()` appends.
- Non-BMP characters: under `True`, U+1F600 is emitted as the surrogate-pair escapes `\ud83d\ude00`; under `False` as the raw astral character. So the ASCII-only mode can *widen* output for astral characters rather than shorten it — the retriever stated this as an unverified inference, and the executor's run now observes it.
- The mode is representation-only, not a semantic change: both outputs `json.loads` back to the identical original object, and become equal once the `\uXXXX` escapes are re-expanded. JSON's own structural escaping (quote, backslash, newline, tab) is byte-for-byte identical under both settings.

**Pinned by the suite.** `tests/test_json.py:48-54` parametrizes exactly `(True, '"\\u2603"')` / `(False, '"\u2603"')` — both pass — and `tests/test_testing.py:110-115` shows `EnvironBuilder.json_dumps()` taking `app.json.ensure_ascii = False` from the app and producing a UTF-8 literal body. That second path is test-only evidence; the werkzeug-side plumbing that reads `app.json` was not read.

**Provenance of the parameter.** It is the successor to the removed `JSON_AS_ASCII` config key: deprecated in 2.2 as "JSON configuration is moved to attributes on the default `app.json` provider" (`CHANGES.rst:285-289`), removed in 2.3 along with the other JSON config keys (`CHANGES.rst:153`), and `docs/config.rst:441` records that "The default `app.json` provider has equivalent attributes instead". The retriever reported "no prose to reconcile" because a grep for the literal `ensure_ascii` matches nothing under `*.rst`; prose does exist, but under the old config-key name, and it *supports* the attribute relationship rather than contradicting it. No source in this working directory contradicts the mapping above.
