## Modular component registration and separate static serving in this Flask worktree

**The architecture is three layers, all verified in `src/`.**

**1. One shared registration base: `Scaffold`.** `src/flask/sansio/scaffold.py:52` defines `Scaffold` with the docstring "Common behavior shared between :class:`~flask.Flask` and :class:`~flask.blueprints.Blueprint`." It owns the entire registration machinery and is factored out, not duplicated: `route` (`:336`), `add_url_rule` as an abstract stub (`:368`, body `raise NotImplementedError` at `:433`), the `_check_setup_finished` hook (`:220-221`) and the `setupmethod` decorator (`:42-49`) that enforces registration-before-first-request. Both components subclass it: `App(Scaffold)` at `sansio/app.py:59` → `Flask(App)` at `flask/app.py:81`, and `Blueprint(Scaffold)` at `sansio/blueprints.py:119` → `Blueprint(SansioBlueprint)` at `flask/blueprints.py:18`. `Scaffold` also carries the static-path policy used by both: `static_folder` property/setter (`:224`, `:234`), `has_static_folder` (`:241`), `static_url_path` (`:252`, derived from the folder basename).

**2. Static serving is registered by the component, implemented outside the framework core.** The modular component (blueprints — `docs/blueprints.rst:1` "Modular Applications with Blueprints", `:8-9` "Flask uses a concept of *blueprints* for making application components") registers its own static route at registration time, in the sansio layer:

```python
if self.has_static_folder:
    state.add_url_rule(f"{self.static_url_path}/<path:filename>",
                       view_func=self.send_static_file,  # type: ignore[attr-defined]
                       endpoint="static")          # sansio/blueprints.py:323-327
```

That layer only *registers*; the file-serving body sits in the component's own concrete module — `Blueprint.send_static_file` at `flask/blueprints.py:82-101`, ending in `send_from_directory(self.static_folder, filename, max_age=max_age)` — as a peer of the app's copy at `flask/app.py:308-327`, whose rule `Flask.__init__` registers separately at `app.py:262-279`. Corroborating the split: `send_static_file` and `get_send_file_max_age` exist nowhere in `src/flask/sansio/` (grep returns only the concrete modules plus the `self.send_static_file` reference above, which needs `# type: ignore[attr-defined]` precisely because the body is not in sansio), and `sansio/README.md` states that sansio code "cannot do any IO, nor be part of a likely IO path" and "cannot use the Flask globals". Behavioural consequence documented at `docs/blueprints.rst:215-218`: a blueprint's static URL is `url_prefix + /static`, its endpoint is `blueprint_name.static`, and with no `url_prefix` the application's `/static` route takes precedence — the two components are distinct but coexist.

**3. Caching parity is an explicit duplicated hook plus one shared config key.** Both components define `get_send_file_max_age` with byte-identical bodies — `flask/app.py:281` and `flask/blueprints.py:55` — reading `current_app.config["SEND_FILE_MAX_AGE_DEFAULT"]`, returning `None` for `None` (conditional requests), `int(value.total_seconds())` for a `timedelta`, else the value. Both `send_static_file` implementations call the hook themselves rather than letting Werkzeug fall back to the app (`flask/app.py:325`, `flask/blueprints.py:99`), under the same comment in both files: *"send_file only knows to call get_send_file_max_age on the app, call it here so it works for blueprints too."* The duplication is deliberate and cross-referenced — the marker docstring "Note this is a duplicate of the same method in the Flask class" occurs exactly four times in `src/` (`app.py:290,314`; `blueprints.py:64,88`) — and `helpers.py:387-389` makes the app hook the default (`kwargs["max_age"] = current_app.get_send_file_max_age`) for generic `send_file`. Design intent is recorded at `CHANGES.rst:1292-1300` ("``Flask`` and ``Blueprint`` now provide a ``get_send_file_max_age`` hook … The default max-age for ``send_file`` and static files can be configured through a new ``SEND_FILE_MAX_AGE_DEFAULT`` configuration variable") and at `docs/config.rst:250-260` ("Override this value on a per-file basis using :meth:`~flask.Flask.get_send_file_max_age` on the application or blueprint").

**The parity holds at runtime.** The executor ran, with `PYTHONPATH=src ./.venv/Scripts/python.exe -m pytest`: `tests/test_blueprints.py -k "static or max_age or cache"` → exit 0, 2 passed (`test_templates_and_static`, `test_default_static_max_age`); `tests/test_helpers.py -k "static_file or send_file"` → exit 0, 2 passed (`test_send_file`, `test_static_file`). Those tests pin the contract on both components: the blueprint route `/admin/static/css/test.css` returns `Cache-Control: max-age=<SEND_FILE_MAX_AGE_DEFAULT>` (`tests/test_blueprints.py:193-207`); a `Blueprint` subclass overriding `get_send_file_max_age` to 100 wins over a configured value (`:219-245`); and `app.send_static_file` / `flask.send_file` both report `max_age is None` by default and `3600` after setting the config key (`tests/test_helpers.py:44-70`). No failing test indicates a defect in this path.
