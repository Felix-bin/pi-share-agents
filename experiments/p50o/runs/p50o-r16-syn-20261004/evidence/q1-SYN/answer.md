## Answer

**The relationship, stated directly.** In the referent framework — Flask, this cwd clone, `85c5d93cbd049c4bd0679c36fd1ddcae8c37b642`, version `3.2.0.dev` (`pyproject.toml:2-5`) — the ASCII-only control parameter is `DefaultJSONProvider.ensure_ascii`, a **class attribute defaulting to `True`** (`src/flask/json/provider.py:144`), and its relationship to Unicode representation is a **one-way output-representation switch that is applied as a default, not a hard-coded argument**:

- `ensure_ascii = True` (the default) ⇒ every non-ASCII character in the serialized document — **string values *and* object keys** — is replaced by `\uXXXX` escape sequences, so the returned string is pure ASCII (`isascii() == True`). A non-BMP character is emitted as a **UTF-16 surrogate pair**, i.e. two escapes (U+1D11E → `"\ud834\udd1e"`, 14 chars).
- `ensure_ascii = False` ⇒ the character is emitted **verbatim** as the literal Unicode character in the returned `str`; ASCII-only-ness is then lost, and the bytes only become non-ASCII when the string is **UTF-8 encoded downstream** (into the response/file).

The switch governs *spelling only, never meaning*: both forms decode to the identical value, so any code that parses rather than compares wire text cannot see the difference.

**The mechanism that makes it a default rather than a mandate** (`provider.py:166-179`):

```
176      kwargs.setdefault("default", self.default)
177      kwargs.setdefault("ensure_ascii", self.ensure_ascii)
178      kwargs.setdefault("sort_keys", self.sort_keys)
179      return json.dumps(obj, **kwargs)
```

This yields a three-level precedence: **explicit per-call kwarg > `app.json.ensure_ascii` (per-instance attribute) > class attribute `True`**. A caller-supplied `ensure_ascii=` always wins because of `setdefault`; assignment on one provider instance shadows only that instance (`run1-raw` check 1c: `app_a=False` in its own `__dict__`, `app_b=True` still on the class). `response()` (`provider.py:189-215`) builds `dump_args` for whitespace only (`indent 2` vs `separators (",", ":")`) and never touches `ensure_ascii`, so debug/compact formatting does not interact with the ASCII control. The base `JSONProvider` has no `ensure_ascii` at all (`dumps` is `raise NotImplementedError`, `provider.py:41-45`) — it is a stdlib-backed `DefaultJSONProvider` concept, wired in per app at `sansio/app.py:230, 329` (`json_provider_class = DefaultJSONProvider`; `self.json = self.json_provider_class(self)`), replaceable wholesale by substituting the provider class (`provider.py:21-31`).

**One genuine partial counterexample to "flip the flag ⇒ verbatim output".** `|tojson` (`app.py:422` installs `self.json.dumps`) keeps Jinja's htmlsafe escaping independently of the flag: with `ensure_ascii=False`, `'</script>'` still renders `'"\\u003c/script\\u003e"'` and `'<☃>&'` still renders `'"\\u003c\u2603\u003e\u0026"'`, while `app.json.dumps(attr=False)` of the same value gives `'"</script>"` raw. So that path keeps escapes for a *different* reason (HTML safety), not because of the provider.
