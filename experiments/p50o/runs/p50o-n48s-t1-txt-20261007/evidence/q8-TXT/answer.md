## The interaction: how the `(iname, aname)` parametrization and `locate_app`'s exception handling produce a uniform failure

**Target, confirmed.** The exception-raising test is `tests/test_cli.py::test_locate_app_raises` (199–219): eight `(iname, aname)` pairs, body `with pytest.raises(NoAppException): locate_app(iname, aname)`. The property intersection — parametrized on an import and an app-name argument ∧ asserts a raise ∧ drives `locate_app` — leaves exactly this test; `test_locate_app` (180–196) is parametrized but asserts a result, `test_locate_app_suppress_raise` (222–228) raises but is not parametrized, `test_find_best_app` (48–126) is neither parametrized on import/app-name nor a `locate_app` caller. The function under discussion is `locate_app(module_name, app_name, raise_if_not_found=True)` (`src/flask/cli.py:241–264`), which delegates the app-name half to `find_app_by_string` (`src/flask/cli.py:121–196`).

**The interaction.** `locate_app` has two *sequential* failure axes, and the parametrization is laid out so each pair trips exactly one guard on exactly one axis, giving one unique failure path per pair and (near-)full coverage of the guards:

- **Import axis (`module_name`, cli.py:242–257).** A single `try: __import__(module_name)` catches `ImportError` (244–246) and normalizes it. The *branch* is decided only by traceback depth: `sys.exc_info()[2].tb_next` truthy (249) ⇒ the `ImportError` came from *inside* the imported module ⇒ `NoAppException("While importing … an ImportError was raised:\n\n<traceback>")` `from None` (250–253); falsy ⇒ the module itself could not be imported ⇒ `NoAppException("Could not import '…'.")` `from None` (255), or `return None` when `raise_if_not_found=False` (256–257). Because this axis is checked first, an `aname=None` pair with an unimportable `iname` never reaches the app-name code at all.
- **App-name axis (cli.py:260–262 → `find_app_by_string`, 121–196).** Once the import succeeds, `app_name` selects which guard fires: the `ast.parse` `SyntaxError` guard (129–134, `from None`), the `ast.Name`/`ast.Call` branching (135–140) with the "simple name only" guard (141–145) and the `literal_eval` `ValueError` guard (156–160, `from None`) and the else guard (161–165), the `getattr` `AttributeError` guard (167–173, `from e`), the `inspect.isfunction` call with the `TypeError`/`_called_with_wrong_args` discrimination (176–187, `from e` for an arity error, bare `raise` for a `TypeError` raised inside the factory), and the final `isinstance(app, Flask)` return-type check (191–196, no chaining).

**Why this yields consistent failure.** The consistency is *at the API boundary, not in the error object*: every one of the eight pairs ends as `NoAppException`, even though the underlying causes differ in type (`ModuleNotFoundError`, `ImportError`, `AttributeError`, `TypeError`, `SyntaxError`) and in origin (import machinery vs. module top level vs. attribute lookup vs. factory call vs. return value). The parametrization is what makes that uniformity testable with one assertion: the four `aname=None` pairs vary only the import axis (missing file, path-style name, module that raises during import, non-Python file), and the four `cliapp.factory` / `cliapp.app` pairs vary only the app-name axis (missing attribute, wrong arity, unparsable name, `None` return). By crossing the axes the test pins each guard to a distinct input, and the handlers preserve the original error only as chained context — `from None` where the original would be noise (a depth-1 import failure, a `SyntaxError` from `ast.parse`, the nested-import traceback, which is instead inlined in the message), `from e` where it is diagnostic (the missing attribute, the arity `TypeError`).

**Which pairs exercise the two discriminating branches.**
- **Traceback-depth distinction (`tb_next`, cli.py:249):** pair 7 `("cliapp.importerrorapp", None)` is the nested side (`tests/test_apps/cliapp/importerrorapp.py` raises `ImportError()` at line 3 before `testapp = Flask("testapp")` at line 5), and pairs 1, 2, 8 are the depth-1 side. Pair 1 `("notanapp.py", None)` is the one that is *pinned* by a test assertion rather than by prediction: `test_locate_app_suppress_raise` (222–224) asserts `locate_app("notanapp.py", None, raise_if_not_found=False) is None`, which can only hold if `tb_next` is falsy, and the same test asserts that `("cliapp.importerrorapp", None)` still raises with `raise_if_not_found=False` (227–228), pinning pair 7's nested branch. Pairs 2 and 8 were the open prediction; the executor measured `tb_next` falsy for both, so both take cli.py:255 with `Could not import '<iname>'.` (pair 8's context is the parent-module error `No module named 'cliapp.message'`, which is why the message says `'cliapp.message.txt'` while the context names `'cliapp.message'`).
- **`_called_with_wrong_args` discrimination:** pair 4 `("cliapp.factory", 'create_app2("foo")')` exercises the **True** side — the `TypeError` is an arity error, so it is swallowed and converted (raise at cli.py:183, not the bare re-raise at 180–181). The **False** side (a `TypeError` raised *inside* a factory propagating unconverted, cli.py:180–181) is exercised by **no pair of this test**: the analogous case lives in `test_find_best_app` (test_cli.py:121–125), and the executor confirmed it directly (`find_app_by_string(m, "bad_factory")` → `TypeError: bad bad factory!`, no `NoAppException`). So the discrimination is only half-exercised inside `test_locate_app_raises`.

**Two corrections to the expected branch coverage.** (i) **No pair reaches `find_best_app`.** All four `aname=None` pairs abort in the import block, so the `app_name is None` dispatch (cli.py:261–262) and `find_best_app` (cli.py:41–90) are not exercised by this test; they are covered by `test_locate_app` rows with `aname=None` (182–184) and by `test_find_best_app`. (ii) **Four guards are hit by no row of the eight:** the "simple name only" guard (141–145), the `literal_eval` `ValueError` guard (156–160), the else guard (161–165), and the bare `TypeError` re-raise (180–181). The "consistency" the test demonstrates is therefore real but bounded by what its eight curated pairs touch.

**Answer status.** The interaction asked about is answered: within `test_locate_app_raises`, the `(iname, aname)` parametrization populates the import axis (rows 1, 2, 7, 8) and the app-name axis (rows 3–6) so that each pair lands on a distinct guard, and `locate_app`/`find_app_by_string` normalize every one of those distinct failures into `NoAppException` — with traceback depth alone deciding the import-axis branch, and `_called_with_wrong_args` alone deciding whether an app-name-axis `TypeError` is normalized or allowed to propagate. The plan's out-of-scope items (whether this normalizing design is desirable, whether the `tb_next` heuristic should be narrowed, any code change, delivery format) remain open by design and are not settled here.
