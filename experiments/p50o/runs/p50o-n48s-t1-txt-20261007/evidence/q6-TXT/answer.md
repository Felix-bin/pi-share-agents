# Answer

Template functions registered on a blueprint become visible at render time because there is exactly one Jinja `Environment` instance per application — cached on the app — and blueprint registration is deferred until that app is known, at which point the deferred callbacks mutate that same instance's `filters` / `tests` / `globals` dicts. The chain has five links, in dependency order:

**1. One shared environment object per app (the enabling property).** `App.jinja_env` is a `@cached_property` (`src/flask/sansio/app.py:469-477`) that returns `self.create_jinja_environment()` (`src/flask/sansio/app.py:477`). The concrete implementation `Flask.create_jinja_environment` constructs `rv = self.jinja_environment(self, **options)` (`src/flask/app.py:409`) and seeds `rv.globals` with `url_for`, `get_flashed_messages`, `config`, `request`, `session`, `g` (`src/flask/app.py:410-419`). `Flask.jinja_environment` is `Environment` (`src/flask/templating.py:39-48`, which also stores `self.app = app`). Because it is a `cached_property`, the first access creates the instance and stores it in `app.__dict__`; every later access — including all accesses after blueprint registration — returns that same object. This is the single property that makes late-registered functions observable.

**2. Every render entry point reads that same instance.** `render_template` (`src/flask/templating.py:149`), `render_template_string` (`src/flask/templating.py:161`), `stream_template` (`src/flask/templating.py:203`) and `stream_template_string` (`src/flask/templating.py:218`) each resolve `app = current_app._get_current_object()` and then use `app.jinja_env...`; `get_template_attribute` uses `getattr(current_app.jinja_env.get_template(template_name).module, attribute)` (`src/flask/helpers.py:308`). No render path copies the environment or builds a fresh one, so any mutation of the cached instance's namespace dicts is picked up by the next render.

**3. Blueprint registration is deferred, not performed eagerly.** `Blueprint.__init__` creates `self.deferred_functions: list[DeferredSetupFunction] = []` (`src/flask/sansio/blueprints.py:204`); `record` merely appends — its whole body is `self.deferred_functions.append(func)` (`src/flask/sansio/blueprints.py:222-231`); `record_once` defines `wrapper(state)` that calls `func(state)` only `if state.first_registration` and passes it to `self.record(update_wrapper(wrapper, func))` (`src/flask/sansio/blueprints.py:233-245`). This is what makes a blueprint-defined function survive until an application exists, without the blueprint holding any environment of its own.

**4. Each `add_app_template_*` records a callback that writes into the app's environment.** All three define an inner `register_template(state)` and defer it with `record_once`:
- filter — `state.app.jinja_env.filters[name or f.__name__] = f` (`src/flask/sansio/blueprints.py:472-473`), deferred at `:475`;
- test — `state.app.jinja_env.tests[name or f.__name__] = f` (`src/flask/sansio/blueprints.py:510-511`), deferred at `:513`;
- global — `state.app.jinja_env.globals[name or f.__name__] = f` (`src/flask/sansio/blueprints.py:548-549`), deferred at `:551`.

These are the *same* dicts the app-level API writes (`Flask.add_template_filter` `src/flask/sansio/app.py:695`, `add_template_test` `:738`, `add_template_global` `:776`), so blueprint- and app-registered names coexist in one namespace.

**5. `Blueprint.register` supplies the real app and runs the callbacks.** `Flask.register_blueprint` is `@setupmethod` (`src/flask/sansio/app.py:570-595`) and its body is `blueprint.register(self, options)` (`src/flask/sansio/app.py:595`). Inside `Blueprint.register` (`src/flask/sansio/blueprints.py:273`): the blueprint is recorded in `app.blueprints` and `self._got_registered_once = True` is set (`:320`), `state = self.make_setup_state(app, options, first_bp_registration)` is built (`:321`) — `make_setup_state` returns `BlueprintSetupState(self, app, options, first_registration)` (`:247-253`) whose `__init__` stores `self.app = app`, "a reference to the current application" (`:38-52`) — and then the single dispatch point runs every recorded callback against that app: `for deferred in self.deferred_functions: deferred(state)` (`src/flask/sansio/blueprints.py:334-335`). That loop is where `state.app.jinja_env.filters|tests|globals[...]` is actually executed.

**Guards that keep this consistent.** `Blueprint._check_setup_finished` raises `AssertionError` when `self._got_registered_once` is set (`src/flask/sansio/blueprints.py:213-221`), and `setupmethod` invokes it before every wrapped method (`src/flask/sansio/scaffold.py:42-49`); `record`, `record_once` and all `add_app_template_*` methods are `@setupmethod`, so no registration can be added after first registration. `record_once`'s first-registration guard (`:241-242`) stops a callback from being applied twice when the same blueprint is registered again under a different name or on a second app. (The deferred loop at `:334-335` itself runs unconditionally; the `record_once` guard is what suppresses the second application. Repeating the *same* name on the *same* app does not reach the guard at all — the name-collision check in `register` raises `ValueError: The name '...' is already registered...` at `src/flask/sansio/blueprints.py:311`.)

**Nested components use the same path, not a different one.** `Blueprint.register_blueprint` only appends `(blueprint, options)` to `self._blueprints` (`src/flask/sansio/blueprints.py:256-271`), and at the end of `register` the parent iterates them calling `blueprint.register(app, bp_options)` (`src/flask/sansio/blueprints.py:377`). A nested blueprint therefore lands in the identical `deferred_functions → register → state.app.jinja_env.*` flow and ends up in the same application environment.

**The "shared environment" is a shared namespace, not a shared template source list.** `DispatchingJinjaLoader` (`src/flask/templating.py:52-120`) is a separate mechanism: it resolves where template *files* come from, yielding the app loader then each blueprint's loader via `self.app.iter_blueprints()` (`src/flask/templating.py:106, 117`). It never touches `filters`, `tests` or `globals`. The isolating negative result confirms the namespaces live on the app only: a full-file search for `jinja_env` in `src/flask/sansio/blueprints.py` returns exactly three lines — `:473`, `:511`, `:549` — all of the form `state.app.jinja_env.*`. A `Blueprint` owns no Jinja environment.

## Scope and open items

- **Answered:** the full mechanism by which blueprint-registered filters/tests/globals are reachable during rendering — the deferred-record → `Blueprint.register` → shared cached `jinja_env` chain, with each link cited and the end-to-end behaviour verified by a passing test run.
- **Reading chosen:** "modular component registration" = Flask blueprint registration. Supported by the docstrings calling these functions "available in any template rendered by the application" (`src/flask/sansio/blueprints.py:465-467` and the analogous test/global docstrings) and by the absence of any blueprint-local environment (only three `state.app.jinja_env.*` lines exist). The alternative reading — extensions as the modular component — is not supported by any distinct code path here: extensions would mutate the app environment directly through the app-level API (`src/flask/sansio/app.py:695/738/776`), which is the same namespace-writing mechanism as links 1–2 without links 3–5.
- **Not established / not decided here:** whether the lazy creation of `jinja_env` during blueprint registration (observed: registration alone populates `app.__dict__['jinja_env']`, which pins `jinja_options` since later changes "will have no effect" per `src/flask/sansio/app.py:473-476`) counts as a defect; and whether this should be framed as documentation or bug analysis. Nothing in the source states the consequence.
- **Setup caveat for anyone re-running the tests:** the plain `python -m pytest` form in the plan does not run here (system Python has no `flask`), and the venv's default Flask resolution points outside the working directory, so a run without `PYTHONPATH=src` would measure a different source tree.
- **Unrelated artifact:** `flask_mut2_i417ar2x/mutated_test.py` concerns subdomain matching and references no `jinja_env`, `filters`, `tests` or `globals`; it does not bear on this question.
