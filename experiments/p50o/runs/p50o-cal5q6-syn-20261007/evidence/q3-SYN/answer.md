## The interaction

The consistency comes from a two-way match between what the parametrization varies and what the handler normalises. The test varies two axes (`tests/test_cli.py:199–219`): `iname` (module import string) and `aname` (app-name string or `None` sentinel), with **no third parameter and no `raise_if_not_found` argument** — so the default `True` (`src/flask/cli.py:241`) is the only path under test. The handler returns exactly one exception type for every failure the two axes can produce, and the assertion checks only that type (`pytest.raises(NoAppException)` at `tests/test_cli.py:218` — no message, no field), which is what makes the matrix a *normalisation* contract rather than a per-case raise-site contract.

**Axis 1 — `iname` decides which layer raises, and both layers are covered.** Four pairs (`notanapp.py`, `cliapp/app`, `cliapp.message.txt`, `cliapp.importerrorapp`) fail at the import guard; four (`cliapp.app`+`notanapp`, `create_app2("foo")`, `create_app(`, `no_app`) survive `__import__` and fail inside a resolver. Executor's trace shows each pair lands on a single `cli.py` frame — 255, 255, 255, 250, 170, 183, 131, 194 respectively — so no `ModuleNotFoundError`, in-module `ImportError`, `AttributeError`, `TypeError` or `SyntaxError` escapes.

**The import guard splits on traceback depth** (`src/flask/cli.py:245–257`): `if sys.exc_info()[2].tb_next` → `NoAppException("While importing …")` at 250 unconditionally (the error came from inside the module); `elif raise_if_not_found` → `NoAppException("Could not import …")` at 255; `else: return None` is the only non-raising exit. This is where the omitted parameter matters: `("notanapp.py", None)`, `("cliapp/app", None)` and `("cliapp.message.txt", None)` all take the depth-1 branch at 255, so they raise *only because* the default is `True`. The sibling test `test_locate_app_suppress_raise` (`tests/test_cli.py:222–228`) pins exactly that boundary — `locate_app("notanapp.py", None, raise_if_not_found=False) is None` while `cliapp.importerrorapp` still raises, "only direct import error is suppressed". The retriever had left the actual depth for `cliapp/app` and `cliapp.message.txt` unverified; the executor closed it — both are depth-1/line 255, not the nested branch at 250.

**Axis 2 — `aname` decides whether a resolver is entered at all.** `None` dispatches to `find_best_app(module)` (`cli.py:261`), a string to `find_app_by_string(module, app_name)` (263). `NoAppException` is `class NoAppException(click.UsageError)` (`cli.py:37`) — not an `ImportError` subclass — so it propagates out of the import guard's `except ImportError` untouched and nothing raised inside the resolvers is swallowed. Both resolvers terminate in `NoAppException`: `find_best_app` at 60/80/87, `find_app_by_string` at 131 (`SyntaxError` from `ast.parse`), 142, 159 (`ValueError`), 163, 170 (`AttributeError`), 183 (wrong-args), 194 (call result is not a `Flask` — the `no_app()` → `None` case). The only non-normalised path is a `TypeError` raised *inside* a factory, deliberately re-raised by `if not _called_with_wrong_args(attr): raise` (`cli.py:176–181`); no parametrized case triggers it, because `create_app2("foo")` fails argument binding before the call and is converted at 183.

**Where the question's premise needs correcting.** The two axes are not independent for the failure guarantee. All four `aname=None` pairs fail *at the import layer*, before `app_name is None` is ever evaluated at line 261 (retriever's inference, confirmed by executor's trace). So the `None` half of the matrix is not made consistent by the `find_best_app` sentinel branch — it is made consistent by the import guard plus the `True` default. The sentinel path's own raise sites (60/80/87) are never exercised by a failing case in this test.

**Net interaction:** `iname` selects the failure layer, `aname=None` vs. string selects whether a resolver runs, and `raise_if_not_found=True` (implied by the missing parameter) makes the depth-1 import failure raise instead of returning `None` — while the handler's uniform `NoAppException` (plus the type-only assertion) collapses `ModuleNotFoundError`, in-module `ImportError`, `SyntaxError`, `ValueError`/`AttributeError`, wrong-args `TypeError` and a non-`Flask` return into one observable outcome. That is what "fails consistently" means here: one exception type per pair, not one raise site.
