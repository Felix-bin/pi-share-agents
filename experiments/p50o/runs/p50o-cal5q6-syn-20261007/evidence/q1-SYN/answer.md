# What makes blueprint-registered template functions reachable at render

Accessibility is guaranteed by a three-stage chain (defer → replay → in-place mutation of one cached environment), with context processors taking a separate two-seam path. "Modular component" = `Blueprint`; "shared template environment" = the single `App.jinja_env` instance (no other environment object exists in `src/`).

**1. Setup calls are deferred, because a blueprint is configured before an app exists.** `Blueprint.__init__` creates `self.deferred_functions` (`src/flask/sansio/blueprints.py:204`); `Blueprint.record` appends to it (`:224-230`); `Blueprint.record_once` wraps the callable so it executes only `if state.first_registration`, then records it (`:233-244`). After registration, `_check_setup_finished` makes further setup calls raise `AssertionError` (`:212-221`). So a registered function is not stored on the blueprint as a filter — it is stored as a *closure to be run later against whatever app registers the blueprint*.

**2. Registration replays the buffer against the concrete app.** `Blueprint.register` sets `self._got_registered_once = True` (`:320`), builds `state = self.make_setup_state(app, options, first_bp_registration)` (`:322`) and runs `for deferred in self.deferred_functions: deferred(state)` (`:334`); the entry point is `App.register_blueprint` → `blueprint.register(self, options)` (`src/flask/sansio/app.py:570-595`). Because `state.app` is the real app object, these closures need neither an app nor a request context to take effect.

**3. The replayed writes land in the single environment that rendering later queries.** Each `add_app_template_*` closes over `state.app.jinja_env` and writes in place:
- filter: `state.app.jinja_env.filters[name or f.__name__] = f` (`blueprints.py:473`, recorded at `:475`)
- test: `...jinja_env.tests[...] = f` (`:511`, recorded at `:513`)
- global: `...jinja_env.globals[...] = f` (`:549`, recorded at `:551`)

`jinja_env` is a `cached_property` returning `create_jinja_environment()` (`sansio/app.py:469-477`, `:479`), and every render path reads that same property — `src/flask/templating.py:149, 161, 203, 218` and `src/flask/helpers.py:308`. There is no per-render copy, merge or snapshot, so the mutation is simply *already present* on the object later queried. The documented boundary is the other direction: changing `jinja_options` after the environment is created has no effect (`sansio/app.py:243-244`). Consequently the order of first environment creation versus `register_blueprint` does not matter — the executor probe forced the env into existence *before* registration and still saw the filter/test/global appear afterwards on the same, identity-preserved object.

**4. Context processors do not go through `jinja_env`; they use two distinct seams.**
- App-wide: `Blueprint.app_context_processor` records `lambda s: s.app.template_context_processors.setdefault(None, []).append(f)` (`blueprints.py:584-593`, esp. `:590-592`) — visible to every template.
- Blueprint-local: `Scaffold.context_processor` appends immediately to the blueprint's own `template_context_processors[None]` (`src/flask/sansio/scaffold.py:542-556`), and `Blueprint._merge_blueprint_funcs` (`blueprints.py:379-410`) `extend`s the blueprint's dict into the app's, renaming the `None` key to the blueprint's dotted name (`:383-386`, call at `:410`); `register` invokes it only when `first_bp_registration or first_name_registration` (`:328-330`).
- Consumption: `App.update_template_context` (`src/flask/app.py:506-533`) iterates `names = (None,)` plus `reversed(request.blueprints)` when a request context exists, doing `context.update(self.ensure_sync(func)())` per registered processor, with caller-supplied context re-applied last. The map is seeded `defaultdict(list, {None: [_default_template_ctx_processor]})` (`scaffold.py:182-184`).

**5. Nested blueprints inherit the same behaviour.** Nested registration recurses (`blueprints.py:375-377`), and the executor probe confirmed `record_once` replay reaches the shared env for a child blueprint too (`app.blueprints == ['parent', 'parent.child']`; parent and child filters both present).

**Verification status of each claim.** Points 1–3 and 5 are sourced at file:line (re-checked by grep/read here) and additionally *observed* at runtime: nothing was in the environment before `register_blueprint`, and after it the filter, test and global appeared by identity in the same cached env. Context-processor bucket behaviour is asserted by the suite (`tests/test_blueprints.py:636-668`: `app_context_processor` appears on both pages, `context_processor` only on the blueprint page). The whole file passes (`tests/test_blueprints.py`: 60 passed, exit 0; the four template-function tests alone: 4 passed, exit 0) with `PYTHONPATH=src`.

**Two claims are genuinely not established.**
- "Shared template environment" = `App.jinja_env` is an inference from a full-tree `jinja_env` grep finding no second environment object; whether the task intends a different shared object is unresolved.
- Ordering between `add_template_filter` calls and first environment creation is *not enforced*: there is no re-sync mechanism. It is harmless only because the cached instance is mutated in place, which the probe showed. Also unprobed: re-registering the same blueprint object under a second name skips `record_once` replay (`first_bp_registration` false) while the earlier in-place mutation persists, and `tests/test_blueprints.py::test_nested_blueprint` covers only routes/errorhandlers, not nested template functions.

- Retrieval caveat: the top-ranked corpus chunk (`templating.py:97-136`, `DispatchingJinjaLoader`) concerns template *lookup*, not template-function accessibility, and does not support the answer; it was a ranking miss.
- Open: the identity of the "shared template environment" beyond `App.jinja_env`; ordering guarantees (absent by design); repeat-registration interaction with `record_once`'s `first_registration` guard; no existing test covers nested template functions.
