## The dependency chain

The three artifacts form a closed loop: the **Flask application instance** creates the **base Click testing runner**, which is seeded with the **application loading helper**, which resolves back to that same application instance once a command runs inside the runner's isolation.

**1. Flask application instance → runner factory.** The app owns the runner class: `test_cli_runner_class: type[FlaskCliRunner] | None = None` (`src/flask/sansio/app.py:277`), and `Flask.test_cli_runner(**kwargs)` (`src/flask/app.py:727`) resolves it — `cls = self.test_cli_runner_class`, falling back to `from .testing import FlaskCliRunner as cls` when unset — then returns `cls(self, **kwargs)`, passing the app itself as the first positional argument. So the app depends on the runner class only through an overridable attribute (the annotation import is TYPE_CHECKING-only: `src/flask/app.py:62`, `src/flask/sansio/app.py:40`), and the runner depends on the app as its construction argument.

**2. Runner → base Click runner.** `FlaskCliRunner(app, **kwargs)` (`src/flask/testing.py:265`) stores `self.app = app` and calls `super().__init__(**kwargs)`, inheriting from `click.testing.CliRunner` (`from click.testing import CliRunner`, `src/flask/testing.py:12`; installed click 8.2.1, `click>=8.1.3` required at `pyproject.toml:25`). `CliRunner.invoke` runs the command as `with self.isolation(...)` → `cli.main(...)` → `Result`; that isolation — rebinding `sys.stdin/stdout/stderr`, patching `os.environ` via `make_env`, mocking Click prompt functions — is inherited wholesale from Click. Flask adds no isolation mechanism of its own; verified in the read of `src/flask/testing.py:265-297` and the retriever's evidence (Click line numbers there are approximate).

**3. Runner → helper (the join edge).** `FlaskCliRunner.invoke` (`src/flask/testing.py:275-297`) closes the missing link: `if cli is None: cli = self.app.cli`, then `if "obj" not in kwargs: kwargs["obj"] = ScriptInfo(create_app=lambda: self.app)`, then `return super().invoke(cli, args, **kwargs)`. The helper is not passed to the runner's constructor; it is manufactured per invocation, and the closure `lambda: self.app` is the sole connection between the runner and the application.

**4. Helper → application instance.** The helper is `class ScriptInfo` (`src/flask/cli.py:293`), holding `app_import_path`, `create_app`, `set_debug_flag`, `load_dotenv_defaults` and `self._loaded_app: Flask | None = None`. `load_app()` (`src/flask/cli.py:333`) returns the cached instance if present, otherwise calls `self.create_app()` — here the closure, yielding the very app under test — else resolves `app_import_path` through `prepare_import`/`locate_app`, else tries `wsgi.py` then `app.py`, and raises `NoAppException` if nothing resolves; it then sets `app.debug = get_debug_flag()` when `set_debug_flag`, caches, and returns. The command side reaches it via `pass_script_info` (`src/flask/cli.py:375`) and `with_appcontext` (`src/flask/cli.py:397`, `ctx.ensure_object(ScriptInfo).load_app()`); `FlaskGroup` (`src/flask/cli.py:623`, `:645`) and `run_command` (`:955`) are the other consumers.

So the *tested* chain is: app → `test_cli_runner()` → `FlaskCliRunner(self)` → `invoke` injects `obj=ScriptInfo(create_app=lambda: self.app)` → Click's `CliRunner.invoke` executes `cli.main` inside `CliRunner.isolation()` → `with_appcontext` → `ScriptInfo.load_app()` → the same app instance. The production path is structurally identical but takes its `create_app` from the group: `FlaskGroup.make_context` (`src/flask/cli.py:659-666`) sets `extra["obj"] = ScriptInfo(create_app=self.create_app, set_debug_flag=self.set_debug_flag, load_dotenv_defaults=self.load_dotenv)`, with `main()` at `src/flask/cli.py:1122`.

**Runtime status.** The chain executes as described against this worktree's `src/flask`: six named tests pass with exit 0 — `tests/test_testing.py:338` (`test_cli_runner_class`), `:348` (`test_cli_invoke`), `:366` (`test_cli_custom_obj`, which shows an explicit `obj` bypasses the injected one), `tests/test_cli.py:257` (`test_scriptinfo`), `tests/test_cli.py:676` and `:696` (invoke through `app.test_cli_runner()`) — and a direct probe reported `ctx.obj type: ScriptInfo` with `ctx.obj.load_app() is app: True`, i.e. the closure really returns the identical instance. The retriever's documentation corroboration (`docs/testing.rst:245-256`, `docs/api.rst:147`, `CHANGES.rst:938`) matches.

**Two things the chain is not.** There is no single artifact that both subclasses `click.testing.CliRunner` and defines `load_app`/app-import logic — the two responsibilities are split across `FlaskCliRunner` and `ScriptInfo`, joined only at runtime by the `create_app` closure (no merged class found). And the isolation guarantee is Click's, not Flask's: Flask's contribution is that the isolated environment is pre-seeded with a helper resolving to the app under test, so `with_appcontext` succeeds inside it.
