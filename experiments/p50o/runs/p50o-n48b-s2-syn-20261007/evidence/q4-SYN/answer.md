## Why `Flask.open_resource` is read-only

**The short answer: because the thing it opens is a package artifact, not a runtime data directory, and Flask puts the writable case in a different method and a different folder.** `Flask.open_resource` resolves paths against `self.root_path`, which `src/flask/sansio/scaffold.py:95-100` defines as `get_root_path(self.import_name)` and documents as *"Absolute path to the package on the filesystem. Used to look up resources contained in the package."* That is where templates, `static/`, and checked-in files like `schema.sql` live — the installed or checked-out code, which the framework treats as read-only input. For files that must change at runtime, Flask has a separate location, the instance folder: `docs/config.rst:772-776` says the instance folder *"is designed to not be under version control and be deployment specific. It's the perfect place to drop things that either change at runtime or configuration files."* That folder gets its own method, `Flask.open_instance_resource` (`src/flask/app.py:363-386`), whose docstring states the pairing explicitly: *"Open a resource file relative to the application's instance folder :attr:`instance_path`. Unlike :meth:`open_resource`, files in the instance folder can be opened for writing."* The restriction on `open_resource`, in other words, is the deliberate complement of that split: read the package, write the instance folder.

**How the restriction is actually implemented.** It is an explicit API gate, not a filesystem or permission mechanism. `src/flask/app.py:330-361`:

```python
if mode not in {"r", "rt", "rb"}:
    raise ValueError("Resources can only be opened for reading.")
path = os.path.join(self.root_path, resource)
```

The method's own contract states the same rule twice — the docstring's first line is *"Open a resource file relative to :attr:`root_path` for reading."*, and `:param mode:` says *"Only reading is supported, valid values are ``"r"`` (or ``"rt"``) and ``"rb"``."* The gate sits before the path join and before both `open()` calls, and there is no writable branch anywhere in the body (executor probe: gate index 55, `open()` call indices 217 and 269 — *gate precedes every open(): True*). `src/flask/blueprints.py:104-128` is a byte-for-byte equivalent: same `{"r","rt","rb"}` whitelist, same `ValueError` message, same `os.path.join(self.root_path, resource)`, described in its docstring as *"The blueprint-relative equivalent of the app's `Flask.open_resource` method."* So every code path that opens a package-relative resource enforces the same rule, and the only route to a writable resource is `instance_path`.

**The supporting explanation for why a package path is treated as read-only input.** `docs/design.rst:54-63` explains that the package name passed to `Flask(__name__)` exists *"to properly load resources relative to your module"* and that Flask *"can then access the package to figure out where the templates and static files are stored (see `Flask.open_resource`)"*; the same passage rejects the current working directory as *"a very unreliable way to determine where the application is"* because it is *"process-wide"* and webservers may set it elsewhere. `src/flask/helpers.py:570-576` confirms `get_root_path` returns the package/module directory in the normal case, falling back to the CWD only *"If it cannot be found"*. Since that resolved path is an installed or version-controlled artifact shared across a process and possibly across deployments, the API exposes it for reading only.

**The `"rt"` entry is historical parity, not a third capability.** `CHANGES.rst:686-687` records: *"`open_resource` accepts the `"rt"` file mode. This still does the same thing as `"r"`. :issue:`3163`"* — which is why the allowed set is three strings rather than two. The `encoding` parameter in the signature was added in Flask 3.1 (`CHANGES.rst:35-37`, issue 5504), matching the `.. versionchanged:: 3.1` note in the method docstring; it does not widen the mode set.

**The rule is verified to hold in this worktree's source.** `tests/test_helpers.py:338-343` parametrizes `("r", "rb", "rt")` and asserts each mode opens and reads `static/index.html`; `tests/test_helpers.py:346-351` parametrizes `("w", "x", "a", "r+")` and asserts each raises `ValueError`. Run against this checkout (`PYTHONPATH=src .venv/Scripts/python.exe -m pytest tests/test_helpers.py -k open_resource -v`): 9 passed, 0 failed. The executor's direct probe produced the same split — `r`/`rb`/`rt` OK, and `w`, `x`, `a`, `r+`, `wb`, `ab`, `w+` all raising `ValueError('Resources can only be opened for reading.')` — while `open_instance_resource` accepted `w` and `a` with no gate. A tmpdir probe showed a refused `"w"` left the file's content unchanged while a plain `open(path, "w")` on the same file succeeded, confirming the restriction comes from this method's gate rather than from filesystem permissions. Documented usage matches the contract: `docs/tutorial/database.rst:126,141-143` and `docs/patterns/sqlite3.rst:140` call `open_resource('schema.sql')` purely to read, with the tutorial noting *"`open_resource()` opens a file relative to the `flaskr` package ... you won't necessarily know where that location is when deploying the application later."*

**Observed vs. inferred — keep this distinction.** The read-only whitelist, the error message, the `root_path` join, the identical blueprint method, the explicit *"Unlike `open_resource` ... can be opened for writing"* contrast, and the two folder definitions are all quoted directly from the code and docs. The causal sentence — *package resources therefore write access is withheld, and the instance folder therefore carries the writable variant* — is **not written verbatim anywhere in this repository**. It is assembled from the `open_instance_resource` contrast (`src/flask/app.py:366-368`) plus the `root_path` docstring (`src/flask/sansio/scaffold.py:98-99`), the instance-folder rationale (`docs/config.rst:772-776`), and the package-loading rationale (`docs/design.rst:54-63`). Treat the "why" as a rationale documented in parts, not as a single quoted justification. One further nuance worth preserving: `docs/config.rst` only says referring to paths relative to the application folder "works well if applications are not packages", so the package-vs-runtime-folder split is the documented reason for introducing `instance_path`, not a blanket statement that all package resources are immutable.
