# Why `ScriptInfo` fills a cached `_loaded_app` instead of loading during `__init__`

Two separable reasons, with different evidential strength.

**1. At construction time the app is not yet knowable — so loading in `__init__` is not merely undesirable, it is impossible.** `ScriptInfo` is built inside `FlaskGroup.make_context` (`src/flask/cli.py:657`) while Click is assembling the context, before options are parsed: `670: extra["obj"] = ScriptInfo(create_app=self.create_app, ...)`. The `--app` import path does not exist yet. It is assigned *later*, by `_set_app` (`440`), the callback of the `-A`/`--app` option (`445: info.app_import_path = value`; option declared at `453`), and that option is deliberately eager. The inline comment at `449` — *"This option is eager so the app will be available if --help is given"* — plus the note that `--env-file` must be processed before `--app` is exactly the ordering constraint that `__init__`-time loading would violate. A load in `__init__` would therefore always run with `app_import_path=None` and fall through to the zero-config `wsgi.py`/`app.py` scan (`load_app` body, lines 340–353) before the user's `--app` was ever parsed: the wrong app, or a spurious `NoAppException`. The module-level `cli = FlaskGroup(...)` object (`1110`) is likewise created at import time with nothing to load.

**2. Deferral is what lets the CLI stay usable; the cache is what makes the deferred load a one-off.** Because loading is a separate `load_app()` call, the four late consumers fetch the app only when they need it: `with_appcontext` (`397: app = ctx.ensure_object(ScriptInfo).load_app()`), `FlaskGroup.get_command` (`623`), `list_commands` (`645: rv.update(info.load_app().cli.list_commands(ctx))`), and `run_command` (`955`). Each handles failure differently and needs the app to *not* be loaded eagerly: `get_command` catches `NoAppException`, prints the message and returns `None` so other commands still resolve (622–626); `list_commands` prints only the message for `NoAppException` but a full traceback for other exceptions (644–655). For this half the rationale is explicitly documented: commit `25357078` *"cleaner message when CLI can't load app"* (David Lord, 2020-07-30) states that *"When loading the app fails for the --help command, only the error message is shown, then the help text. The full traceback is shown for other exceptions"*, and the tests pin it — `tests/test_cli.py::test_help_echo_loading_error` (line 413) and `::test_help_echo_exception` (line 428) both assert `--help` exits `0` with no app / with a `create_app` that raises.

The cache itself is the guard/`return` pair at `338–339: if self._loaded_app is not None: return self._loaded_app` with the single write at `371: self._loaded_app = app`, and the slot declared in `__init__` at `331`. Its effect is that import plus factory execution happen once and every caller gets the same object; the docstring contract at `334–336` states this ("Calling this multiple times will just result in the already loaded app to be returned"), and `tests/test_cli.py::test_scriptinfo` (line 247) asserts identity repeatedly (`obj.load_app() is app` at lines 251, 259, 263, 271), with line 274 showing `NoAppException` surfaces only on `load_app()`, never at construction. On this last point the evidence is weaker than for the rest: **no file in the repository states the cached-once / single-execution rationale in words.** The commit that introduced the attribute is the only one that ever touched it — `git log --oneline --follow -S"_loaded_app" -- src/flask/cli.py` returns exactly one commit, `3bdb90f0` *"Added click support to Flask"* (Armin Ronacher, 2014-04-28) — and its message body is **empty**. History is full (5439 commits, HEAD `85c5d93c`, 2025-06-12), so this is a genuine single introduction, not a truncated log. `5d8e3565` *"refactor lazy loading"* (2022-08-01) describes run-command and reloader exception handling, not the cache. `docs/cli.rst` "Application Discovery" (lines 14–56) documents only what discovery does, not why it is lazy; `docs/api.rst` merely autodocs `ScriptInfo` (line 703); `CHANGES.rst` has no entry on the lazy design.

**Bottom line:** reason 1 is established directly from the code; the deferral half of reason 2 is established by a commit body, an inline comment and two tests; the cached-once purpose is a well-supported inference from code, docstring and tests, but it is not author-stated anywhere in the repository.
