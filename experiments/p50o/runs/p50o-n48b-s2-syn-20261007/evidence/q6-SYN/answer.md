# Answer

**In this worktree the premise does not hold: setting `accessed` in the dictionary access methods has no effect on the signed-cookie conversion path at all. `accessed` is not an input to the decision that runs the conversion.** The attribute is written unconditionally in three methods — `self.accessed = True` at `src/flask/sessions.py:85` (`__getitem__`), `:89` (`get`), `:93` (`setdefault`) — and read in exactly one place, `src/flask/sessions.py:363` `if session.accessed:` → `response.vary.add("Cookie")` (`:364`). Nothing else in `src/flask` reads it. The conversion, `val = self.get_signing_serializer(app).dumps(dict(session))` at `src/flask/sessions.py:387`, is reached only after these guards, in source order: `if not session:` early return (`:368`), and `if not self.should_set_cookie(app, session): return` (`:383`). `should_set_cookie` is `return session.modified or (session.permanent and app.config["SESSION_REFRESH_EACH_REQUEST"])` (`:259-261`). The gate is **`modified`**, set by werkzeug's `CallbackDict` callback `on_update` (`src/flask/sessions.py:79-80`, installed at `:82`), which fires only on real dict-item mutation (`_always_update` and the `setdefault`/`pop` callbacks in `.venv/Lib/site-packages/werkzeug/datastructures/mixins.py`). A bare attribute store is not a dict mutation, so the read methods set `accessed` without setting `modified` and without reaching `dumps`.

Runtime probes confirm this (worktree flask 3.2.0.dev0, itsdangerous 2.2.0, `.venv/Scripts/python.exe`, `dumps` counted by wrapping the serializer from `SecureCookieSessionInterface.get_signing_serializer`):

- Read-only request via `session.get` / `session["k"]`: **`dumps` calls = 0**, no `Set-Cookie`, `Vary: Cookie` present, and afterwards `accessed=True, modified=False`.
- Setting `session.modified = True` directly, with no dict mutation: **`dumps` = 1** and `Set-Cookie` emitted — the conversion follows `modified`, not any access flag.
- `should_set_cookie.__code__.co_names` is `('modified', 'permanent', 'config')`; `'accessed'` is not among them.
- `tests/test_basic.py:246-250` already asserts a `session.get` leaves `accessed` True and `modified` False; `tests/test_basic.py:520-571` asserts the read endpoints (`/get`, `/getitem`, `/setdefault`, `/clear`) produce only a `Vary: Cookie` header; `CHANGES.rst:868-869` states the design intent: "`Cookie` is added to the response's `Vary` header if the session is accessed at all during the request (and not deleted)" (PR 2288). That is the whole purpose of the flag.

**What actually re-runs the conversion during frequent reads.** Only two things do, and neither is `accessed`:

1. **A `setdefault` that inserts.** `SecureCookieSession.setdefault` (`:92-94`) sets `accessed`, then werkzeug's `UpdateDictMixin.setdefault` calls `on_update` only `if modified and ...` where `modified = key not in self`. Measured: `setdefault` on a **missing** key → `dumps` = 1, `Set-Cookie` yes, `modified=True` — i.e. it behaves as a write, not a read. On an existing key there is no mutation and no callback.
2. **Permanent sessions with refresh enabled.** A read-only request on a permanent session still re-signs every time when `SESSION_REFRESH_EACH_REQUEST` is True (default `True` at `src/flask/app.py:197`); with it set to `False` the same request gave `dumps` = 0 and no `Set-Cookie` (while `Vary: Cookie` stayed). So frequent reads *do* hit the conversion for permanent sessions — but the trigger is `session.permanent and SESSION_REFRESH_EACH_REQUEST`, an independent cause. The `accessed` flag is set along the way only as a side effect, because the `permanent` property (`:28-30`, `return self.get("_permanent", False)`) calls the overridden `get`; that side effect neither causes nor modifies the conversion.

**The cost of the unconditional attribute store, quantified.** It is a read-path cost, not a conversion cost: `SecureCookieSession.get` 151 ns vs `dict.get` 35 ns, `session["k"]` 129 ns vs 31 ns (N=200000) — roughly +120 ns per read. One conversion measured 115.5 µs/call (N=3000, 20 nested entries: `TaggedJSONSerializer.dumps` ~81.3 µs, `zlib.compress` ~7.9 µs, `signer.sign` ~7.6 µs, serializer construction ~5.34 µs, `dict(session)` copy ~0.11 µs). So even under the premise's reading, the flag store is ~0.1% of one conversion; the only way access tracking could matter for conversion throughput would be if it triggered the conversion, and it does not. `dict(session)` at `:387` provably bypasses the overridden `__getitem__` (a subclass counting `__getitem__` calls: `dict(p)` → 0 calls, a comprehension → 3), so the conversion cannot retroactively set `accessed` either.
