## Why `ScriptInfo` takes both `create_app` and `app_import_path`

They are not two designs competing inside one object; they are the two different callers of the same "produce a Flask app" step, and each caller can only supply one of the two shapes.

`ScriptInfo` — "Helper object to deal with Flask applications … used internally in the dispatching to click" (`src/flask/cli.py:293`) — declares both inputs as parallel optional fields in one constructor:

- `app_import_path: str | None = None` — `#: Optionally the import path for the Flask application.` (`src/flask/cli.py:307`, `312`)
- `create_app: t.Callable[..., Flask] | None = None` — `#: Optionally a function that is passed the script info to create the instance of the application.` (`src/flask/cli.py:308`, `314-315`)

`load_app()` (`src/flask/cli.py:333-379`) turns them into a three-tier resolution: use `self.create_app()` if set (`341-342`), else resolve `self.app_import_path` (`path:name` split, `prepare_import`, `locate_app`, `344-350`), else fall back to `wsgi.py`/`app.py` autodiscovery (`351-357`), and raise `NoAppException("Could not locate a Flask application. Use the 'flask --app' option, 'FLASK_APP' environment variable, or a 'wsgi.py' or 'app.py' file…")` if all three miss (`359-364`).

**The import path is the wire format of the stock `flask` command, so it has to be a string.** The `-A/--app` option's callback writes exactly that attribute — `info = ctx.ensure_object(ScriptInfo); info.app_import_path = value` (`src/flask/cli.py:445`) — and env binding comes from `extra["context_settings"].setdefault("auto_envvar_prefix", "FLASK")` → `FLASK_APP` (`FlaskGroup.__init__`, `~580-583`). A string is unavoidable there because the user types it, so this side also needs machinery a callable never needs: `find_best_app` searching `app`, `application`, the sole `Flask` instance, then zero-arg `create_app`/`make_app` with a `TypeError` probe (`src/flask/cli.py:53-110`), and `find_app_by_string` parsing the `name(args)` grammar via `ast.parse(..., mode="eval")` + `ast.literal_eval` (`120-181`). The `--app` help text spells out that grammar (`metavar="IMPORT"`, `'module:name'`, name optional for `app`/`application`/`create_app`/`make_app`, `'name(args)'` to pass arguments), which is the capability that justifies the string form: `docs/cli.rst:12-67` documents `--app 'hello:create_app("dev")'` — "The ``create_app`` factory in ``hello`` is called with the string ``'dev'`` as the argument."

**The callable is the console-script escape hatch for code that already holds a factory object and does not want to be discovered by name.** `FlaskGroup.__init__(..., create_app=...)` stores it (`src/flask/cli.py:563-568`, `589`) and `FlaskGroup.make_context` threads it into the object, building `ScriptInfo(create_app=self.create_app, set_debug_flag=..., load_dotenv_defaults=...)` only when the caller supplied no `obj` (`~667-673`). The docs state the intent directly: "When you are using the app factory pattern, it may be more convenient to define your own Click script. Instead of using ``--app`` and letting Flask load your application, you can create your own Click object and export it as a console script entry point." (`docs/cli.rst:473-476`) — followed by `@click.group(cls=FlaskGroup, create_app=create_app)` (`478-491`) and "Note that you don't need to set ``--app``" (`493-501`). Because the factory is handed over as an object, none of the string side applies: it is invoked as `app = self.create_app()` with no name resolution and no argument parsing (`src/flask/cli.py:341-342`). The same docs section keeps the hierarchy straight — its admonition notes a custom script's module-level errors break the reloader and "The ``flask`` command, being separate from your code, does not have this issue and is recommended in most cases" (`503-513`), so the callable is an opt-in path, not an equal-status default.

**Precedence, undocumented:** when both fields are set, `create_app` wins unconditionally, purely from branch order (`if self.create_app is not None:` at `341` before the `else: if self.app_import_path:` at `344`). Executed confirmation: `ScriptInfo(app_import_path="no_such_module_xyz:app", create_app=factory).load_app()` returned an app named `made-by-create_app`, and the deliberately bogus import path was never touched. No documentation in `src/flask/cli.py`, `docs/` or `CHANGES.rst` states this rule.

**Contradiction left standing (two sources disagree with the code):** both docstrings claim the callable receives the script info — `src/flask/cli.py:314-315` ("a function that is passed the script info to create the instance of the application") and the `FlaskGroup` docstring `:541-542` ("an optional callback that is passed the script info and returns the loaded app") — but the single call site passes nothing. Executed form: the factory recorded `create_app called with (args, kwargs): [((), {})]`, i.e. zero positional arguments and zero keyword arguments. `pass_script_info` still exists (`src/flask/cli.py:381`) but is not used to invoke `create_app`. `CHANGES.rst` (`~851-857`) is consistent with the code, not the docstrings: "Factory functions are not required to take a ``script_info`` parameter to work with the ``flask`` command" (:pr:`2319`), and `FLASK_APP` may name a factory with arguments (:pr:`2326`).

**Behavioural support:** `tests/test_cli.py::test_scriptinfo` (`247-286`) exercises the import-path forms (`"cliapp.app:testapp"`, an absolute `.py` path, `"<path>:testapp"`), then a local `def create_app(): return Flask("createapp")` passed as `ScriptInfo(create_app=create_app)` (`265-271`), then asserts `pytest.raises(NoAppException, obj.load_app)` for neither (`273-274`) — the two are treated as alternatives, not alternatives-with-a-required-one. Executed: `pytest tests/test_cli.py::test_scriptinfo -q` → `1 passed in 0.11s`; the 8-test subset covering both wiring paths (`test_scriptinfo`, `test_app_cli_has_app_context`, `test_with_appcontext`, `test_appgroup_app_context`, `test_flaskgroup_app_context`, `test_flaskgroup_debug`, `test_flaskgroup_nested`) → `8 passed in 0.40s`; `ScriptInfo().load_app()` → `NoAppException`. End-to-end, in `tests/test_apps` (no `wsgi.py`/`app.py`): `flask --app cliapp.app:testapp routes` printed the route table, exit 0; bare `flask routes` → exit 2 with the "Could not locate a Flask application" error; `FLASK_APP=cliapp.app:testapp flask routes` → route table; `FLASK_APP_IMPORT_PATH=cliapp.app:testapp flask routes` → exit 2, confirming the env binding is `FLASK_APP` and not a name derived from the parameter.
