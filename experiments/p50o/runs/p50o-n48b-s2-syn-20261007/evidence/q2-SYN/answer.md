# Why the async method view is a subclass of the sync dispatch base

**Short answer: because in this codebase there is no asynchronous method view class to begin with.** The library never introduced one. The only class matching that description is `AsyncMethodView` in the test suite (`tests/test_async.py:30`), which subclasses the sync `MethodView`, and it inherits rather than reimplementing dispatch because async support was deliberately placed at a single conversion hook — `current_app.ensure_sync` — that sits *inside* the existing sync dispatch call sites. With that hook in place, an independent async dispatch class would duplicate the method-resolution logic for zero behavioural gain, so the whole upstream change was a two-call-site edit to `MethodView`/`View` rather than a new class.

**1. The premise needs correcting first.** Grepping `src/` finds exactly two view classes: `class View` (`src/flask/views.py:16`) and `class MethodView(View)` (`src/flask/views.py:138`). In `src/`, `def dispatch_request` appears only three times: `app.py:879` (the per-request dispatch), `views.py:78` (the `View` base, which raises `NotImplementedError`), and `views.py:182` (`MethodView`, a plain `def`). There is no async counterpart anywhere in the library. `AsyncMethodView(MethodView)` with `async def get` / `async def post` lives at `tests/test_async.py:30-36` and is registered like any other view at `tests/test_async.py:76`. History agrees that the name is test-local: `git log --all -S"AsyncMethodView"` returns only one commit, and its diff touches no file in `src/` beyond `views.py`.

**2. Why inheriting is sufficient — the mechanism.** Both dispatch paths funnel into one hook:

- `src/flask/views.py:110` and `:116` — both branches of the body generated by `as_view` end in `return current_app.ensure_sync(self.dispatch_request)(**kwargs)`.
- `src/flask/views.py:191` — `MethodView.dispatch_request` ends in `return current_app.ensure_sync(meth)(**kwargs)`, after resolving `meth = getattr(self, request.method.lower(), None)` (`:183`) and the HEAD→GET fallback (`:187-188`).
- `src/flask/app.py:965-976` `ensure_sync` — "Plain `def` functions are returned as-is. `async def` functions are wrapped to run and wait for the response", delegating to `async_to_sync` (`app.py:980-1001`, which imports `asgiref` and raises `RuntimeError` without the async extra).

Because `MethodView.dispatch_request` is itself a plain `def`, the *outer* `ensure_sync` returns it unchanged, and the *inner* `ensure_sync(meth)` is what converts a coroutine `get`/`post`. The consequence, read directly off the code: method lookup, the HEAD→GET fallback, and the `methods` auto-collection in `__init_subclass__` (`:165`) all run as ordinary synchronous code and never have to know whether the handler is async. Async-ness is absorbed at the innermost callable, so it is orthogonal to dispatch — which is exactly why a separate dispatch class buys nothing.

**3. That mechanism was measured, not just read.** `PYTHONPATH=src .venv/Scripts/python.exe -m pytest tests/test_async.py -q` exits 0 with 8 passed in 0.24s (asgiref 3.8.1 present, so the module's `importorskip` guard passes). An instrumented spy on `Flask.ensure_sync`/`Flask.async_to_sync` while driving `AsyncMethodView.as_view("mv")` and `AsyncView.as_view("view")` through the test client recorded: `ensure_sync` was handed `View.as_view.<locals>.view` and `MethodView.dispatch_request` and returned both unchanged, while only the coroutine handlers (`AsyncMethodView.get` on GET, `.post` on POST, `AsyncView.dispatch_request` on `/view`) were passed to `async_to_sync`. `GET /mv`, `POST /mv` and `GET /view` all returned 200; `AsyncMethodView.methods` resolves to `{'POST', 'GET'}` without the class setting it, and `iscoroutinefunction(MethodView.dispatch_request)` is `False` while `iscoroutinefunction(AsyncMethodView.get)` is `True`.

**4. The change history records support added to existing classes, not a new class.** `git log --all -S"ensure_sync(meth)" -- src/flask/views.py` yields one hit: commit `270eb2df`, "Support View and MethodView instances with async handlers" (Miguel Grinberg, 2021-05-28). Its `views.py` diff is five lines — `self.dispatch_request(...)` → `current_app.ensure_sync(self.dispatch_request)(...)` in `as_view`'s generated body, `meth(...)` → `current_app.ensure_sync(meth)(...)` in `MethodView.dispatch_request`, plus `from .globals import current_app`. The same commit added the paragraph now at `docs/async-await.rst:20-24` and the changelog line. `CHANGES.rst:473` (2.0.2): "Support View and MethodView instances with async handlers. :issue:`4112`"; `CHANGES.rst:600` (2.0): async views, error handlers, before/after request and teardown, `:pr:`3412``. The docs state the outcome as a property of the existing classes: "This applies to the `dispatch_request` method in views that inherit from the `flask.views.View` class, as well as all the HTTP method handlers in views that inherit from the `flask.views.MethodView` class" (`docs/async-await.rst:20-24`).

**5. Supporting context, but not a quoted reason.** The documented cost model rules out async being a separate high-performance dispatch architecture: Flask "uses one worker to handle one request/response cycle… Each request still ties up one worker, even for async views" and "**Async is not inherently faster than sync code**" (`docs/async-await.rst:36-48`), with `:69-79` directing performance-seekers to Quart. That context is consistent with reusing `MethodView`, but the docs do **not** draw the connection explicitly — treat it as background, not as the stated rationale.

**What is answered and what is open.** Answered: *what* the async method view is (a test-local `MethodView` subclass, not a library class), and *why* inheriting suffices — the `ensure_sync` boundary at `views.py:110/116/191` absorbs async-ness at the innermost handler, keeping dispatch logic sync-only, verified by the 8-passing test run and the conversion spy, and corroborated by commit `270eb2df`'s five-line diff and the `CHANGES.rst:473`/`as_view` docs wording. Still open: **no sentence anywhere in the worktree states in words why a separate async dispatch class was rejected.** The commit body carries no prose beyond its subject and no PR trailer, and no issue/PR discussion is present, so the rationale in section 2 is derived from the diff and the call sites — a well-supported inference, not a citation. The task's framing ("the asynchronous HTTP method view class") also assumes a library class that does not exist; anyone reading this as design documentation should know the premise is a test fixture.
